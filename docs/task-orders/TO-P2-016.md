## 3. Fresh current-provider reassessment

Current official MEXC Spot documentation was rechecked against the current repository and a live read-only provider observation.

### 3.1 Candle finality

The current MEXC Spot WebSocket K-line schema exposes interval, window start/end, OHLCV, symbol and create time, and states that the stream updates the current candle every second. It does not document a provider final/closed field or an equivalent finality guarantee.

The REST K-line schema exposes open time, OHLCV and close time and states that K-lines are uniquely identified by open time. It does not document close-time as a provider finality assertion.

Therefore no authoritative provider-finality mechanism has been newly identified.

### 3.2 Trade identity / completeness

Current MEXC WebSocket trade-stream documentation exposes price, quantity, trade type and trade time; it does not expose a stable trade identifier or sequence field in the documented trade payload.

The REST recent-trades documentation names an `id` field as Trade id, but the current documented example permits `id: null`. A live read-only observation from the governed SentinelX host returned recent-trade rows with `id=null`.

The current aggregate-trades endpoint documents aggregate tradeId / first tradeId / last tradeId fields, but the current live observation returned `a/f/l=null`. No authoritative continuity/completeness guarantee was established by the provider documentation.

Consequently, no current provider mechanism establishes the unique per-trade identity and complete stream coverage required to manufacture a stronger canonical trade-stream guarantee.

## 4. Repository compatibility finding

The current Meylux normalization contract requires a non-empty `CanonicalTrade.trade_id`.

The current MEXC normalizer obtains that field from provider `id` / `tradeId`. The live provider observations do not supply such a stable identifier on the public REST/WebSocket trade paths examined.

Generating a local hash from price/time/quantity or assigning a receipt-order identifier would not establish provider trade identity, and would introduce collision/order/reproducibility risks. Such a value therefore MUST NOT be silently substituted for authoritative provider identity.

## 5. Resolution target

When activated, Producer shall carry the capability through implementation and independent verification only if a genuine provider-grounded resolution mechanism is available.

The resulting capability must establish, with real evidence:

1. authoritative MEXC candle finality compatible with the existing canonical `is_closed` contract; and/or
2. a provider-grounded unique trade identity and sufficient stream-integrity semantics for the intended canonical trade capability;
3. deterministic acquisition, normalization, persistence, provenance and replay behavior;
4. no fabricated finality, identity, completeness or fallback;
5. compatibility with frozen architecture and contracts unless an explicit change-control decision is obtained.

If only one capability becomes genuinely resolvable, that capability may be delivered independently; failure of one must not be used to discard another legitimately resolvable capability.

## 6. Authorized implementation boundary upon activation

Producer may, within this Task Order and only after activation:

- update the existing MEXC acquisition/normalization path where the provider-grounded mechanism actually supports it;
- add deterministic tests and runtime evidence;
- use necessary read-only SentinelX runtime observation and, if explicitly authorized by CONTROL for implementation acceptance, bounded runtime deployment/execution;
- preserve raw/provider evidence;
- maintain existing canonical identity and persistence semantics unless a real conflict is escalated.

Producer MUST NOT:

- infer candle finality from time, close-time, repeated observation, local clock or absence of messages;
- synthesize trade IDs from receipt order or non-unique market fields;
- infer stream completeness from finite observation;
- substitute another provider;
- weaken `CanonicalCandle.is_closed`;
- introduce a new canonical truth layer;
- rewrite historical evidence;
- modify Binance acceptance;
- perform trading, execution, capital or custody activity.

## 7. Decision boundary

The fresh reassessment has not identified a truthful implementation path from the currently documented/live MEXC public mechanisms.

The exact remaining dependency is therefore:

**MEXC must expose and document an authoritative candle-finality mechanism and/or a stable provider trade-identity/sequence mechanism sufficient for the intended canonical capability.**

Alternatively, if the Owner wishes Meylux to support semantics that do not require those provider guarantees, that requires an explicit architecture/contract ratification and change-control decision. CONTROL and Producer must not make that change implicitly.
