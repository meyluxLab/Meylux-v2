## 2. Objective

Establish the canonical data, identity and validation foundation required by the remaining Phase 3 Validation, Normalization & Data Quality Engine, with an unambiguous governed meaning of valid canonical data before downstream validation and normalization behavior depends upon it.

## 3. Authoritative Basis

The Producer must work within the established repository authority, including `DOC-V2-ARCH-001`, `PH-P3`, `STEP-P3-001`, `DOC-P3-001` as reference roadmap, existing canonical contracts and registry conventions, existing governance and Artifact Protocol, `GOV-BOUNDARY-001`, `ADR-GOVERNANCE-012`, and `ADR-GOVERNANCE-013`.

No roadmap statement may override ratified architecture or existing governed contract.

1. canonical instrument identity;
2. canonical candle semantics;
3. canonical trade semantics;
4. canonical order-book semantics;
5. canonical derivatives-data semantics where already required;
6. venue identity semantics;
7. symbol identity semantics;
8. market type semantics;
9. contract type semantics;
10. timeframe semantics;
11. timestamp semantics;
12. required/optional field semantics;
13. null semantics;
14. authoritative Decimal representation;
15. precision and scale semantics;
16. deterministic identity requirements;
17. validation-result taxonomy;
18. provenance requirements;
19. lineage requirements;
20. explicit data-quality semantics required by the Phase 3 boundary.

The implementation must preserve: `Canonical contracts contain only validated semantic data.` Provider-specific aliases, wire identifiers, sequence details and transport-specific fields remain outside canonical semantics unless an explicit authoritative domain requirement establishes semantic promotion.

## 5. Existing Contract and Architecture Preservation

The Producer must preserve frozen architecture, existing contracts and Stable IDs. `DOC-V2-ARCH-001` must remain unchanged. Existing Phase 2 acquisition contracts must remain unchanged unless an exact compatibility issue is demonstrated and escalated. `CTR-P2-001` must remain provider-neutral. Phase 2 acquisition ownership remains separate from Phase 3 validation/normalization ownership.

If implementation requires modification of a frozen contract, architecture, Stable ID, schema or governance boundary: **STOP THAT PART** and report the exact conflict to CONTROL. Do not invent a workaround or silently broaden scope.

## 6. Required Implementation Boundary

The Producer may modify only implementation, tests, contracts and directly necessary repository artifacts required for this Step.

The Producer must not implement `STEP-P3-002` or later; implement Phase 4; implement quantitative indicators, market structure, specialist intelligence, AI interpretation, Opportunity Score, trade-idea generation, trading/order execution, capital/custody/leverage/transfer behavior; modify V1; redesign frozen architecture; create speculative Stable IDs; fabricate missing market data; silently repair invalid data; introduce provider-specific semantics into canonical contracts without authoritative justification; or perform unrelated cleanup/refactoring.

## 7. Deterministic Data Rules

Use the approved authoritative numeric representation; preserve explicit missing/null semantics; prevent NaN/Inf from authoritative outputs; avoid silent divide-by-zero or equivalent invalid mathematical behavior; remain deterministic where required; and keep pure mathematical/contract logic free from network, wall-clock, mutable-global-state or unrelated I/O dependencies unless explicitly authorized by existing architecture.

No fabricated fallback market values are permitted.
