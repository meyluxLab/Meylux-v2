## 2. Objective

Establish the authoritative specialist foundation required for later P5 Steps: contracts/evidence model, deterministic configuration, append-only specialist persistence semantics, and the test/evidence foundation.

## 3. Required Scope

1. Define/implement the P5 specialist contract and evidence model required by the Roadmap and frozen architecture.
2. Preserve Stage-1 independence: specialist components may consume the authoritative Input Snapshot only; no specialist may consume another specialist's output.
3. Implement versioned configuration with complete provenance and allowed-range semantics; configuration cannot disable architectural invariants.
4. Implement append-only persistence semantics for specialist outputs and the required identity/version/evidence references.
5. Preserve explicit statuses such as `SUCCESS`, `PARTIAL`, `INSUFFICIENT_DATA`, `UNAVAILABLE_INPUT`, `SKIPPED`, `DISABLED`, `FAILED`, and `TIMEOUT` where applicable.
6. Enforce no NaN/Inf leakage and no fabricated fallback values.
7. Add focused unit/contract/integration tests for malformed, missing, boundary, duplicate/replay and contradictory inputs relevant to this foundation.
8. Produce documentation and traceability sufficient for independent audit.

## 4. Explicit Dependency / Futures Boundary

The Owner has authorized Spot + Futures as product scope. This Task Order does not authorize implementation of a Futures acquisition adapter.

CONTROL has independently observed from the repository that:
- the provider-neutral `ProviderAdapter` contract is capability-oriented;
- `CanonicalInstrument` already contains `market_type`, `contract_type`, and `contract_multiplier`;
- the current Binance adapter exposes public Spot REST/WebSocket capabilities;
- the current MEXC adapter is explicitly a public Spot adapter.

Accordingly, if an actual P5 Step requires Futures data and the current upstream capability is insufficient, CONTROL shall route the concrete gap through the existing P2 ownership boundary as a bounded additive change if it preserves the frozen architecture and applicable change-control rules. No Futures implementation is to be added inside this Task Order.
