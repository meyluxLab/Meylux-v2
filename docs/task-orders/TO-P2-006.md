# TO-P2-006 — End-to-End Acquisition Verification & Phase 2 Closure

**Task Order SID:** `TO-P2-006`
**Phase:** `PH-P2`
**Step:** `STEP-P2-006`
**Issuer:** `ROL-V2-001` CONTROL / REVIEWER
**Recipient:** `ROL-V2-002` PRODUCER / ARCHITECT-BUILDER
**Status:** AUTHORIZED TO EXECUTE

## Authority

This Task Order is issued under the Project Owner's standing General Continuation / Phase Progression Authority following verified completion of `TO-P2-005 / STEP-P2-005` under `AR-P2-AUDIT-005`.

It is bounded by the Constitution / Architectural Invariants, `DOC-V2-ARCH-001` RATIFIED / FROZEN, the Master Registry, `PH-P2`, `STEP-P2-006`, and `GOV-BOUNDARY-001`.

This Task Order authorizes only end-to-end verification of the existing Phase 2 acquisition boundary and the evidence preparation required for Phase 2 closure. It does not authorize architecture redesign, new provider functionality, Phase 3/4 implementation, AI functionality, or trading/account/capital activity.

## Objective

Prove the Phase 2 acquisition boundary end-to-end using authorized repository and runtime evidence, then prepare the evidence required for separate CONTROL Phase 2 closure verification.

## Authoritative Scope

1. Exercise the existing Binance and MEXC acquisition paths through the governed acquisition boundary.
2. Verify provider isolation and degraded-provider behavior in the integrated acquisition path.
3. Verify acquisition sequencing, replay/idempotency, raw/staging persistence, and bounded recovery behavior using actual evidence.
4. Verify the existing queue/transport and persistence boundaries without redesigning them.
5. Perform bounded authorized VPS/runtime validation where the authorized V2 Development Workspace is available.
6. Capture exact commands, timestamps, outputs, and runtime evidence for all performed validation actions.
7. Verify that no uncontrolled long-running validation process remains after testing.
8. Produce the required `BR-P2-006` / completion evidence and report deviations, Open Questions, Known Design Considerations, and evidence gaps explicitly.
9. Remain strictly within the existing Phase 2 architecture and verified P2-001 through P2-005 contracts/behavior.

## Contracts / Architecture

Preserve without silent modification:
- `CMP-P2-001` — Provider-Neutral Acquisition Boundary;
- `CTR-P2-001` — `AcquisitionEnvelope` Provider-Neutral Acquisition Contract;
- verified Binance and MEXC acquisition adapters;
- existing collector, queue, transport, and PostgreSQL/TimescaleDB persistence architecture;
- existing Redis/ARQ conventions;
- `DOC-V2-ARCH-001` and Phase 2 ownership boundaries.

No Phase 3 validation/normalization implementation or Phase 4 quantitative/market-structure computation may be introduced.

If an end-to-end requirement cannot be satisfied without changing a ratified/frozen contract, architecture, Stable ID, or higher-level governance rule, stop that part and report an Open Question / escalation. Do not invent a workaround that changes the governed boundary.

## Development / VPS Boundary

`GOV-BOUNDARY-001` applies.

The Producer may use the authorized V2 Development Workspace, including the VPS-hosted Development Workspace, for bounded verification actions explicitly within this Task Order.

Runtime validation must be bounded, observable, and evidence-producing. No production deployment, V1 activity, financial/trading operation, or unrelated infrastructure change is authorized.

Provider credentials or secret material must not be exposed in repository artifacts, chat, logs, or reports.

## Required Evidence

The Producer must report actual evidence for:
- Binance acquisition-path execution;
- MEXC acquisition-path execution;
- provider isolation/degraded behavior;
- sequencing and replay/idempotency behavior;
- raw/staging persistence behavior;
- queue/transport behavior and bounded recovery;
- exact runtime commands and actual outputs where VPS validation is performed;
- timestamps and relevant execution identifiers;
- cleanup/termination of bounded runtime validation;
- any unavailable, insufficient, stale, or unverified evidence;
- deviations, Open Questions, Known Design Considerations, and out-of-scope items.

No execution, runtime, benchmark, test, or verification result may be claimed without actual evidence.

## Required Verification Activities

At minimum, applicable verification must cover:
1. Binance end-to-end acquisition through the existing collector boundary;
2. MEXC end-to-end acquisition through the existing collector boundary;
3. independent provider failure isolation;
4. canonical degraded/rate-limit/disconnected handling;
5. sequence/reconnect and replay/idempotency behavior;
6. raw/staging persistence and read-back evidence;
7. bounded queue/backpressure and recovery behavior;
8. existing observability evidence for acquisition states;
9. repository regression and relevant foundation validation;
10. bounded VPS/runtime verification where the authorized environment is available.

## Explicit Non-Scope

Not authorized:
- Phase 3 implementation;
- Phase 4 implementation;
- AI/specialist intelligence;
- changes to frozen architecture or provider contracts;
- production deployment;
- V1 mutation/runtime activity;
- trading, orders, leverage, balances, transfers, withdrawals, custody, account control, or capital operations;
- unrelated infrastructure work;
- redesign of queue/persistence architecture;
- implementation of future-phase functionality.

## Definition of Done — Producer Side

Producer completion requires:
- all applicable end-to-end verification activities executed with actual evidence;
- both first-class providers exercised where the authorized environment permits;
- replay/idempotency and persistence evidence captured;
- provider isolation/degradation evidence captured;
- bounded runtime validation cleaned up;
- repository regression evidence recorded;
- no unauthorized scope expansion;
- `BR-P2-006` produced with the Producer's actual execution state and explicit evidence boundaries.

Producer must not claim Phase 2 closure or independently transition Phase 2 to `VERIFIED / COMPLETE`.

## CONTROL Closure Boundary

After Producer completion, CONTROL will independently audit the complete Phase 2 evidence set and determine whether `STEP-P2-006` and `PH-P2` satisfy their governed closure criteria.

This Task Order authorizes verification work; it does not itself constitute Phase 2 closure.
