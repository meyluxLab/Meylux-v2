# MEYLUX V2 — TASK ORDER

## TO-P0-009 — Verification / Evidence / Gates

**Task Order ID:** `TO-P0-009`
**Phase:** `PH-P0`
**Step:** `STEP-P0-008` — Verification / Evidence / Gates
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** `AUTHORIZED TO EXECUTE`
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-003`
**Predecessor:** `STEP-P0-007` — Environment Contract (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-008 — Verification / Evidence / Gates`: formalize and reconcile the governed V2 verification, evidence provenance, gate semantics, and completion-evidence requirements without authorizing runtime implementation or changing the ratified Phase 0 sequence.

## 2. Authoritative Boundary

`ADR-ARCHITECTURE-001` establishes `STEP-P0-008` as the eighth Phase 0 Step. It is now the sole activated Step. Later Steps remain defined but are not authorized.

The work shall establish verification/evidence/gate semantics required for V2 governance while preserving the distinction between design, implementation, execution, verification, acceptance, ratification, and freeze.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the current authoritative verification/evidence/gate artifacts, Constitution, Artifact Protocol, AI Continuation Protocol, environment contract, architecture baseline, checkpoint/state, registries, ratified ADRs, Open Questions, Deferred Decisions, and relevant V1 isolation constraints.
2. Determine the required V2 verification and evidence model, including:
   - evidence provenance and traceability;
   - verification independence;
   - lifecycle/state distinctions;
   - gate semantics and authority boundaries;
   - completion and acceptance evidence requirements;
   - distinction between analytical/data evidence and governance evidence where applicable.
3. Identify material verification/evidence/gate gaps, contradictions, stale records, ambiguous authority, missing provenance, or traceability weaknesses.
4. Reconcile only the records required by the Step objective and supported by authoritative evidence.
5. Preserve the repository as Source of Truth and preserve all lifecycle/evidence distinctions.
6. Ensure verification/evidence/gate definitions do not silently authorize runtime implementation, deployment, V1/VPS mutation, market/trading/capital activity, or provider-runtime activity.
7. Preserve existing Stable IDs and historical records. Do not invent identities where authority is absent.
8. Use the delegated Build Report allocation procedure under `ADR-GOVERNANCE-003` when a Build Report is required.
9. Produce a Build Report containing actual evidence and explicitly distinguishing Producer production from independent CONTROL verification.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- ratify or freeze the Master Architecture;
- alter the ratified Phase 0 sequence;
- activate future Steps or issue future Task Orders;
- convert policy/design requirements into claims of executed or verified behavior without evidence;
- modify V1, V1 VPS/runtime, market providers, trading, capital, fund-transfer, or provider-runtime state;
- create competing verification, evidence, gate, governance, checkpoint, registry, or approval subsystems;
- alter or reinterpret existing Stable IDs;
- silently rewrite or invalidate historical evidence;
- self-approve, self-audit, self-verify, close the Step, or ratify governance decisions;
- fabricate execution, verification, acceptance, deployment, runtime, market, provider, or repository state;
- make unrelated architecture, governance, registry, implementation, or runtime changes.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-007` remains `COMPLETE / VERIFIED` with `AR-P0-AUDIT-011` as its completion audit;
- the V2 verification/evidence/gate model is explicitly defined or reconciled within the authorized Step objective;
- evidence provenance and lifecycle distinctions are explicit;
- independent verification authority and authority separation are preserved;
- gate semantics are distinguishable from implementation/execution claims;
- completion/acceptance/ratification/freeze evidence boundaries are explicit;
- existing Stable IDs and ratified governance/constitutional boundaries remain preserved;
- any unresolved verification/evidence/gate conflict is explicitly recorded rather than silently resolved;
- no later Step is activated;
- no unauthorized runtime, V1/VPS, market, trading, capital, or provider-runtime activity occurred;
- the Build Report remains unverified until independent CONTROL audit.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the resulting Build Report and repository changes before any Step completion transition. If accepted, the next Step may be activated only through the existing sequential governance process.
