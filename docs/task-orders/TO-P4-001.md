## 2. Governing Intent — Maximum Quality and Success-Rate Standard

Apply ADR-GOVERNANCE-013 Rule 5 as the governing intent of this engagement, not as a checklist line:

Every part of the authorized implementation, validation, test coverage, edge-case handling, documentation and evidence must be developed to the maximum achievable standard of correctness, robustness, reproducibility and efficiency, aimed at the highest realistically attainable success rate for the finished product. Minimum-to-pass quality is insufficient.

The standard applies to every implementation detail. It does not expand scope, override higher-authority architecture/governance, or bypass Rule 1 stop conditions.

## 3. Objective

Establish the deterministic quantitative foundation required for all later Phase 4 engines without implementing those later engines early.

The foundation must make authoritative numeric behavior explicit, reproducible and change-controlled before downstream indicators or market-structure logic depend on it.

## 4. Required Scope

### 4.1 Quantitative Contracts

Establish and/or extend only the authoritative contracts required for:
- Indicator;
- Market Structure;
- Volume Profile;
- Order Flow;
- Regime.

Contracts must define semantics, not merely types, for supported fields including as applicable:
`value`, `status`, `reason`, `source_ref`, `timestamp`, `timeframe`, `symbol`, `venue/context`, `version`.

Do not invent fields where an authoritative existing contract does not support them. Reconcile all changes against the frozen architecture and existing contract vocabulary.

### 4.2 Numeric Policy

Define and document the governing numeric policy, including as applicable:
- internal numeric representation;
- boundary representation;
- precision;
- rounding mode;
- quantization;
- permitted comparison tolerance;
- deterministic serialization.

The roadmap's Hybrid internals + Decimal boundary proposal is a planning input, not authority. Select and justify implementation details only after inspecting authoritative architecture/contracts and preserving their hierarchy.

### 4.3 Mathematical Primitives

Establish reusable deterministic primitives required by later Phase 4 work, including as applicable:
- rolling calculations;
- averages;
- weighted calculations;
- smoothing;
- standard deviation;
- percentile/ranking;
- accumulation;
- normalization.

Avoid duplicated, semantically divergent implementations of common arithmetic.

### 4.4 Insufficient History / Missing Inputs

Create one governed foundation-level behavior for insufficient history and missing/invalid inputs.

Required principle:

`NOT ENOUGH HISTORY → explicit status + reason + no numeric fabrication`

No NaN, Inf, arbitrary zero, stale substitution, fabricated fallback or silent repair is permitted.

### 4.5 Golden Vector Infrastructure and Freeze Boundary

Establish an extensible system of:

`Input fixture → Function → Expected output → Exact comparison → Regression protection`

The initial vectors must exercise representative nominal, boundary, precision/rounding and insufficient-input behavior for the primitives actually implemented in this Step.

Define the change-control boundary so changing an authoritative mathematical reference requires governed review rather than merely editing expected values to make tests pass.

### 4.6 Persistence Model Foundation

Establish the minimum coherent model foundation for the roadmap-identified quantitative outputs, subject to actual architecture/schema inspection:

- `DB-P4-001` — `calculated_indicator_vectors`;
- `DB-P4-002` — `market_structure_events`;
- `DB-P4-003` — `market_structure_zones`;
- `DB-P4-004` — `volume_profile_sessions`;
- `DB-P4-005` — `market_regime_states`.

This is model foundation only. Do not implement full orchestration/runtime processing for these outputs in P4-001.

## 5. Engineering Requirements

The Producer must inspect the actual repository before implementation and must cover, within the authorized boundary:

1. deterministic arithmetic and serialization;
2. explicit precision/rounding behavior;
3. decimal/float boundary behavior where applicable;
4. negative, zero, very small and very large values within supported domains;
5. empty, singleton, short and exactly-at-warmup inputs;
6. missing and malformed values;
7. invalid/non-finite input rejection;
8. insufficient-history semantics;
9. stable ordering and deterministic tie-breaking where relevant;
10. no lookahead or hidden clock dependency;
11. idempotent/reproducible golden-vector execution;
12. exact expected-value comparison semantics;
13. regression protection against accidental numeric drift;
14. contract/schema compatibility with existing P3 canonical data;
15. provenance/timeframe/symbol/venue context preservation where contractually required;
16. migration/schema ordering and idempotency if database artifacts are changed;
17. least-privilege database boundaries if persistence objects are introduced;
18. explicit failure behavior and useful evidence;
19. test isolation and maintainability;
20. documentation of implementation-level choices and their authoritative basis.

A passing happy-path test is not sufficient evidence.

## 6. Required Test/Evidence Coverage
