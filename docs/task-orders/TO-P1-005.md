# MEYLUX V2 — TASK ORDER

## TO-P1-005 — Data Quality Foundation

**Task Order ID:** `TO-P1-005`
**Phase:** `PH-P1`
**Step:** `STEP-P1-005`
**Governance Class:** Phase Implementation
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** `AUTHORIZED TO EXECUTE`
**Predecessor:** `STEP-P1-004` — COMPLETE / VERIFIED
**Authorization Basis:** `PH-P1` / General Continuation and Phase Progression Authority / `AR-P1-AUDIT-004`
**Architectural Basis:** `DOC-V2-ARCH-001` — RATIFIED / FROZEN

## 1. Objective

Establish the foundational Meylux V2 data-quality representation and handling required before later market-data acquisition and normalization phases.

This Task Order activates only `STEP-P1-005`. It does not activate or authorize `STEP-P1-006` or any later step.

## 2. Required Scope

Implement and test the P1 Data Quality Foundation defined by `PH-P1`, including:

1. Explicit representation of data-quality state and validity/degradation information required by the existing V2 architecture.
2. Deterministic validation/rejection boundaries for data that is invalid, insufficient, stale, unavailable, contradictory, or otherwise outside the authoritative quality boundary where such states are defined by the repository architecture.
3. Explicit degradation representation so missing or insufficient evidence remains visible and is never silently converted into fabricated authoritative market values.
4. Clear separation between data quality and downstream analytical confidence/opportunity interpretation where those concepts already exist in the governed architecture.
5. Compatibility with the verified P1 Repository, Docker, Database, and Data Contract foundations, including the canonical contract boundary established by `TO-P1-004`.
6. Deterministic tests covering the defined quality-state and validation behavior.
7. Required governed registry/state updates for newly created material artifacts, using existing Stable-ID governance; do not invent competing IDs.
8. A factual Build Report containing actual changes, tests, results, deviations, Open Questions, and final Producer state.

## 3. Architectural / Governance Requirements

The implementation MUST preserve:

- `INV-V2-001` STRICT READ-ONLY.
- `INV-V2-002` DETERMINISTIC BASELINE.
- `INV-V2-003` NO FABRICATION.
- `INV-V2-004` EVIDENCE PROVENANCE.
- `INV-V2-006` LOGICAL IDENTITY.
- `INV-V2-007` SINGLE AUTHORITATIVE PERSISTENCE.
- `INV-V2-008` PROVIDER ISOLATION.
- `INV-V2-010` EVIDENCE-BACKED STATE.

The implementation must not introduce provider-runtime activity, live market acquisition, trading, capital control, V1 access/mutation, specialist/AI intelligence, or any later P1/future-phase functionality.

Do not silently modify frozen architecture, existing verified contracts, Stable IDs, approved repository structure, or existing interfaces. If a genuine architecture/governance/authority conflict is discovered, STOP THAT PART and report the conflict.

## 4. Implementation Boundary

Implementation choices are bounded by the existing architecture and repository conventions. Do not introduce unrelated frameworks, speculative abstractions, future-phase features, or performance tuning outside this step.

No external market data is required for this step. Do not fabricate market observations, provider values, or fallback values as authoritative evidence.

## 5. Required Outputs

At minimum, provide:

- data-quality contract/state artifacts justified by the existing architecture;
- required validation/rejection/degradation logic;
- deterministic tests for the defined behavior;
- governed registry/state updates for newly created material artifacts where required;
- `BR-P1-005` containing actual implementation and test evidence.

## 6. Verification Requirements

Producer self-test evidence MUST distinguish:

`IMPLEMENTED` ≠ `TESTED` ≠ `VERIFIED`.

The Build Report must contain actual:

- changed paths;
- Stable IDs where applicable;
- commands/tests executed;
- exit codes/results;
- observed test counts only when actually observed;
- deviations and Open Questions;
- final implementation state.

CONTROL will independently audit the repository and Build Report before the step can become `COMPLETE / VERIFIED`.

## 7. Acceptance Criteria

The step is acceptable for independent CONTROL audit when evidence demonstrates:

1. required data-quality states/representation exist for the authorized P1 boundary;
2. validity and degradation semantics are explicit and deterministic;
3. invalid/insufficient/stale/unavailable/contradictory evidence is not silently converted into authoritative fabricated values;
4. data quality remains distinct from analytical confidence/opportunity interpretation where applicable;
5. provenance and canonical-contract boundaries remain intact;
6. deterministic tests exercise the required quality-state and rejection/degradation behavior;
7. existing P1 foundations remain compatible;
8. no prohibited activity or future-step scope was introduced;
9. Build Report is complete and based only on actual evidence.

## 8. Explicit Non-Authorization

This Task Order does NOT authorize:

- live market-data acquisition;
- provider runtime integration;
- Binance/MEXC runtime implementation;
- specialist/AI intelligence;
- trading or order execution;
- capital movement, custody, withdrawal, deposit, or leverage control;
- V1/V1 VPS mutation;
- activation of `STEP-P1-006` or any later step;
- architecture/governance override;
- silent repair of defects outside the Producer implementation boundary.

## 9. Completion Boundary

On successful implementation and self-test, Producer returns `BR-P1-005` to CONTROL. The step remains `IMPLEMENTED / TESTED` until independent CONTROL audit establishes `VERIFIED`.

Only after that verification may normal Phase 1 progression activate the next defined step.
