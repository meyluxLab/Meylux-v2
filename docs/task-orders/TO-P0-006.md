# MEYLUX V2 — TASK ORDER

## TO-P0-006 — Governance / Artifact Protocol

**Task Order ID:** `TO-P0-006`
**Phase:** `PH-P0`
**Step:** `STEP-P0-005` — Governance / Artifact Protocol
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** AUTHORIZED TO EXECUTE
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-003`
**Predecessor:** `STEP-P0-004` — Stable Identity / Registry (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-005 — Governance / Artifact Protocol`: establish and reconcile the governed artifact lifecycle, authority boundaries, and evidence protocol required for V2 operation, using the existing ratified governance baseline and preserving all already-ratified decisions and historical evidence.

## 2. Authoritative Boundary

`ADR-ARCHITECTURE-001` establishes `STEP-P0-005` as the fifth Phase 0 Step. It is now the sole activated Step. Later Steps remain defined but are not authorized.

The existing `docs/governance/ARTIFACT_PROTOCOL_V2.md` is already a ratified operational protocol. This Step is therefore a reconciliation/completeness task, not permission to redesign governance or silently replace ratified mechanisms.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the current ratified governance decisions, Artifact Protocol, role contracts/definitions, Phase 0 governance boundary, artifact registry, and relevant architecture/constitutional requirements.
2. Identify material governance or artifact-protocol gaps, contradictions, ambiguity, missing authority boundaries, lifecycle-state inconsistencies, traceability gaps, or evidence-provenance weaknesses relevant to the current V2 baseline.
3. Reconcile only those governance/artifact-protocol records required by the Step objective and supported by authoritative evidence.
4. Preserve all existing ratified governance decisions, Stable IDs, historical artifact records, and verified evidence unless an explicitly authorized correction is required.
5. Ensure the official artifact chain and lifecycle states remain explicit and distinguish at minimum design, production, execution, verification, acceptance, ratification, and freeze states where applicable.
6. Preserve independent verification: Producer production must remain distinct from CONTROL audit/verification and from Project Owner ratification authority.
7. Verify that authority boundaries among Project Owner, CONTROL / REVIEWER, Producer / Architect-Builder, Producer Relay, Market Intelligence, Phase Chat, Troubleshooting, and Operator remain explicit and non-conflicting.
8. Reconcile the delegated Producer Build Report allocation procedure only if a material protocol inconsistency is evidenced; do not expand the delegation beyond `ADR-GOVERNANCE-003`.
9. Identify unresolved governance conflicts that require higher-level governance or Project Owner disposition; do not silently resolve genuine conflicts.
10. Use the delegated Build Report allocation procedure in `ADR-GOVERNANCE-003` when a Build Report is required. Allocate only the next BR for this currently authorized Task Order.
11. Produce a Build Report containing actual evidence and preserving the distinction between Producer production and CONTROL verification.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- ratify or freeze the Master Architecture;
- alter the ratified Phase 0 sequence;
- activate future Steps or issue future Task Orders;
- alter or reinterpret existing Stable IDs or historical artifact identities;
- create a competing governance subsystem, Artifact Protocol, Registry, or approval mechanism;
- change Project Owner final authority or CONTROL independent verification authority;
- self-approve, self-audit, self-verify, close the Step, or ratify governance decisions on behalf of the Project Owner;
- modify V1, V1 VPS/runtime, market providers, trading, capital, fund-transfer, or provider-runtime state;
- fabricate governance, lifecycle, artifact, execution, or verification evidence;
- make unrelated registry, architecture, implementation, environment, or runtime changes.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-004` remains `COMPLETE / VERIFIED` with `AR-P0-AUDIT-008` as its completion audit;
- governance/artifact-protocol work is limited to the authorized Step objective;
- existing ratified governance decisions and historical identities remain preserved;
- artifact authority, lifecycle states, provenance, and verification boundaries are explicit and internally consistent;
- Project Owner ratification authority and CONTROL independent audit authority remain distinct;
- unresolved conflicts remain explicitly recorded rather than silently resolved;
- no later Step is activated;
- no unauthorized runtime, V1/VPS, market, trading, capital, or provider-runtime activity occurred;
- Build Report evidence is actual and remains unverified until independent CONTROL audit.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the resulting Build Report and repository changes before any Step completion transition. If accepted, the next Step may be activated only through the existing sequential governance process.
