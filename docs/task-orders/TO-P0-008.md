# MEYLUX V2 — TASK ORDER

## TO-P0-008 — Environment Contract

**Task Order ID:** `TO-P0-008`
**Phase:** `PH-P0`
**Step:** `STEP-P0-007` — Environment Contract
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** AUTHORIZED TO EXECUTE
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-003`
**Predecessor:** `STEP-P0-006` — AI Continuation Protocol (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-007 — Environment Contract`: define and reconcile the governed V2 environment contract and its boundaries, while preserving the strict separation between environment definition and runtime deployment/execution authorization.

## 2. Authoritative Boundary

`ADR-ARCHITECTURE-001` establishes `STEP-P0-007` as the seventh Phase 0 Step. It is now the sole activated Step. Later Steps remain defined but are not authorized.

The work shall establish the environment contract required for V2 governance and continuity without silently authorizing runtime deployment, V1/VPS mutation, provider-runtime activity, market-data activity, trading, capital movement, or implementation outside this Step.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the current authoritative environment-related repository artifacts, architecture baseline, Constitution, governance/artifact protocol, continuation protocol, checkpoint/state, registry, ratified ADRs, Open Questions, Deferred Decisions, and relevant V1 isolation constraints.
2. Determine the required V2 environment contract and explicitly distinguish:
   - logical environment requirements;
   - development/build/test environment boundaries;
   - runtime/deployment boundaries;
   - persistence and authoritative-state boundaries;
   - provider/runtime isolation boundaries;
   - V1/VPS isolation boundaries;
   - Operator prerequisites where physical/environment execution would later be required.
3. Identify material environment-contract gaps, contradictions, stale records, ambiguous authority, missing boundaries, or traceability weaknesses that affect reliable V2 operation.
4. Reconcile only the environment-contract records required by the Step objective and supported by authoritative evidence.
5. Preserve the repository as Source of Truth and preserve all lifecycle/evidence distinctions.
6. Ensure environment definition does not silently authorize runtime implementation, deployment, V1/VPS mutation, market/trading/capital activity, or provider-runtime activity.
7. Preserve existing Stable IDs and historical records. Do not invent identities where authority is absent.
8. Use the delegated Build Report allocation procedure under `ADR-GOVERNANCE-003` when a Build Report is required.
9. Produce a Build Report containing actual evidence and explicitly distinguishing Producer production from independent CONTROL verification.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- ratify or freeze the Master Architecture;
- alter the ratified Phase 0 sequence;
- activate future Steps or issue future Task Orders;
- treat an environment contract as runtime/deployment authorization;
- modify V1, V1 VPS/runtime, market providers, trading, capital, fund-transfer, or provider-runtime state;
- create competing environment, deployment, persistence, provider, governance, checkpoint, registry, or approval subsystems;
- alter or reinterpret existing Stable IDs;
- silently rewrite or invalidate historical evidence;
- self-approve, self-audit, self-verify, close the Step, or ratify governance decisions;
- fabricate environment, execution, verification, deployment, runtime, market, provider, or repository state;
- make unrelated architecture, governance, registry, implementation, or runtime changes.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-006` remains `COMPLETE / VERIFIED` with `AR-P0-AUDIT-010` as its completion audit;
- the V2 environment contract is explicitly defined/reconciled within the authorized Step objective;
- environment requirements and boundaries are distinguishable from runtime/deployment authorization;
- persistence, provider, V1/VPS, and Operator boundaries are explicit where applicable;
- authoritative state, evidence, unresolved matters, and historical records remain distinguishable;
- existing Stable IDs and ratified governance/constitutional boundaries remain preserved;
- any unresolved environment conflict is explicitly recorded rather than silently resolved;
- no later Step is activated;
- no unauthorized runtime, V1/VPS, market, trading, capital, or provider-runtime activity occurred;
- the Build Report remains unverified until independent CONTROL audit.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the resulting Build Report and repository changes before any Step completion transition. If accepted, the next Step may be activated only through the existing sequential governance process.
