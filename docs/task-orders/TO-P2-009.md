## 1. Lifecycle Boundary

`PH-P2` remains `CLOSED / VERIFIED` and `STEP-P2-006` remains `COMPLETE / VERIFIED`. This Task Order is a post-closure investigation under the existing Step boundary. It does not reopen Phase 2 or alter the historical closure.

## 2. Objective

Determine whether MEXC exposes an authoritative provider-side candle finality/closed-candle mechanism that can support a governed MEXC finality representation without inference, lookahead, or synthetic facts.

The investigation must answer exactly:

1. Does the authoritative current MEXC Spot interface expose an explicit candle-finality/closed flag?
2. If not, does MEXC document another authoritative mechanism that establishes finality independently of operational receipt/local time?
3. Can the existing repository MEXC adapter preserve that evidence without changing frozen architecture, G-4 identity, canonical bytes, or P5 ownership?
4. Is an implementation Task Order justified, or must the MEXC finality boundary be recorded as unavailable and the investigation closed?

## 3. Mandatory Provider Evidence

Use authoritative current MEXC documentation for the applicable Spot interfaces. Do not infer a finality flag from:

- `windowend` / close time;
- `createtime` / event time;
- receipt time;
- local clock;
- persistence time;
- repeated updates;
- REST row availability.

The current public MEXC Spot documentation exposes K-line start/end and event timing fields but does not, on the inspected documentation baseline, show a WebSocket `closed`/finality flag. This is an investigation hypothesis only; Producer must independently verify it and must not treat the hypothesis as a final disposition.

## 4. Repository Inspection

Inspect at minimum:

- current MEXC acquisition adapter;
- MEXC WebSocket kline parsing;
- MEXC REST historical kline path;
- provider-neutral AcquisitionEnvelope;
- MEXC normalization mapping;
- existing `is_closed`, `close_time`, provenance, replay/idempotency and identity behavior;
- current G-4 identity material;
- existing MEXC tests and CI path.

## 5. Explicit Non-Scope

This Task Order authorizes **investigation only**.

It does not authorize:

- MEXC implementation changes;
- modification of `contracts/normalization.py` for MEXC semantics;
- modification of the MEXC adapter;
- new tests that alter production semantics;
- Binance changes;
- A-P3;
- Routes B/C/D;
- P5-003;
- Futures;
- Forex;
- architecture redesign;
- new truth layer;
- identity/canonical-byte changes;
- migration or historical rewrite;
- VPS mutation or provider activation.

If implementation is required to establish an authoritative mechanism, STOP THAT PART and report the exact conflict. Do not implement it under this investigation.

## 6. Required Deliverable

- authoritative MEXC sources inspected and exact relevant fields;
- Spot WebSocket finality finding;

- distinction among close/window time, event time, receipt time, persistence time and knowledge time;
- repository implementation facts;

- explicit disposition:
  - `MEXC_FINALITY: ESTABLISHED`, with the exact authoritative mechanism and bounded implementation recommendation; or
  - `MEXC_FINALITY: UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`, with evidence and reason;

## 7. Conditional Continuation Rule

If and only if an authoritative MEXC finality mechanism is established by the investigation, CONTROL may issue a separate bounded MEXC implementation Task Order under the Owner's preauthorization, without another Owner round-trip.

If the mechanism is not authoritatively established, the investigation must be closed with:

`MEXC_FINALITY: UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`

and no MEXC implementation Task Order may be issued.

No other scope is activated by either outcome.
