# MEYLUX V2 — TASK ORDER

## TO-P1-006 — Async Worker & Queue Foundation

**Task Order ID:** `TO-P1-006`
**Phase:** `PH-P1`
**Step:** `STEP-P1-006`
**Governance Class:** Phase Implementation
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** `AUTHORIZED TO EXECUTE`
**Predecessor:** `STEP-P1-005` — COMPLETE / VERIFIED
**Authorization Basis:** `PH-P1` / General Continuation and Phase Progression Authority / `AR-P1-AUDIT-005`
**Architectural Basis:** `DOC-V2-ARCH-001` — RATIFIED / FROZEN

## 1. Objective

Establish the bounded asynchronous worker and queue foundation required by Meylux V2 P1, providing a reproducible transport/execution boundary for later workloads without activating market acquisition, provider runtime, specialist/AI intelligence, trading, or any later phase.

This Task Order activates only `STEP-P1-006`. It does not authorize `STEP-P1-007`, `STEP-P1-008`, or any later phase.

## 2. Required Scope

Implement and test the P1 async worker/queue foundation defined by the frozen architecture and Phase P1 specification, including:

1. A reproducible queue/transport foundation compatible with the already verified V2 runtime foundation and existing Redis infrastructure.
2. Clear worker ownership with one primary responsibility per worker and explicit allowed/forbidden dependencies or responsibilities.
3. Explicit queue ownership and semantics for each queue introduced in this step, including owner, producer, consumer, purpose, payload contract, ordering requirement where applicable, retry policy, timeout, concurrency/backlog limits, DLQ policy, idempotency, retention, and drain/recovery method.
4. Bounded concurrency and bounded backlog behavior; queues must not be allowed to grow without an explicit overload response.
5. Explicit timeout, bounded retry/backoff, failure-isolation, and recovery behavior appropriate to this foundation.
6. Deterministic and reproducible tests for worker/queue behavior, including success, failure, retry/timeout boundaries, overload/backpressure behavior, and isolation semantics where applicable.
7. No silent coupling of one worker to another subsystem's responsibility.
8. Required governed registry/state updates for material worker/queue artifacts. Stable IDs are governance-controlled: do not invent competing IDs. If a new governed identity is required and not already allocated, record it as a controlled identity requirement for CONTROL rather than silently inventing one.
9. A factual `BR-P1-006` containing actual changes, tests, results, deviations, Open Questions, and final Producer state.

## 3. Architectural / Governance Requirements

The implementation MUST preserve:

- `INV-V2-001` STRICT READ-ONLY.
- `INV-V2-002` DETERMINISTIC BASELINE.
- `INV-V2-003` NO FABRICATION.
- `INV-V2-004` EVIDENCE PROVENANCE.
- `INV-V2-006` LOGICAL IDENTITY.
- `INV-V2-007` SINGLE AUTHORITATIVE PERSISTENCE.
- `INV-V2-008` PROVIDER ISOLATION.
- `INV-V2-010` EVIDENCE-BACKED STATE.

The implementation must preserve the architecture's worker/queue safety model. Worker records must declare primary responsibility, inputs, outputs, queues, allowed dependencies, forbidden responsibilities, side effects, resource budget, retry policy, timeout, concurrency, and failure isolation. Queue records must declare owner, producer, consumer, purpose, payload contract, ordering, retry policy, timeout, concurrency/backlog limits, DLQ policy, idempotency, retention, and drain/recovery method.

The implementation must not introduce provider-runtime activity, live market acquisition, Binance/MEXC runtime, specialist/AI intelligence, trading/order execution, capital/account/custody actions, V1 access/mutation, or `STEP-P1-007`/`STEP-P1-008` work.

Do not silently modify frozen architecture, verified canonical contracts, Stable IDs, security boundaries, or unrelated interfaces. If a genuine architecture/governance/authority conflict is discovered, STOP THAT PART and report it.

## 4. Implementation Boundary

Use the existing P1 runtime foundation and existing Redis transport direction. Do not introduce an alternative broker or unrelated framework without explicit authorization.

Keep the foundation provider-neutral and deterministic. No external market data is required.

No numeric retry, timeout, concurrency, backlog, retention, or resource parameter may be represented as an architectural invariant merely by implementation choice; such values are implementation/configuration parameters and must be explicit, bounded, reproducible, and tested.

Queue overload behavior must be safe and observable at the foundation boundary. Do not silently discard work unless the defined policy explicitly permits it and the event is represented as evidence.

## 5. Required Outputs

At minimum, provide:

- worker/queue foundation implementation within the existing repository structure;
- explicit worker/queue ownership and safety semantics;
- bounded retry/timeout/concurrency/backlog behavior;
- failure isolation and recovery behavior;
- deterministic tests and observed results;
- governed registry/state updates for newly created material artifacts where required;
- `BR-P1-006` containing actual implementation and test evidence.

## 6. Verification Requirements

Producer self-test evidence MUST distinguish:

`IMPLEMENTED` ≠ `TESTED` ≠ `VERIFIED`.

The Build Report must contain actual:

- changed paths;
- Stable IDs where applicable;
- commands/tests executed;
- exit codes/results;
- observed test counts only when actually observed;
- deviations and Open Questions;
- final implementation state.

CONTROL will independently audit the repository, implementation, Build Report, and relevant runtime evidence before the step can become `COMPLETE / VERIFIED`.

## 7. Acceptance Criteria

The step is acceptable for independent CONTROL audit when evidence demonstrates:

1. reproducible async transport/worker foundation exists within the authorized P1 boundary;
2. every introduced worker has one primary responsibility and explicit safety/ownership semantics;
3. every introduced queue has explicit ownership, payload, ordering, retry, timeout, concurrency/backlog, DLQ, idempotency, retention, and drain/recovery semantics;
4. retry and timeout behavior is bounded and deterministic;
5. concurrency/backlog limits and overload/backpressure behavior are explicit and safe;
6. failure isolation prevents one worker/queue failure from silently becoming unrestricted cross-domain failure;
7. no authoritative persistence role is delegated to Redis or queue infrastructure;
8. deterministic tests exercise success and material failure/boundary behavior;
9. existing P1 foundations remain compatible;
10. no prohibited activity or future-step scope was introduced;
11. Build Report is complete and based only on actual evidence.

## 8. Explicit Non-Authorization

This Task Order does NOT authorize:

- live market-data acquisition;
- provider runtime integration;
- Binance/MEXC runtime implementation;
- specialist/AI intelligence;
- trading or order execution;
- capital movement, custody, withdrawal, deposit, or leverage control;
- V1/V1 VPS mutation;
- activation of `STEP-P1-007`, `STEP-P1-008`, or any later step;
- architecture/governance override;
- silent repair of defects outside the Producer implementation boundary.

## 9. Completion Boundary

On successful implementation and self-test, Producer returns `BR-P1-006` to CONTROL. The step remains `IMPLEMENTED / TESTED` until independent CONTROL audit establishes `VERIFIED`.

Only after that verification may normal Phase 1 progression activate the next defined step.
