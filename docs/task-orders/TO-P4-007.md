## 3. In-scope capability boundary

Producer shall implement and evidence, as applicable to the actual repository contracts and architecture:

### 3.1 Quantitative orchestration facade
- a deterministic orchestration boundary connecting the verified P4 engines;
- explicit input/context/configuration and output/error semantics;
- preservation of engine contracts and authoritative mathematical semantics;
- deterministic ordering and provenance/version propagation;
- no silent reinterpretation or duplicate mathematical truth.

### 3.2 Candle-close execution
- execution only from governed canonical closed-candle observations where required;
- explicit rejection/deferral of incomplete or temporally invalid observations;
- deterministic event ordering;
- no wall-clock dependency in authoritative calculation semantics.

### 3.3 Multi-timeframe processing
- governed support for the existing P4 engine capability range where the implementation/contracts support it;
- controlled acceptance slice: BTCUSDT — 15M primary + 1H + 4H, using actually available governed data;
- explicit temporal alignment between primary and higher timeframes;
- no future HTF information becoming visible before its actual knowledge/close boundary;
- distinguish engine capability from demonstrated runtime coverage.

### 3.4 Authoritative persistence
Use the already established PostgreSQL/TimescaleDB quantitative persistence boundary and existing DB foundations. Preserve, as applicable:
- identity;
- provenance/source linkage;
- timestamp;
- symbol;
- timeframe;
- venue/context;
- calculation configuration/version;
- deterministic ordering;
- append-only quantitative truth semantics;
- idempotency and duplicate protection;
- restart/recovery consistency.

Do not weaken existing database privileges or invent a competing authoritative store.

### 3.5 Worker / event-driven boundary
Integrate with the repository's existing governed worker and event infrastructure, including the established Redis queue/stream boundary where applicable.

The quantitative worker must consume the governed candle-close event path and produce only authorized quantitative outputs.

Retry, timeout, duplicate delivery, ACK/recovery and failure behavior must be explicit and tested where those mechanisms are exercised.

### 3.6 Read-only quantitative API
Expose only authorized quantitative read paths required by the Step, using the repository's existing API architecture.

At minimum, where supported by the authoritative contracts:
- quantitative feature output access;
- quantitative market-structure output access;
- regime/other verified quantitative output access where an established contract and persistence boundary exists.

API behavior must be:
- read-only;
- DB-backed where authoritative persistence is required;
- provenance-aware;
- deterministic in serialization/order where applicable;
- free of trading, order, portfolio, capital, custody or mutation authority.

Do not invent a broad public API surface merely for convenience.

### 3.7 Replay
Establish a deterministic replay harness/path over governed historical inputs.

Replay evidence must address:
- repeated-run equality;
- equivalent input/configuration equality;
- duplicate/replay safety;
- persistence consistency;
- ordering;
- restart/recovery interaction where applicable;
- explicit no-lookahead behavior.

Replay must not use future observations to manufacture historical outputs.

### 3.8 Failure, recovery and idempotency
Exercise realistic operational failure classes appropriate to the implemented path, including where applicable:
- duplicate event delivery;
- worker restart;
- queue/stream pending/recovery;
- database/service restart;
- partial execution/retry;
- repeated replay;
- stale/incomplete candle input;
- malformed/contradictory context.

Recovery must preserve authoritative state and must not silently duplicate, delete or overwrite quantitative truth outside governed semantics.

### 3.9 Performance and operational evidence
Measure, do not assume, relevant performance characteristics.

Where roadmap or architecture targets exist, record:
- exact workload/data set;
- methodology;
- environment;
- warm/cold conditions where relevant;
- observed measurements;
- limitations.

Do not convert an unmeasured target into a completion claim.

### 3.10 Security and observability
Preserve existing security boundaries, secret handling, least privilege, read-only API doctrine and structured observability.

No secret may be emitted into tests, API responses, EXEC-LOGs, Build Reports or runtime evidence.

No arbitrary execution path, unauthorized network behavior, V1 access, trading/capital capability or future-phase functionality may be introduced.
