# MEYLUX V2 — TASK ORDER

## TO-P0-005 — Stable Identity / Registry

**Task Order ID:** `TO-P0-005`
**Phase:** `PH-P0`
**Step:** `STEP-P0-004` — Stable Identity / Registry
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** AUTHORIZED TO EXECUTE
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-003`
**Predecessor:** `STEP-P0-003` — V1 Lessons Integration (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-004 — Stable Identity / Registry`: establish and reconcile the stable identity and registry completeness required by the ratified Phase 0 sequence and current V2 design baseline, without redesigning unrelated architecture or governance.

## 2. Authoritative Boundary

`ADR-ARCHITECTURE-001` establishes `STEP-P0-004` as the fourth Phase 0 Step. It is now the sole activated Step. Later Steps remain defined but not authorized.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the current authoritative Stable ID and artifact registry records and their governing identity conventions.
2. Identify material identity/registry gaps, duplicates, ambiguity, missing traceability, or inconsistencies relevant to the current V2 baseline.
3. Reconcile only those registry/identity records required by the Step's objective and supported by authoritative evidence.
4. Preserve all existing stable identities and historical records; do not silently rename, reuse, or reassign an existing identity.
5. Ensure registry records needed for current traceability have appropriate entity type, canonical path/name, lifecycle state, and relevant traceability.
6. Preserve the distinction between architectural identity and physical path/filename/runtime labels.
7. Identify unresolved identity or registry issues that require higher-level governance or architecture disposition; do not silently resolve genuine conflicts.
8. Use the delegated Build Report allocation procedure in `ADR-GOVERNANCE-003` when a Build Report is required. Allocate only the next BR for this currently authorized Task Order.
9. Produce a Build Report containing actual evidence and preserving the distinction between Producer production and CONTROL verification.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- alter or reinterpret ratified Stable IDs;
- renumber or mutate historical artifact identities;
- redesign the Master Architecture;
- ratify or freeze the Master Architecture;
- alter the Phase 0 sequence or activate future Steps;
- issue Task Orders for future Steps;
- alter unrelated governance mechanisms or registries outside the identity/registry scope required by this Step;
- modify V1, V1 VPS/runtime, market providers, trading, capital, fund-transfer, or provider-runtime state;
- fabricate identity, registry, or verification evidence;
- self-approve, self-audit, self-verify, or close this Step.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-003` remains `COMPLETE / VERIFIED`;
- identity/registry work is limited to the authorized Step objective;
- existing Stable IDs and historical records remain preserved;
- relevant registry entries are complete, unique, collision-safe, and traceable;
- unresolved conflicts remain explicitly recorded rather than silently resolved;
- no later Step is activated;
- no unauthorized runtime, V1/VPS, market, trading, capital, or provider-runtime activity occurred;
- Build Report evidence is actual and remains unverified until independent CONTROL audit.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the resulting Build Report and repository changes before any Step completion transition. If accepted, the next Step may be activated only through the existing sequential governance process.
