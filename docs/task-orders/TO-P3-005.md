## 2. Objective

Transform validated provider representations into provider-neutral Meylux canonical semantics while preserving provider isolation and traceability.

Required conceptual flow:

`Binance Provider Representation → Canonical Mapping`
`MEXC Provider Representation → Canonical Mapping`

The canonical result must contain validated semantic meaning, not provider-specific wire-format structure.

## 3. Authorized Scope

Implement the P3-005 normalization/mapping boundary for the provider representations already established by Phase 2 and the canonical contracts established by P3-001 through P3-004.

The mapping boundary covers, where supported by the existing canonical contracts and provider evidence:
- instrument identity;
- candle semantics;
- trade semantics;
- order-book semantics;
- derivatives semantics;
- venue identity;
- market type;
- contract type;
- timeframe;
- timestamp semantics;
- price;
- quantity;
- volume;
- side semantics;
- provenance.

Provider-specific aliases, event identifiers, sequence details, transport fields, and other wire-format details must remain behind the provider boundary unless an explicit authoritative domain requirement makes a field semantic.

Use existing provider adapters/contracts and existing canonical contracts. Do not redefine them.

## 4. Deterministic Normalization Requirements

1. Mapping must be deterministic and reproducible for the same validated input and governed mapping context.
2. No silent guessing or fabrication is permitted.
3. Unknown, ambiguous, unsupported, or unmappable provider semantics must remain explicitly represented and must not be silently promoted to canonical truth.
4. Canonical output must use existing canonical field names, types, enums, Decimal/precision doctrine, and identity semantics.
5. Provider aliases may be translated only where the mapping is explicitly supported by existing evidence/contracts or a governed mapping table created within this Task Order.
6. Normalization must preserve upstream provenance required by the canonical contract.
7. Do not introduce provider-specific fields into the canonical domain merely for implementation convenience.
8. Do not invent exchange-specific numeric thresholds, precision rules, market semantics, or fallback values.
9. Do not duplicate or redefine identity authority already established by `AcquisitionEnvelope` and P3-001.
10. Mapping failures must be explicit and testable; they must not become valid canonical data by fallback behavior.

## 5. Provider Boundary

P3-005 is provider mapping, not acquisition.

Binance and MEXC provider adapters remain responsible for provider wire semantics. P3-005 consumes their validated provider representations and maps them into the provider-neutral canonical domain.

The implementation must not modify the provider acquisition boundary established in Phase 2 except where a concrete integration defect is demonstrated and separately governed.

## 8. Tests and Acceptance Criteria

The implementation is acceptable for CONTROL audit only if evidence demonstrates:

- provider representations from the authorized Binance and MEXC boundaries can be mapped into the applicable canonical semantics;
- canonical output conforms to the existing canonical contracts;
- provider-specific wire fields do not leak into canonical semantics without an authoritative reason;
- identity, venue, market type, contract type, timeframe and timestamp semantics are preserved correctly;
- price, quantity, volume and side semantics are mapped without reinterpretation that contradicts P3-004 validation doctrine;
- provenance remains traceable according to the existing canonical contract;
- ambiguous/unsupported mappings are explicit rather than silently guessed;
- deterministic/reproducible mapping behavior is demonstrated;
- malformed or unmappable provider input cannot silently become authoritative canonical data;
- regression tests for P3-001 through P3-004 remain passing.

Tests must cover both positive and negative mapping cases and provider-specific differences relevant to the implemented mappings.
