## 1. Purpose and lifecycle boundary

`PH-P2` remains `CLOSED / VERIFIED` and `STEP-P2-006` remains `COMPLETE / VERIFIED`. This Task Order is a post-closure corrective action under the existing Phase-2 / Step-2-006 boundary.

This Task Order MUST NOT rewrite, invalidate, or retroactively alter the historical TO-P2-009 investigation, its Build Report, or AR-P2-AUDIT-009. Those records remain the authoritative evidence that MEXC provider-side candle finality was not authoritatively established.

This Task Order exists because TO-P2-009 exposed a material implementation defect:

- provider-side MEXC candle finality is `UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`;
- the current repository MEXC normalization path nevertheless assigns `closed=True`;
- therefore the canonical boundary currently converts absence of provider-finality evidence into an authoritative closed-candle fact.

The required endpoint is **technical correction**, not another investigation report.

## 2. Authoritative starting facts

CONTROL has independently established from the current repository:

1. `CanonicalCandle.is_closed` is a required semantic boolean at the canonical contract boundary. It is not an `Optional[bool]` state.
2. `docs/registry/contracts.yaml` records `is_closed` as `bool` and identifies it as canonical candle contract semantics.
3. Quantitative indicator semantics require `is_closed=True` by default for authoritative calculations; provisional processing is an explicit caller choice and is not a substitute for unknown finality.
4. Quantitative orchestration rejects an aligned candle that is not closed.
5. Market-structure processing requires closed canonical candles.
6. MEXC Spot kline acquisition currently provides candle timing and OHLCV evidence but no authoritative provider-finality signal in the governed MEXC path.
7. `contracts/normalization.py` currently maps the MEXC candle path with `closed=True` without provider evidence.
8. Binance hardening under TO-P2-008 already established the governing anti-coercion principle: unavailable finality is not converted into `closed=True`; historical REST rows without explicit finality are rejected at canonical normalization rather than promoted to provider-final.

These facts establish the correct semantic disposition for the current frozen architecture:

> **MEXC candles may remain acquired and provenance-preserved as raw/staging observations, but they MUST NOT become canonical `CanonicalCandle` objects while provider finality is unavailable.**

The correction therefore belongs at the existing P3 normalization/canonicalization boundary. The MEXC acquisition adapter does not need to invent a false acquisition failure merely because the acquired observation is not canonically eligible.

## 3. Explicit semantic decision

Within the existing frozen architecture and current contracts, the deterministic canonical behavior is:

### 3.1 MEXC finality unavailable

If an MEXC candle payload contains no authoritative provider-finality signal, normalization MUST reject the candle for canonicalization with an explicit `is_closed` semantic issue.

It MUST NOT:

- set `is_closed=True`;
- set `is_closed=False`;
- set `is_closed=None`;
- infer finality from `windowEnd`;
- infer finality from `createTime` / event time;
- infer finality from receipt time or local clock;
- infer finality from REST-row availability;
- infer finality from repeated observations;
- infer finality from elapsed wall-clock time;
- infer finality from OHLC temporal geometry.

### 3.2 Why no new canonical state is introduced

The existing `CanonicalCandle` contract is frozen and represents `is_closed` as boolean. Downstream P4 semantics also distinguish closed candles from incomplete candles; neither `False` nor a new `UNKNOWN` value is equivalent to "provider finality unavailable."

Introducing `Optional[bool]`, a third enum-like state, or a competing canonical contract would therefore be an architecture/contract change, not a bounded bug fix. This Task Order does not authorize such a redesign.

If implementation evidence demonstrates that rejection at normalization cannot satisfy the required semantics without changing a frozen contract or higher-order invariant, Producer MUST STOP THAT PART and return the exact conflict to CONTROL. No silent contract change is permitted.

## 4. Required implementation

Producer MUST correct the existing MEXC path so that:

1. MEXC raw/acquisition evidence remains provider-specific and provenance-preserving.
2. MEXC REST historical klines remain available as raw observations when acquisition itself succeeds.
3. MEXC WebSocket kline observations remain available as raw observations when acquisition itself succeeds.
4. MEXC normalization no longer manufactures `closed=True`.
5. MEXC normalization explicitly rejects unavailable finality before constructing `CanonicalCandle`.
6. The rejection is deterministic and uses the existing normalization/validation error vocabulary rather than creating an unnecessary parallel semantic framework.
7. Before implementation, Producer MUST inspect the repository's existing `ValidationCode` / `ValidationIssue` vocabulary and select the semantically correct existing code for unavailable MEXC finality. A new validation taxonomy/code is NOT authorized merely for this correction. If the existing vocabulary is demonstrably insufficient, Producer MUST STOP ONLY THAT PORTION and report the exact contract/governance conflict to CONTROL.
8. Producer MUST define and test deterministic validation precedence when multiple invalid conditions coexist, including unavailable finality with malformed `windowEnd`, contradictory timing, malformed OHLCV, or contradictory provider metadata. Classification MUST NOT depend on dictionary ordering, incidental branch order, or exception behavior; the chosen precedence must remain within existing validation semantics and be evidenced by tests.
7. No rejected MEXC candle reaches canonical persistence, quantitative orchestration, or P4 structural processing.
8. Raw/staging persistence and provenance behavior remain intact; the correction MUST NOT delete or rewrite historical raw evidence merely because it is not canonicalizable.
9. Existing Binance semantics remain unchanged.
10. Unsupported providers remain rejected.
11. No provider-specific MEXC semantics are transferred from Binance by analogy except the already-established general anti-fabrication rule: unsupported finality must not become provider-final `True`.

## 6. Required test matrix

The correction MUST be tested beyond the happy path.

### 6.1 MEXC normal acquisition / unavailable finality

Prove that:

- a valid MEXC WebSocket kline with valid OHLCV, interval, `windowStart`, and `windowEnd` is acquired successfully;
- normalization rejects it because provider finality is unavailable;
- the rejection identifies `is_closed` / finality semantics explicitly;
- no `CanonicalCandle` value is produced;
- raw payload, provenance, event time, and source sequence remain intact.

### 6.2 MEXC REST historical kline

Prove that:

- a valid historical REST kline row is acquired successfully;
- its close-time field is preserved as close-time evidence only;
- normalization rejects it as lacking authoritative finality;
- receipt time or elapsed time cannot promote it to closed.

### 6.3 No temporal inference

Use controlled test clocks/timestamps to prove that changing:

- `windowEnd`;
- event/create time;
- receipt time;
- local clock;
- relative age of the observation

does not turn unavailable MEXC finality into `is_closed=True`.

### 6.4 Malformed and contradictory input

Producer MUST test the interaction of finality-unavailable with other invalid conditions and document deterministic precedence for each applicable combination.

Where the existing MEXC wire representation can express the relevant condition, cover:

- missing required kline fields;
- malformed `windowStart`;
- malformed `windowEnd`;
- `windowEnd <= windowStart`;
- malformed OHLCV;
- contradictory provider metadata/symbol identity;
- malformed/unexpected payload shape.

Such failures must remain explicit and must never fall through to synthetic finality.

If a "finality flag" cannot be represented by the actual MEXC wire contract, the test MUST document that fact rather than inventing a provider field merely to create a fixture.

### 6.5 Replay / idempotency / identity

Prove that:

- replaying the same MEXC observation remains deterministic;
- raw acquisition identity/deduplication remains stable for identical provider observations;
- rejection at normalization does not mutate or rewrite acquisition identity;
- an unavailable-finality observation cannot become canonical merely because it is replayed;
- no previously non-final/unavailable observation can be promoted to canonical closed state without authoritative provider evidence.

### 6.6 Downstream protection

Prove at the existing boundaries that a rejected MEXC candle:

- cannot enter canonical candle persistence;
- cannot enter default closed-candle quantitative processing;
- cannot be used as a closed structural candle;
- does not create fabricated quantitative/structure facts.

No new downstream semantic workaround may be introduced.

### 6.7 Regression

Run the complete applicable repository test suite and required CI checks. At minimum, the focused MEXC normalization/acquisition tests and the existing Binance finality suite MUST pass, together with the applicable full regression suite.

Exact commands, test counts, CI run identifiers, and results MUST be reported from actual execution.
