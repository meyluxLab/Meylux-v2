# MEYLUX V2 — TASK ORDER

## TO-P1-004 — Data Contracts

**Task Order ID:** `TO-P1-004`
**Phase:** `PH-P1`
**Step:** `STEP-P1-004`
**Governance Class:** Phase Implementation
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** `AUTHORIZED TO EXECUTE`
**Predecessor:** `STEP-P1-003` — COMPLETE / VERIFIED
**Authorization Basis:** `PH-P1` / `General Continuation and Phase Progression Authority` / `AR-P1-AUDIT-003`
**Architectural Basis:** `DOC-V2-ARCH-001` — RATIFIED / FROZEN

## 1. Objective

Establish the canonical Meylux V2 data-contract foundation required for deterministic, validated downstream processing.

This Task Order activates only `STEP-P1-004`. It does not activate or authorize any later P1 step.

## 2. Required Scope

Implement and test the P1 Data Contracts boundary defined by `PH-P1`, including:

1. Canonical contract definitions for the V2 data objects required by the current P1 foundation and its immediate downstream dependencies.
2. Explicit type semantics and approved numeric/precision semantics required by the frozen architecture and existing validated data path.
3. Explicit timestamp/timezone/time-semantics contracts; no ambiguous temporal representation.
4. Clear contract boundaries between raw/input representations, canonical representations, validation outputs, and downstream consumers where those boundaries already exist in the repository architecture.
5. Immutability/read-only semantics where required by the canonical data model; contracts must not silently permit mutation that can compromise provenance or deterministic processing.
6. Contract validation rules and deterministic failure behavior for invalid contract instances.
7. Contract tests sufficient to demonstrate the defined schema/type/precision/time/immutability behavior.
8. Compatibility with the already verified P1 Repository, Docker, and Database foundations.

## 3. Architectural / Governance Requirements

The implementation MUST preserve:

- `INV-V2-001` STRICT READ-ONLY.
- `INV-V2-002` DETERMINISTIC BASELINE.
- `INV-V2-003` NO FABRICATION.
- `INV-V2-004` EVIDENCE PROVENANCE.
- `INV-V2-006` LOGICAL IDENTITY.
- `INV-V2-007` SINGLE AUTHORITATIVE PERSISTENCE.
- `INV-V2-008` PROVIDER ISOLATION.
- `INV-V2-010` EVIDENCE-BACKED STATE.

The implementation must not introduce provider-runtime activity, market acquisition, trading, capital control, V1 access/mutation, or future-phase functionality.

The Producer must preserve existing Stable IDs, approved filenames, repository structure, interfaces, schemas, and contracts unless the Task Order explicitly requires a new artifact. If a genuine conflict with the frozen architecture or an existing ratified contract is discovered, STOP THAT PART and report the conflict rather than silently redesigning it.

## 4. Implementation Boundary

The Producer may choose implementation details inside the approved architectural constraints. Do not add unrelated frameworks, speculative abstractions, future-phase features, or performance tuning outside this step.

Use the existing repository conventions established by P1 Steps 1–3.

No external market data is required for this step. Do not fabricate sample market values as authoritative evidence.

## 5. Required Outputs

At minimum, provide:

- implemented canonical data-contract artifacts under the repository structure justified by the existing architecture;
- required contract validation logic;
- deterministic contract tests;
- updates to governed registry entries for newly created material artifacts, where required;
- a Build Report identifying all actual changes, tests, results, deviations, and open questions.

Stable IDs must be allocated only through the governed repository registry/convention; do not invent competing IDs.

## 6. Verification Requirements

Producer self-test evidence MUST distinguish:

`IMPLEMENTED` ≠ `TESTED` ≠ `VERIFIED`.

The Build Report must contain actual:

- changed paths;
- artifact IDs where applicable;
- commands/tests executed;
- exit codes/results;
- relevant test counts only when actually observed;
- deviations and Open Questions;
- final implementation state.

CONTROL will independently audit the Build Report and repository state before the step can become `COMPLETE / VERIFIED`.

## 7. Acceptance Criteria

The step is acceptable for independent CONTROL audit when evidence demonstrates:

1. canonical contracts exist for the scope defined by this Task Order;
2. type semantics are explicit and deterministic;
3. numeric/precision semantics are explicit and compatible with the V2 deterministic doctrine;
4. timestamp/timezone semantics are explicit and deterministic;
5. invalid contract instances fail through defined validation behavior;
6. required immutability/provenance boundaries are enforced;
7. contract tests exercise the required behavior;
8. existing P1 foundations remain compatible;
9. no prohibited activity or future-step scope was introduced;
10. Build Report is complete and based only on actual evidence.

## 8. Explicit Non-Authorization

This Task Order does NOT authorize:

- market/provider runtime activity;
- live market-data acquisition;
- specialist/AI intelligence implementation;
- trading or order execution;
- capital movement, custody, withdrawal, deposit, or leverage control;
- V1/V1 VPS mutation;
- activation of `STEP-P1-005` or any later step;
- architecture/governance override;
- silent repair of defects outside the Producer implementation boundary.

## 9. Completion Boundary

On successful implementation and self-test, Producer returns the Build Report to CONTROL. The step remains `IMPLEMENTED / TESTED` until independent CONTROL audit establishes `VERIFIED`.

Only after that verification may normal Phase 1 progression activate the next defined step.
