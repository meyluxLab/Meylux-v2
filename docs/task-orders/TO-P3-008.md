## 2. Objective

Establish and independently verify the final operational Phase 3 boundary in which validated, normalized, quality-aware canonical data reaches:
1. authoritative canonical persistence;
2. normalized event handoff;
3. observable runtime behavior;
4. real authorized V2 VPS execution;
5. deterministic failure/recovery behavior;
6. evidence sufficient for G-3 and Phase 3 closure.

Required conceptual flow:

`P2 raw/staging evidence → validation → normalization → quality/quarantine/lineage → authoritative canonical persistence → normalized event handoff → P4-ready canonical data`

A passing unit test, successful container start, database write, or nominal event publication alone is insufficient.

## 3. Scope and Architecture Boundary

### 3.1 Authoritative persistence

Implement the authoritative persistence boundary required by the Phase 3 architecture and the referenced P3 roadmap, subject to actual contract/schema inspection and higher-authority architecture.

The target logical canonical persistence objects identified by the registered P3 roadmap are:
- `canonical_instruments`
- `canonical_candles`
- `canonical_trades`
- `canonical_orderbook_depth`
- `canonical_derivatives`
- `data_quality_logs`

The Producer MUST NOT assume these names are sufficient merely because the roadmap lists them. Before implementation, inspect existing migrations, contracts, data structures and runtime boundaries and establish the minimum coherent schema necessary to satisfy the authorized P3-008 boundary.

Authoritative persistence must:
- contain only canonical-eligible validated semantic data;
- preserve stable identity, provenance and lineage references available from P3-007;
- preserve explicit quality state where required downstream;
- use deterministic identity/uniqueness and idempotency rules;
- define insert/update/delete semantics explicitly;
- preserve append-only semantics for the canonical authoritative objects where required by architecture;
- prevent application runtime roles from receiving broad DDL authority;
- prevent ordinary application paths from mutating or deleting authoritative history contrary to the table contract;
- define transaction boundaries and atomicity;
- support safe replay without duplicate canonical truth;
- make failure behavior explicit;
- make schema versioning/migration state explicit;
- preserve UTC/timezone semantics;
- remain provider-neutral.

No fabricated data may be persisted.

### 3.2 Normalized event handoff

Implement the Phase 3 normalized-event handoff boundary required by the architecture.

The P3 roadmap identifies the logical stream as:

`stream:canonical:market_events`

This identifier is planning/reference context until validated against the actual repository/runtime boundary. The Producer must use it if it is the correct governed implementation target, or document the exact authoritative/repository-supported equivalent rather than silently inventing a competing stream.

The handoff must define and test, as applicable:
- event identity;
- canonical payload identity;
- serialization;
- quality state propagation;
- provenance/lineage references;
- ordering/sequence semantics;
- duplicate handling;
- idempotency;
- retry behavior;
- acknowledgement semantics where a consumer boundary exists;
- failure isolation;
- backpressure/boundedness;
- replay behavior;
- consumer compatibility;
- no promotion of rejected/unavailable data;
- provider-neutral payload semantics.

### Governing Read-Only Boundary

For purposes of this authority, the governing criterion is the **actual effect of the operation on the VPS and its production state**, not merely the Producer's stated intent or the apparent name of the command.

Read-only activity may therefore:

```text
OBSERVE
→ INSPECT
→ READ
→ QUERY
→ DIAGNOSE
→ CORRELATE
→ VALIDATE
```

provided that the operation does not mutate Production state.

This authority does **not** authorize:

```text
DEPLOY
→ INSTALL
→ MIGRATE
→ INSERT / UPDATE / DELETE
→ CREATE / ALTER / DROP
→ START / STOP / RESTART
→ MODIFY CONFIGURATION
→ MODIFY SERVICES
→ MODIFY CONTAINERS
→ MODIFY IMAGES
→ MODIFY PRODUCTION REPOSITORY STATE
→ DELETE DATA
→ ROLLBACK PRODUCTION
→ CHANGE PRODUCTION RUNTIME STATE
→ ANY OTHER PRODUCTION MUTATION
```

unless a separate, explicit, governed authorization grants that exact mutation authority.

Execution of a command whose **actual effect is strictly observational or otherwise non-mutating** does not transfer, exercise, or imply Production VPS mutation authority.

The Producer must nevertheless apply professional engineering judgment when selecting inspection commands.

Where a command, operation, query, script, diagnostic utility, or tool has uncertain, conditional, implicit, or potentially side-effecting behavior, the Producer must **not execute it under this read-only authority** unless its non-mutating behavior has first been established with sufficient confidence.

Where safe read-only alternatives exist, they must be preferred.
