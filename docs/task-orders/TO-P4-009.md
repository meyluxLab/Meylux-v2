## 3. Authorized Producer Scope
The Producer is authorized only to implement the database-grant hardening required by Decision 2.

### 3.1 Migration boundary
- Add exactly one new forward migration after migrations '0001'–'0005'.
- Do not edit, rewrite, reorder, delete, or otherwise modify migrations '0001'–'0005'.
- The migration must be idempotent under the repository's migration conventions.
- No unrelated schema, data, index, function, trigger, role, password, or configuration change is authorized.

### 3.2 raw_acquisition_events
- Revoke UPDATE on 'meylux.raw_acquisition_events' from 'meylux_app'.
- Before implementation, search the complete repository implementation/tests for legitimate application-role UPDATE paths against this table.
- A direct SQL UPDATE used only by a negative permission test is not a legitimate production path.
- Do not revoke required SELECT/INSERT access.

### 3.3 meylux_admin default privileges
Correct the applicable 'meylux_admin' default privileges so future tables do not silently inherit UPDATE for 'meylux_app'. Determine the exact existing default-privilege grant from repository/runtime evidence before changing it. Narrow only the unauthorized UPDATE inheritance relevant to 'meylux_app'. Do not alter unrelated default privileges.

### 3.4 canonical_event_outbox
Attempt to narrow 'meylux_app' UPDATE privilege to the relay-required columns: 'published_at' and 'published_stream_id'. This is conditional: only implement column-level narrowing if PostgreSQL privilege semantics and the actual relay code permit it without changing relay behavior or violating the existing contract.

The Producer must test the actual relay path, including its UPDATE operation. If column-level privilege behavior is incompatible with the relay's actual SQL or with the ratified contract, STOP THAT PART and report the authoritative conflict/open question. Do not invent a workaround outside this Task Order.

### 3.5 Explicit non-scope
- Any edit to migrations '0001'–'0005'.
- Any architecture change.
- Any Phase 5 implementation or authorization.
- Any change to quantitative engines.
- Any change to Decimal policy.
- Any change to canonical/quantitative data semantics.
- Deletion or mutation of governed market data except bounded test fixtures required to verify the authorized grant behavior.
- Modification of application credentials/secrets.
- Runtime deployment/application to the VPS.
- SentinelX execution by the Producer.
- Legacy 'compose-api-run-*' container cleanup.
- Docker prune.
- Removal/modification of volumes, images, networks, or services.
- Registry/Checkpoint/README/Change Ledger closure synchronization.

## 4. Required Pre-Implementation Evidence
Before coding, Producer must establish from repository evidence:
1. Current migrations '0001'–'0005' and migration ordering.
2. The current definition and grants relevant to 'raw_acquisition_events'.
3. The current definition of 'canonical_event_outbox'.
4. The exact relay code path performing the outbox publication UPDATE.
5. All repository code/tests containing UPDATE operations against 'raw_acquisition_events'.
6. Existing tests covering application-role privilege boundaries and outbox publication.
7. Current canonical/quantitative truth-table expectations, preserving verified counts '156' and '3/1/1'.
No implementation may proceed by assuming any of the above.

## 5. Required Implementation Tests
Producer must add/update deterministic tests sufficient to demonstrate:
- 'meylux_app' cannot UPDATE 'raw_acquisition_events'.
- 'meylux_app' retains required SELECT/INSERT behavior for 'raw_acquisition_events'.
- The relevant 'meylux_admin' default privilege no longer grants future-table UPDATE to 'meylux_app'.
- 'canonical_event_outbox' relay publication continues to work.
- If column-level UPDATE is implemented, the relay can update 'published_at' and 'published_stream_id' and cannot update unrelated outbox columns through that privilege.
- DELETE/TRUNCATE boundaries remain unchanged.
- Existing migration ordering remains valid.
- Existing P4 canonical/quantitative truth-table tests remain valid.

## 6. Build Report Requirements
Producer must deliver a Build Report identifying exact files changed, exact new migration identifier, pre-implementation code-search evidence, privilege SQL and rationale, test commands and real results, relay behavior evidence, any compatibility limitation concerning column-level privileges, explicit confirmation that migrations '0001'–'0005' were not modified, explicit confirmation that no Phase/Step/G-4 status was changed, and any deviations/open questions.
Producer must not declare project-level VERIFIED or CLOSED.

## 7. CONTROL Audit / Runtime Application Boundary
After Producer delivery:
1. CONTROL independently audits the Build Report and implementation.
2. CONTROL verifies the migration diff and test evidence.
3. Only after an independent audit passes may CONTROL apply the authorized migration through SentinelX only.
4. CONTROL then re-verifies application-role grants, default privileges, relay publication behavior, canonical inventory count = '156', quantitative inventory = '3/1/1', worker/relay behavior, and absence of unintended G-4 evidence changes.
5. Any G-4 evidence impact is a mandatory stop-and-report condition.
6. CONTROL owns all post-completion synchronization and resolution of 'OQ-P4-006-APP-GRANTS'.

## 8. Acceptance / Stop Conditions
Acceptance requires all of the following: new forward migration only; migrations '0001'–'0005' unchanged; no legitimate raw-table UPDATE path broken; required relay behavior preserved; grant boundary matches the Owner directive; canonical count remains '156'; quantitative count remains '3/1/1'; no G-4 evidence invalidation; no architecture/engine/Decimal/Phase-5 mutation; complete Build Report evidence.

Stop and report immediately if a legitimate raw-table UPDATE path is discovered; column-level outbox privilege narrowing is incompatible with the actual relay; migration ordering or existing migration integrity is threatened; required truth-table counts change unexpectedly; any G-4 evidence is affected; implementation would require architecture, engine, Decimal, or Phase-5 changes; or authoritative repository artifacts conflict.

## 9. Lifecycle Boundary
This Task Order is a post-closure hardening action. It does not reopen 'PH-P4', 'STEP-P4-006', or 'G-4'. The existing closure remains authoritative unless independent CONTROL evidence demonstrates that the authorized hardening has materially invalidated a closure criterion. In that event, CONTROL must report the specific evidence and stop the affected action rather than silently changing closure state.
