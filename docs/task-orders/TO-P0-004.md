# MEYLUX V2 — TASK ORDER

## TO-P0-004 — V1 Lessons Integration

**Task Order ID:** `TO-P0-004`  
**Phase:** `PH-P0`  
**Step:** `STEP-P0-003` — V1 Lessons Integration  
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)  
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)  
**Status:** AUTHORIZED TO EXECUTE  
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-002`  
**Predecessor:** `STEP-P0-002` — Constitution Ratification (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-003 — V1 Lessons Integration`: identify and integrate approved V1 lessons and failure evidence into V2 architectural controls and governance knowledge, without importing V1 implementation or authorizing V1 mutation.

## 2. Authoritative Boundary

The authoritative Phase 0 sequence is established by `ADR-ARCHITECTURE-001`. `STEP-P0-001` and `STEP-P0-002` are complete and verified. `STEP-P0-003` is the sole currently activated Step. Later Steps remain defined but not authorized.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the authoritative V1 lesson/failure evidence already available to the repository/project, including documented lessons from persistence growth, duplicate identity, queue backlog, provider stream liveness, order-book sequence semantics, repeated resync/rate-limit pressure, hidden worker coupling, host resource pressure, and evidence/state drift.
2. Map each materially relevant lesson to an explicit V2 architectural control, invariant, requirement, behavior, governance control, observability/recovery requirement, or known design consideration as justified by evidence.
3. Preserve separation between V1 historical evidence and V2 architecture; do not import V1 code, deployment, runtime assumptions, or implementation patterns merely because they existed in V1.
4. Identify contradictions, omissions, or unresolved lessons requiring higher-level architectural/governance disposition. Do not silently resolve a genuine conflict.
5. Preserve V2 constitutional boundaries, including strict read-only operation, deterministic baseline, no fabrication, evidence provenance, independent evidence, logical identity, single authoritative persistence, provider isolation, zero lookahead, evidence-backed state, and V1 isolation.
6. Maintain traceability from each integrated lesson/control to its source evidence and relevant V2 architectural/governance artifact.
7. Produce a Build Report at the next legitimately registered BR identity/path. Do not invent an unregistered identity.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- modify, resume, deploy, or operate V1 or the V1 VPS/runtime;
- execute market-data, trading, capital, fund-transfer, or provider-runtime actions;
- activate `STEP-P0-004` through `STEP-P0-010`;
- issue Task Orders for future Steps;
- ratify/freeze the Master Architecture;
- alter ratified Stable IDs or governance decisions;
- silently convert historical V1 implementation into V2 architecture;
- fabricate missing V1 evidence or claim lessons not supported by available evidence.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-002` remains `COMPLETE / VERIFIED`;
- only V1 lessons/failure evidence integration was performed;
- each material integrated lesson has traceable V1 evidence and V2 disposition;
- unsupported or unresolved lessons remain explicitly identified;
- V1 remains frozen and unmodified;
- no later Step was activated;
- no unauthorized runtime/environment/market/trading/capital activity occurred;
- Build Report contains actual evidence and does not claim Reviewer approval or Project Owner ratification.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the Build Report and repository evidence before any Step completion transition. If accepted, the next Step may be activated only through the existing sequential governance process.
