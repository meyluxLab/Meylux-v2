## 1. Authority and Purpose

This Task Order implements the Project Owner direction to resolve the upstream P4 `knowledge_time` problem before further P5 progression that depends on authoritative historical fact knowledge-time semantics.

The Owner intentionally authorized CONTROL to determine the correct technical and governance path rather than prescribing a database column, schema, migration shape, contract change, provenance structure, backfill mechanism, or implementation pattern.

The governing objective is:

> Do not make P5 accept existing P4 data by weakening P5 evidence requirements. Repair the upstream P4 semantic and persistence boundary so that eligible persisted facts have an authoritative, reproducible knowledge-time basis, while facts whose historical knowledge cannot legitimately be established remain explicitly unevidenced.

## 2. Accepted CONTROL Finding

The accepted CONTROL finding is that the defect is not simply the absence of a database column.

Existing P4 semantic knowledge-time capability exists in parts of the upstream calculation path, while the required semantic is not currently preserved as authoritative and recoverable fact-level evidence through the persistence boundary.

The existing G-4 / orchestration `as_of` / primary knowledge boundary demonstrates that an operational temporal boundary exists. It does **not** establish that every persisted P4 fact family has an identical fact-level `knowledge_time` semantic.

The Producer must therefore perform fact-family-specific semantic investigation and must not assume a universal knowledge-time rule.

## 3. Governing Authorities

- `DOC-V2-ARCH-001` and all superior frozen architecture;

If an actual authoritative conflict is discovered that cannot be resolved without guessing, stop the affected portion under ADR-GOVERNANCE-013 Rule 1(B) and report the exact conflict. Do not silently reinterpret a frozen authority.

## 4. Required Semantic Outcome

For every currently persisted P4 fact family materially affected by this problem, determine and preserve, where evidence permits:

1. the fact's `event_time` meaning;
2. the authoritative origin of `knowledge_time`;
3. the earliest legitimate knowledge boundary;
4. the evidence supporting that boundary;
5. provenance and source identity;
6. deterministic fact identity;
7. persistence/read-back representation;
8. replay/recovery semantics;
9. historical recoverability.

The following concepts must remain distinct unless an authoritative semantic rule proves equivalence:

- `event_time`;
- provider/source timestamps;
- observation/receipt time;
- ingestion time;
- persistence time;
- logging time;
- wall-clock execution time;
- `knowledge_time`.

Never substitute `persisted_at`, `logged_at`, `event_time`, current time, or another operational timestamp merely because it is available.

Do not assume that the G-4 `as_of` boundary is automatically the fact-level `knowledge_time` for every P4 family.

## 6. Historical Evidence Boundary

Classify existing historical records into at least:

1. directly evidenced authoritative knowledge time;
2. deterministically reconstructible from preserved authoritative evidence;
3. insufficient evidence;
4. values requiring unsupported inference.

Only classes 1 and 2 may receive an authoritative historical knowledge-time value.

Classes 3 and 4 must remain explicitly unavailable/unevidenced for P5 purposes.

No authorization is given to fabricate timestamps, infer knowledge from persistence time, use wall-clock reconstruction, or manufacture historical certainty.

Existing valid historical data must not be destructively rewritten merely to increase P5 availability.

## 7. P5 Temporal Compatibility

The correction must satisfy the existing P5 evidence model; P5-002 must not be weakened or reopened merely to accommodate P4.

For an eligible fact:

`knowledge_time <= snapshot.as_of`

must remain the temporal eligibility condition.

The resulting evidence must preserve independently:

- `event_time`;
- `knowledge_time`;
- identity;
- provenance.

A fact whose authoritative knowledge time is unavailable must remain unavailable/rejected rather than silently admitted.

## 8. Persistence and Contract Boundary

CONTROL has not prescribed the implementation mechanism.

If the correct solution requires contract, persistence, schema, provenance, or migration changes, use the existing authoritative P4 architecture and persistence model.

Any migration must be:

- deterministic;
- idempotent;
- non-destructive;
- compatible with populated historical data;
- consistent with append-only/security boundaries;
- directly tested;
- explicit about legacy rows.

Do not create a competing truth store.

Do not grant unauthorized mutation privileges merely to implement this correction.

Do not rewrite frozen/ratified migrations.

If an additive compatible contract extension is sufficient, implement it through the normal governed correction path. If the required semantic cannot be expressed without violating a frozen contract or architecture, stop that affected portion and report the conflict.

## 9. Mixed Legacy/New Data

The resulting implementation must explicitly distinguish, where applicable:

- legacy rows without authoritative knowledge time;
- new authoritative rows;
- rows with explicitly unavailable knowledge time;
- rows whose knowledge time is deterministically reconstructible.

P5 eligibility must never silently treat legacy unevidenced records as equivalent to newly authoritative records.

## 10. Replay, Identity and Provenance

Demonstrate that knowledge-time semantics survive:

- calculation replay;
- worker replay where applicable;
- duplicate delivery;
- persistence retry;
- service restart where applicable;
- serialization/deserialization;
- database read-back;
- deterministic reconstruction.

Repeated observations must not create contradictory knowledge-time values for the same authoritative fact.

Identity must remain stable unless an explicit semantic/identity requirement is established and governed.

A future reviewer must be able to determine what evidence justifies the stored knowledge-time value.

## 11. Temporal Edge Conditions

Where materially applicable, implementation/tests must cover:

- missing/null knowledge-time evidence;
- malformed timestamps;
- timezone normalization;
- precision/boundary behavior;
- invalid temporal ordering;
- `knowledge_time == snapshot.as_of`;
- `knowledge_time > snapshot.as_of`;
- event-time/knowledge-time divergence;
- duplicate/repeated observations;
- late/out-of-order information;
- contradictory evidence;
- mixed legacy/new persistence;
- migration reruns;
- deterministic serialization and identity.

No silent repair of invalid or contradictory temporal evidence is permitted.

## 12. Required P5 Compatibility Proof

The Producer must provide direct evidence that a resulting persisted fact can satisfy the existing P5 evidence boundary without weakening it.

At minimum demonstrate:

`event_time` preserved independently  
`knowledge_time` preserved independently  
identity preserved  
provenance preserved  
`knowledge_time <= snapshot.as_of` → eligible  
`knowledge_time > snapshot.as_of` → excluded  
missing authoritative `knowledge_time` → unavailable/rejected

Do not modify P5-002 semantics to make these tests pass.
