# MEYLUX V2 — TASK ORDER

## TO-P1-007 — Observability Foundation

**Task Order ID:** `TO-P1-007`
**Phase:** `PH-P1`
**Step:** `STEP-P1-007`
**Governance Class:** Phase Implementation
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** `AUTHORIZED TO EXECUTE`
**Predecessor:** `STEP-P1-006` — COMPLETE / VERIFIED
**Authorization Basis:** `PH-P1` / General Continuation and Phase Progression Authority / `AR-P1-AUDIT-006`
**Architectural Basis:** `DOC-V2-ARCH-001` — RATIFIED / FROZEN

## 1. Objective

Establish the structured observability foundation required to diagnose, verify, and safely operate Meylux V2 P1 behavior, without activating market acquisition, provider runtime, specialist/AI intelligence, trading, capital control, V1 activity, or later-phase functionality.

This Task Order activates only `STEP-P1-007`. It does not authorize `STEP-P1-008` or any later phase.

## 2. Required Scope

Implement and test the minimum reproducible observability foundation required by the frozen V2 architecture and PH-P1 specification:

1. Structured application logging with stable machine-readable event fields and deterministic severity semantics.
2. Correlation/context propagation sufficient to connect a request, queue operation, worker execution, failure, and verification-relevant event without relying on hidden chat state.
3. Explicit secret/credential scrubbing at the logging boundary. Logs must not expose passwords, tokens, API keys, private keys, connection secrets, or equivalent sensitive material.
4. Health and diagnostic signals sufficient to distinguish normal operation, degraded operation, overload, dependency failure, and unavailable capability without fabricating business/market values.
5. Observability of the P1 queue/worker boundary, including bounded backlog/overload, retry/DLQ outcomes, timeout/failure outcomes, and recovery-relevant events.
6. Evidence-compatible event structure so material runtime observations can be correlated with Task Orders, tests, execution evidence, and audit artifacts.
7. Bounded logging/resource behavior: no uncontrolled log amplification, unbounded in-memory event accumulation, or silent failure when observability itself is degraded.
8. Deterministic tests for structured event shape, context propagation, secret scrubbing, health/diagnostic semantics, queue/worker observability, and bounded failure behavior as applicable.
9. Required governed registry/state updates for material artifacts. Stable IDs are governance-controlled; do not invent competing identities.
10. A factual `BR-P1-007` containing actual changes, tests, results, deviations, Open Questions, and final Producer state.

## 3. Architectural / Governance Requirements

The implementation MUST preserve:

- `INV-V2-001` STRICT READ-ONLY.
- `INV-V2-002` DETERMINISTIC BASELINE.
- `INV-V2-003` NO FABRICATION.
- `INV-V2-004` EVIDENCE PROVENANCE.
- `INV-V2-006` LOGICAL IDENTITY.
- `INV-V2-007` SINGLE AUTHORITATIVE PERSISTENCE.
- `INV-V2-008` PROVIDER ISOLATION.
- `INV-V2-010` EVIDENCE-BACKED STATE.

Observability must remain an operational/evidence layer and must not become an alternative source of authoritative business truth. Logs and metrics may describe observed system state but must not manufacture market data or replace canonical persistence.

Secret scrubbing is mandatory. Sensitive configuration values must never be copied into logs, test fixtures, Build Reports, audit reports, or repository artifacts.

Do not silently modify frozen architecture, verified contracts, Stable IDs, security boundaries, or unrelated interfaces. If a genuine architecture/governance/authority conflict is discovered, STOP THAT PART and report it.

## 4. Implementation Boundary

Use the existing V2 Python/application foundation and existing service/queue boundaries. Do not introduce an alternative observability platform or unrelated infrastructure framework unless already required by the repository architecture.

Keep the foundation provider-neutral. No external market data is required for implementation or tests.

Numeric limits such as log-rate limits, retention periods, sampling thresholds, and diagnostic intervals are implementation/configuration parameters, not architectural invariants. They must be explicit and bounded where introduced.

The implementation must avoid unbounded logging loops, recursive logging failure, uncontrolled payload expansion, and silent loss of critical diagnostic context.

## 5. Required Outputs

At minimum, provide:

- structured logging/event foundation within the existing repository structure;
- correlation/context propagation;
- mandatory secret scrubbing;
- health/diagnostic semantics for P1 operation;
- queue/worker observability for material success/failure/retry/overload/recovery outcomes;
- bounded observability/resource behavior;
- deterministic tests and observed results;
- governed registry/state updates where required;
- `BR-P1-007` containing actual implementation and test evidence.

## 6. Verification Requirements

Producer self-test evidence MUST distinguish:

`IMPLEMENTED` ≠ `TESTED` ≠ `VERIFIED`.

The Build Report must contain actual:

- changed paths;
- Stable IDs where applicable;
- commands/tests executed;
- exit codes/results;
- observed test counts only when actually observed;
- deviations and Open Questions;
- final implementation state.

CONTROL will independently audit the repository, implementation, Build Report, and relevant runtime evidence before the step can become `COMPLETE / VERIFIED`.

## 7. Acceptance Criteria

The step is acceptable for independent CONTROL audit when evidence demonstrates:

1. structured events are machine-readable and contain the required diagnostic context;
2. correlation/context can be followed across relevant P1 execution boundaries;
3. secrets and sensitive configuration are scrubbed before emission;
4. health/diagnostic signals distinguish meaningful operational states without fabricating business data;
5. queue/worker success, failure, retry, timeout, overload, DLQ, and recovery-relevant outcomes are observable;
6. observability behavior is bounded and does not create an uncontrolled resource-growth path;
7. observability remains separate from authoritative business persistence;
8. deterministic tests exercise the material behavior and failure boundaries;
9. existing P1 foundations remain compatible;
10. no prohibited activity or future-step scope is introduced;
11. Build Report is complete and based only on actual evidence.

## 8. Explicit Non-Authorization

This Task Order does NOT authorize:

- live market-data acquisition;
- provider runtime integration;
- Binance/MEXC runtime implementation;
- specialist/AI intelligence;
- trading or order execution;
- capital movement, custody, withdrawal, deposit, or leverage control;
- V1/V1 VPS mutation;
- activation of `STEP-P1-008`;
- architecture/governance override;
- replacement of authoritative persistence with logs/metrics;
- silent repair of defects outside the Producer implementation boundary.

## 9. Completion Boundary

On successful implementation and self-test, Producer returns `BR-P1-007` to CONTROL. The step remains `IMPLEMENTED / TESTED` until independent CONTROL audit establishes `VERIFIED`.

Only after that verification may normal Phase 1 progression activate `STEP-P1-008`.
