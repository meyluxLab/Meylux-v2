## 2. Objective

Establish the explicit data-quality trust boundary for validated/normalized Phase 3 data so that downstream consumers can distinguish trustworthy, degraded, stale, incomplete, contradictory, rejected and unavailable evidence, while invalid or untrusted data is isolated through governed quarantine/DLQ behavior and material lineage remains traceable.

The Step must strengthen the existing Phase 3 validation/normalization foundation rather than replacing it.

Required conceptual flow:

`P3 validated/normalized evidence`
→ `quality classification`
→ `VALID canonical-eligible OR explicit degraded/non-canonical state`
→ `quarantine/DLQ for invalid/untrusted data where applicable`
→ `lineage/provenance record sufficient for audit and replay`

This Step does not establish authoritative persistence or normalized event handoff; those belong to `STEP-P3-008`.

## 3. Authorized Scope

Within the existing architecture and contracts, design and implement the P3-007 boundary covering, as applicable to actual supported data:

### 3.1 Quality classification

Implement explicit, deterministic quality classification capable of representing the authoritative record-level states:

`VALID`, `DEGRADED`, `STALE`, `INCOMPLETE`, `CONTRADICTORY`, `REJECTED`, `UNAVAILABLE`.

Where the architecture/data-flow boundary requires pipeline-level state, support the applicable states:

`RAW`, `STAGED`, `VALIDATING`, `NORMALIZED`, `CANONICAL`, `QUALITY_DEGRADED`, `REJECTED`, `QUARANTINED`, `EXPIRED`, `ARCHIVED`.

Do not invent additional authoritative quality states merely for convenience. Implementation-internal categories may be used only where they map deterministically to governed external semantics and do not leak as competing lifecycle vocabulary.

### 3.2 Data Quality Score and explanation

Where supported by the ratified architecture and existing contract boundary, implement the Phase 3 quality score as a deterministic value in `0.00–1.00` with an explainable component/vector representation covering the applicable dimensions identified by the Phase 3 architecture:

- freshness;
- completeness;
- consistency;
- feed health;
- validation status;
- provider capability.

The implementation must not manufacture a score when required evidence is absent. Missing evidence must produce an explicit governed outcome rather than an invented numeric substitute.

If the authoritative contract boundary does not support a numeric score for a particular state/input, the Producer must preserve explicit quality state and report the exact contract limitation to CONTROL rather than silently inventing semantics.

### 3.3 Quarantine / DLQ

Implement the authorized isolation boundary for corrupt, invalid, contradictory, unsupported or otherwise non-promotable evidence.

Required invariant:

`Invalid → Detect → Classify → Route`

and, where the applicable failure policy requires isolation:

`Invalid → Quarantine / DLQ`

The implementation MUST NOT:
- silently delete invalid evidence;
- promote invalid evidence to canonical truth;
- silently repair authoritative market values;
- allow a corrupt record to crash the worker solely because it is being routed to quarantine/DLQ;
- conflate quarantine/DLQ isolation with authoritative persistence.

The architecture-defined `normalization_dlq` boundary must be respected where applicable.

The Producer must make failure isolation, malformed input handling, duplicate/retry behavior, and bounded resource behavior explicit and testable.

### 3.4 Lineage / provenance

Establish sufficient lineage for each quality-classified canonical-eligible record and each quarantined/DLQ item to reconstruct the material evidence path:

`Provider → Raw/Staging record → Validation result → Normalization → Quality result → Canonical record`

Where a canonical record does not exist because the item was rejected/quarantined, the lineage record must preserve the available upstream identity and the validation/quality routing evidence necessary to explain why canonical promotion did not occur.

Lineage must preserve existing provenance semantics and must not invent upstream identifiers.

### 3.5 Integration boundary

The implementation must consume the already verified P3-001 through P3-006 foundation rather than duplicating or redefining their semantics.

P3-007 may add the quality/routing/lineage behavior required to turn prior validation findings into explicit downstream-safe data-quality outcomes.

Do not implement P3-008 authoritative persistence or normalized event handoff.

## 4. Required Engineering Properties

The implementation must be:

1. **Provider-neutral** — canonical quality semantics must not depend on Binance/MEXC wire-format details.
2. **Deterministic** — identical governed input/context produces identical classification, score and reason semantics.
3. **No-fabrication** — absent or insufficient evidence remains explicit.
4. **No silent fixing** — P3-007 classifies/routes; it does not silently repair authoritative data.
5. **Failure-isolated** — bad records do not corrupt unrelated records or crash the quality-routing path merely because one item is invalid.
6. **Replayable / auditable** — quality decisions and lineage are sufficiently explicit to reproduce and audit the decision.
7. **Downstream-safe** — canonical eligibility is never inferred merely from a passing superficial check; quality state remains explicit.
8. **Bounded** — untrusted inputs cannot induce unbounded memory/queue growth or uncontrolled retry behavior within the implemented boundary.
9. **Maintainable/extensible** — implementation-level abstractions should support additional providers/data types without provider coupling.
10. **Observable** — appropriate quality/routing evidence may be exposed through existing observability conventions, without creating an unrelated operational subsystem.
11. **Contract-preserving** — do not redesign established canonical contracts unless a concrete incompatibility is found; if found, stop only the conflicting portion and report it to CONTROL.
12. **AI-to-AI reconstructable** — decisions and evidence structures should be understandable from repository artifacts without hidden conversational assumptions.
