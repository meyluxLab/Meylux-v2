## 3. Objective

Establish the authoritative **Input Snapshot Builder** and the first complete **Fact Requirements Matrix (FRM)** for Phase 5 specialist execution.

The Step must answer, from actual repository contracts and actual available persisted facts:

1. What facts does each currently governed specialist domain require?
2. From which authoritative P4 fact source/table/contract does each fact come?
3. At what granularity/timeframe is it required?
4. What warm-up/history depth is required?
5. Is the fact mandatory or optional for the specialist?
6. What exact status/reason is produced when it is unavailable, unsupported, stale, incomplete or otherwise unusable?
7. How are `unsupported` and `unavailable` distinguished without guessing?
8. Can an authoritative Input Snapshot be built deterministically, hashed, and reproduced from the same persisted inputs?

The Snapshot Builder is a **consumer** of authoritative facts. It must not become a new fact-generation engine.

## 4. Authorized Scope

### 4.1 Input Snapshot Builder

Implement the provider-neutral, deterministic builder required to:

- accept an explicit snapshot boundary/as-of value;
- select only authoritative persisted facts permitted by the Phase 5 contract;
- require an explicit `knowledge_time` for every fact admitted to the authoritative Snapshot; `knowledge_time` is not optional for Snapshot membership and MUST satisfy `knowledge_time <= snapshot.as_of`;
- preserve symbol, venue, product, timeframe, identity, provenance, version and relevant status metadata;
- distinguish available, unsupported, unavailable and insufficient/invalid inputs explicitly;
- reject or route contradictory/ambiguous inputs rather than silently repairing them;
- produce deterministic ordering and deterministic identity/hash;
- make repeated construction from identical persisted inputs produce the same authoritative identity;
- prevent future-data/lookahead leakage;
- expose provenance sufficient for later `EvidenceRef` resolution, including the governed evidence-reference fields `source_family`, `record_id`, `identity_hash`, `event_time`, `knowledge_time`, `timeframe`, and `venue` where applicable;
- preserve `event_time` and `knowledge_time` as semantically distinct fields; never substitute one for the other or derive `knowledge_time` merely by copying `event_time` unless the authoritative upstream contract explicitly states that equality;
- remain independent of specialist outputs.

No specialist may consume another specialist's output through the Snapshot.

### 4.2 Fact Requirements Matrix (FRM)

Produce and register the FRM covering the full specialist requirement surface defined by the currently authorized Phase 5 roadmap.

At minimum, each FRM row must identify:

- specialist/domain identifier or governed domain reference;
- required fact;
- authoritative source/contract/table;
- granularity/timeframe;
- minimum history/warm-up requirement;
- mandatory vs optional;
- availability/status semantics;
- distinction between `unsupported`, `unavailable`, `insufficient`, `invalid`, and `stale` where applicable;
- provenance/evidence reference requirements;
- lookahead/as-of rule;
- the authoritative `USR-03` lifecycle disposition, which MUST be exactly one of `AVAILABLE_PERSISTED`, `PRQ_DELIVERED`, or `UNAVAILABLE_DISPOSITIONED`; there is no fourth disposition;
- a subordinate reason/status taxonomy where needed to preserve the required distinction among `unsupported`, `unavailable`, `insufficient`, `invalid`, and `stale` without creating additional USR-03 lifecycle states;
- exact repository evidence supporting the disposition and reason;
- for every `UNAVAILABLE_DISPOSITIONED` row, an explicit OQ/DD reference or other governed disposition record satisfying USR-03 is mandatory; a prose dependency route alone is insufficient.

Do not invent a P4 fact merely because the roadmap names it.

If a fact is not currently available, the FRM must state the real USR-03 disposition and reason, and route the dependency to its owning boundary. It must not silently create a P4 implementation.

### 4.3 Availability Verification

`AVAILABLE_PERSISTED` is a runtime evidence state, not a source-code/table-existence claim. A row may be classified `AVAILABLE_PERSISTED` only after the underlying persisted fact is independently evidenced on the authoritative VPS/runtime by CONTROL. Specialist executability or the existence of an upstream table/engine does not establish `AVAILABLE_PERSISTED`.

The following distinctions are mandatory during audit:
- specialist can execute with a Snapshot boundary;
- required facts for that specialist are actually available;
- all mandatory facts required for the specialist are available.
These are not equivalent claims. In particular, a specialist being described as executable in the roadmap does not by itself make its required facts `AVAILABLE_PERSISTED`.


Implement repository-level tests sufficient to verify deterministic Snapshot behavior and FRM semantics.

CONTROL will independently perform the authorized **read-only VPS verification** through SentinelX for this Step, including the applicable read-only data/fact availability queries. Producer must not perform VPS mutation or provider-runtime activation.

## 6. No-Lookahead and Determinism

The authoritative Snapshot must:

- use explicit `as_of` semantics;
- exclude facts with `knowledge_time > as_of`;
- have deterministic ordering;
- have deterministic canonical serialization and identity;
- preserve exact Decimal/numeric semantics already ratified by the project;
- contain no hidden wall-clock dependency;
- contain no NaN/Inf or fabricated fallback values;
- produce identical identity for identical authoritative inputs;
- change identity when authoritative input content changes.

Tests must include boundary cases around equal-to-as-of and strictly-after-as-of facts.

## 7. Failure and Data-Quality Semantics

The implementation must detect, classify and route. These reason classifications do not create additional USR-03 lifecycle dispositions:

- missing required fact;
- unsupported fact;
- unavailable fact;
- insufficient history;
- stale fact where the authoritative freshness rule applies;
- invalid/non-finite fact;
- contradictory or duplicate authoritative records where ambiguity affects Snapshot identity;
- malformed repository/persistence input.

No silent repair, interpolation, provider substitution, fabricated numeric value or synthetic market observation is permitted.

## 8. Specialist Independence

The Snapshot is the sole Stage-1 input boundary.

Tests must demonstrate that:

- a specialist output cannot become an authoritative Snapshot input;
- specialist ordering cannot change Snapshot identity;
- adding/removing another specialist's output cannot change the Snapshot;
- no import/dependency path is introduced that makes one specialist consume another specialist output.

Do not implement the specialist execution engine in this Step.
