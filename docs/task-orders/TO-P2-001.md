# TO-P2-001 — Provider Boundary & Acquisition Contracts

**Task Order SID:** `TO-P2-001`  
**Phase:** `PH-P2`  
**Step:** `STEP-P2-001`  
**Issuer:** `ROL-V2-001` CONTROL / REVIEWER  
**Recipient:** `ROL-V2-002` PRODUCER / ARCHITECT-BUILDER  
**Status:** AUTHORIZED TO EXECUTE

## Authority

This Task Order is issued under the Project Owner's explicit authorization to establish Phase 2 and the existing General Continuation / Phase Progression Authority. It is bounded by the Constitution, `DOC-V2-ARCH-001` RATIFIED / FROZEN, the Master Registry, and the Phase 2 definition in `docs/phases/PH-P2.md`.

## Objective

Establish the provider-neutral acquisition boundary that all Phase 2 market-data providers must use. The result must be precise enough for Binance and MEXC adapters to be implemented later without duplicating or redefining provider semantics.

## Required Repository Work

1. Establish the governed provider abstraction boundary and stable logical identities required by this Step.
2. Define provider-neutral acquisition contracts/envelopes for the Phase 2 acquisition scope.
3. Preserve and reuse existing canonical V2 contracts; do not create competing canonical market-data contracts.
4. Define the minimum provider-neutral fields required for provenance, provider identity, instrument identity, event type, event time, receive time, source sequence where applicable, and acquisition status.
5. Define explicit acquisition/degradation states for unavailable, stale, invalid, disconnected, rate-limited, sequence-gap, and insufficient provider data conditions where applicable. Do not fabricate market values or synthetic success states.
6. Define provider capability/error semantics so one provider's failure cannot silently corrupt another provider or authoritative state.
7. Define deterministic serialization / identity requirements sufficient for replay, deduplication, and later normalization without embedding provider-specific behavior into canonical contracts.
8. Define the boundary between raw/staging acquisition output and the Phase 3 Validation / Normalization / Data Quality Engine. Phase 2 must not absorb Phase 3 validation ownership.
9. Add deterministic unit tests for the new contracts/abstractions, including positive, missing, invalid, degraded, provenance, and identity/sequence cases that are material to the boundary.
10. Update only the governed Repository artifacts required for this Step and preserve Stable-ID traceability. Do not silently alter frozen architecture, existing canonical contracts, or unrelated components.

## Explicit Non-Scope

- Binance or MEXC network/runtime implementation.
- Provider credentials or secret acquisition.
- Live market-data connections.
- Database migrations for provider runtime.
- Collector production deployment.
- Phase 3 validation/normalization implementation.
- Phase 4 quantitative/structure computation.
- AI intelligence/specialist layers.
- Trading, capital, custody, leverage, or account control.
- V1 changes.

## VPS / Runtime Boundary

For `STEP-P2-001`, VPS involvement is **INSPECTION ONLY**.

CONTROL has already established the relevant starting baseline on the actual V2 VPS. No provider runtime, external market connection, migration, restart, service activation, or persistent runtime change is authorized by this Task Order.

The Producer must not claim VPS execution or runtime verification from this Task Order.

## Required Tests

The Producer must run the deterministic tests relevant to the changed contracts/abstractions and report the exact commands and actual results. Tests must not require external market access unless explicitly justified by the implementation and separately authorized; the primary contract suite must remain reproducible.

## Definition of Done

All of the following must be true:

- provider-neutral acquisition boundary exists;
- acquisition contracts/envelopes are explicit and deterministic;
- provenance and provider isolation semantics are explicit;
- degradation/error states are explicit and do not fabricate data;
- Phase 3 ownership boundary is explicit;
- required tests pass with actual evidence;
- no unauthorized provider runtime activity occurred;
- no frozen architecture, Stable ID, or canonical contract was silently changed;
- Build Report `BR-P2-001` is produced with actual changes, tests, deviations, and open questions.

## Producer Reporting Requirements

The Build Report must identify:

- actual implementation state;
- exact test commands and outputs/results;
- any deviations from this Task Order;
- any Open Questions;
- any Known Design Considerations that are non-blocking;
- and explicit confirmation that no VPS/provider runtime execution was performed under this Task Order.
