## 1. Required outcome

Resolve the remaining authoritative upstream fact/evidence population gap preventing genuine acceptance of `STEP-P5-006`.

Independent runtime acceptance of `TO-P5-006` established that the specialist runtime path itself executes correctly, but the governed VPS does not contain the required authoritative Group-C fact population:

- S-03 has no persisted `VOLUME_SMA`, `RVOL`, `VOLUME_SPIKE`, or `VOLUME_CLIMAX` facts;
- S-17 has no authoritative `BTCUSDT` 15m Volume Profile session on the required primary acceptance boundary;
- only one historical 1h profile session was present;
- the accepted S-17 trade lineage previously exposed NULL venue context;
- no silent substitution of `persisted_at` for authoritative `knowledge_time` is permitted.

The required result is genuine real-data population of the existing P4 fact surfaces, not documentation or reclassification.

`TO-P2-015` is the immediate owning-boundary prerequisite for explicit Binance trade venue evidence.

This Task Order becomes **AUTHORIZED TO EXECUTE** only after `TO-P2-015` is independently VERIFIED / COMPLETE, unless CONTROL establishes by authoritative evidence that the venue prerequisite has already been resolved without further implementation.

## 4. Required fact population

For the governed `BTCUSDT` primary slice:

### S-03 source facts

Establish persisted authoritative quantitative facts for the required 15m primary timeframe, with eligible 1h/4h context where the existing Phase-5 acceptance boundary requires/supports them.

The resulting rows must:

- originate from real authoritative closed canonical candles;
- use the existing P4 `volume_sma`, `rvol`, `volume_spike`, and `volume_climax` engines;
- preserve deterministic identity;
- expose authoritative `knowledge_time`;
- satisfy `knowledge_time <= as_of`;
- preserve instrument/timeframe/provenance/venue semantics;
- remain append-only and replay-safe.

Insufficient history must remain explicit. No fabricated numeric value is acceptable.

### S-17 source facts

Establish an authoritative persisted `volume_profile_sessions` surface for `BTCUSDT` at the primary 15m acceptance timeframe.

Where eligible 1h/4h context is actually supported by authoritative input data, establish the corresponding profiles without inventing missing history.

The runtime must:

- consume real persisted `CanonicalTrade` lineage;
- use the existing explicit-interval `VolumeProfileEngine`;
- preserve source-record lineage;
- resolve `knowledge_time` only from authoritative evidence;
- preserve explicit venue context after `TO-P2-015`;
- persist through the existing append-only table;
- support direct read-back and deterministic replay.

Prior-session POC comparison is required only when the authoritative persisted history contains the required prior session. A single-session result must remain truthful and must not be promoted to two-session evidence.

## 7. Evidence semantics

Every accepted fact must preserve:

- real source record identity;
- identity hash;
- event time;
- authoritative knowledge time;
- instrument;
- timeframe;
- venue;
- source family;
- no-lookahead relative to `as_of`.

For S-03, the existing P4 indicator `knowledge_time = event_time` semantic authority remains applicable.

For S-17, knowledge time must remain derived from authoritative P3 quality-evidence lineage as implemented; it must never be substituted with `persisted_at`.

## 8. Edge cases / Rule-5

Cover at minimum:

- missing volume facts;
- insufficient candle history;
- invalid/non-finite volume inputs;
- wrong instrument/timeframe;
- missing/contradictory venue evidence;
- missing trade lineage;
- empty profile interval;
- insufficient profile trades;
- exactly one session;
- multiple sessions;
- missing POC/VAH/VAL/HVN/LVN;
- deterministic replay;
- duplicate identity with differing content;
- no-lookahead / `knowledge_time > as_of`;
- persistence/read-back;
- append-only UPDATE/DELETE protection.

No synthetic or unjustified fallback evidence is permitted.
