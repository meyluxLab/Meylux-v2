# TO-P2-002 — Binance Acquisition Adapter

**Task Order SID:** `TO-P2-002`  
**Phase:** `PH-P2`  
**Step:** `STEP-P2-002`  
**Issuer:** `ROL-V2-001` CONTROL / REVIEWER  
**Recipient:** `ROL-V2-002` PRODUCER / ARCHITECT-BUILDER  
**Status:** AUTHORIZED TO EXECUTE

## Authority

This Task Order is issued under the Project Owner's standing General Continuation / Phase Progression Authority, following verified completion of `TO-P2-001` and `STEP-P2-001` under `AR-P2-AUDIT-001`. It is bounded by the Constitution / Architectural Invariants, `DOC-V2-ARCH-001` RATIFIED / FROZEN, the Master Registry, the Phase 2 definition in `docs/phases/PH-P2.md`, `STEP-P2-002`, the approved provider-neutral acquisition boundary, and `GOV-BOUNDARY-001`.

This Task Order commissions implementation only within the already-established `STEP-P2-002` boundary. It does not redesign Phase 2, redefine the provider-neutral contract, or authorize any subsequent Phase 2 Step.

## Objective

Implement the Binance acquisition adapter against the approved provider-neutral acquisition boundary for the Phase 2 acquisition scope, including the required REST/bootstrap and live-stream capabilities, bounded retry/reconnect behavior, provider isolation, and evidence-compatible telemetry.

The adapter must consume the existing provider-neutral acquisition contracts and keep Binance-specific wire/API behavior behind the provider adapter boundary. It must not create a competing canonical market-data contract or move Phase 3 validation/normalization ownership into Phase 2.

## Authoritative Scope

The implementation shall remain within the established `STEP-P2-002` scope:

1. Binance provider adapter implementation against the approved provider-neutral acquisition boundary.
2. Required Binance REST/bootstrap acquisition capabilities within the existing acquisition architecture.
3. Required Binance live-stream acquisition capabilities within the existing acquisition architecture.
4. Bounded retry/reconnect behavior appropriate to the established provider boundary and implementation context; do not silently introduce unbounded retry, uncontrolled reconnect loops, or architecture-level policy changes.
5. Provider isolation so Binance failure cannot silently corrupt MEXC, other provider state, or authoritative canonical state.
6. Evidence-compatible telemetry for acquisition/provider state and relevant failure/degradation behavior, using existing observability/governance conventions where applicable.
7. Correct mapping of Binance provider-specific payloads/events into the existing provider-neutral acquisition boundary.
8. Preserve provenance, provider identity, instrument identity, event type, event/receive timestamps, source sequencing where applicable, acquisition status, and deterministic identity/serialization semantics already established by `TO-P2-001`.
9. Preserve the explicit Phase 2 raw/staging boundary and do not absorb Phase 3 validation/normalization ownership.
10. Add or update governed implementation/tests/traceability artifacts required to demonstrate the adapter behavior and its isolation from unrelated providers.

Provider-specific API/wire details are implementation concerns inside this boundary and must not leak into canonical provider-neutral contracts.

## Contracts / Interfaces

The Producer must use and preserve the already-established provider-neutral acquisition boundary, including the governed acquisition contracts and component identified by:

- `CMP-P2-001` — Provider-Neutral Acquisition Boundary;
- `CTR-P2-001` — `AcquisitionEnvelope` Provider-Neutral Acquisition Contract;
- the ratified/frozen `DOC-V2-ARCH-001` architecture;
- `PH-P2` / `STEP-P2-002` requirements.

Do not create a competing acquisition envelope, provider-neutral contract, or alternate canonical identity model.

If an apparent requirement cannot be satisfied without changing a ratified/frozen architecture, canonical contract, Stable ID, or higher-level governance rule, stop that part and report it as an Open Question / escalation rather than silently changing the higher-level artifact.

## Provider Credentials / Secrets

No credentials, API keys, tokens, cookies, secrets, or private authentication material may be committed to the Repository, Build Report, tests, logs, screenshots, or other governed artifacts.

If Binance credentials are required for authorized development/runtime validation, use only the project's approved secret-handling mechanism. Never substitute plaintext repository configuration for approved secret handling.

Public market-data acquisition that does not require credentials may be used only within the authorized development/validation context.

## Development / VPS Boundary

`GOV-BOUNDARY-001` applies.

The Producer may use the authorized Development Workspace, including a VPS-hosted Development Workspace, for implementation and development validation **within this Task Order**.

For `STEP-P2-002`, VPS deployment/configuration is authorized only as part of the governed development/validation workflow and only within the explicit actions below:

- inspect the current authorized V2 development environment;
- install/use development dependencies required for the adapter;
- modify project implementation/configuration required by this Task Order;
- run authorized development tests and integration validation;
- perform non-production adapter/runtime validation where necessary to demonstrate the Task Order's acceptance criteria.

The Producer is not authorized by this Task Order to perform production deployment, uncontrolled infrastructure changes, unrelated service changes, V1 activity, or any financial/trading operation.

Live Binance connectivity may be used only for authorized acquisition validation of this Step. It is not authorization for trading, account control, order placement, withdrawals, transfers, leverage, custody, or capital activity.

Any runtime operation must remain bounded, observable, and evidence-producing. Do not leave uncontrolled long-running processes or provider sessions running after validation unless separately authorized by the applicable runtime workflow.

3. REST/bootstrap mapping and failure handling tests;
4. live-stream parsing/mapping and lifecycle tests where technically applicable;

8. provenance/time/sequence/status propagation tests applicable to Binance events;
9. credential/secret non-leakage checks where applicable;
10. compilation/static validation for changed code.

External-network tests must be clearly distinguished from deterministic local tests. If live Binance validation is unavailable, report the limitation explicitly and do not represent unexecuted live validation as passed.
