## 2. Authoritative starting facts

TO-P2-012 and AR-P2-AUDIT-012 established, without implementation authorization, that:

1. MEXC Spot exposes REST order-book snapshots.
2. MEXC Spot aggregated WebSocket depth exposes provider version fields `fromVersion` and `toVersion`.
3. MEXC documents the continuity invariant `fromVersion == previous toVersion + 1` and requires reinitialization from a REST snapshot when continuity is broken.
4. Outdated updates are to be ignored relative to the established snapshot/version state according to provider semantics.
5. Existing Meylux `AcquisitionEnvelope` can preserve provider provenance, event time, received time, source sequence and payload without creating a new upstream truth contract.
6. Existing `CanonicalOrderBook` is a provider-neutral immutable snapshot contract containing instrument, timestamp, bids, asks and provenance, while deliberately excluding provider sequence identifiers.
7. Existing MEXC acquisition already has REST order-book acquisition and Protobuf depth decoding paths.
8. MEXC candle finality remains unavailable and MEXC public trade-stream completeness remains unavailable. This Task Order does not change either disposition.

Provider documentation remains the authority for the MEXC version-chain semantics. A bounded live observation may support implementation diagnostics but MUST NOT be elevated into a universal provider guarantee.

## 3. Required implementation objective

When separately activated, Producer MUST implement only the bounded capability needed to:

- acquire an authoritative MEXC Spot REST order-book snapshot;
- consume MEXC aggregated WebSocket depth updates;
- validate and maintain the provider-documented version chain;
- detect continuity gaps and stale/outdated updates;
- reinitialize/recover from a REST snapshot when continuity cannot be maintained;
- preserve provider provenance and replayability;
- expose only an order-book state whose semantic claims are directly supported by the provider mechanism and existing contracts.

The implementation MUST remain provider-isolated and MUST NOT create unsupported market, trade, candle or historical-completeness facts.

## 5. Provider-semantic requirements

The implementation MUST preserve the following provider facts exactly as established:

### 5.1 REST snapshot

- Snapshot acquisition MUST retain the provider's snapshot version/update identifier where available at the acquisition/evidence boundary.
- Snapshot depth limits MUST be treated as actual provider limits, not as evidence of unlimited market depth.
- Snapshot timestamp/update identity MUST not be confused with candle finality or trade completeness.

### 5.2 Aggregated WebSocket depth

- Decode and preserve `fromVersion` and `toVersion`.
- Treat them as provider version-chain evidence, not as trade IDs or candle sequence IDs.
- Preserve absolute quantity semantics for each price level as documented by MEXC.
- Reject or route malformed version values explicitly; never coerce invalid provider state into continuity.

### 5.3 Continuity

For an established local state with previous accepted version `V_prev`, an incoming update beginning at `fromVersion` is contiguous only when:

`fromVersion == V_prev + 1`.

If the update begins after the required next version, the local state has a continuity gap and MUST be reinitialized from a fresh REST snapshot.

If the update is entirely older than the established state, it MUST be treated as stale/outdated and MUST NOT regress canonical state.

The implementation MUST define behavior for boundary cases such as:

- exact contiguous update;
- update overlapping the snapshot version range where provider semantics permit integration;
- stale update;
- gap;
- malformed/non-numeric version;
- version regression;
- equal-version duplicate;
- restart with no local state;
- REST snapshot failure during required recovery;
- WebSocket disconnect/reconnect;
- repeated gap/recovery cycles.

No arithmetic overflow, string-ordering error, lexical comparison, or silent integer coercion may create false continuity.

## 6. Snapshot/update reconstruction boundary

If a stateful local reconstruction mechanism is implemented, it MUST:

1. establish a valid REST snapshot baseline;
2. establish the snapshot's provider version;
3. consume only provider depth updates that can be proven contiguous relative to that baseline;
4. apply absolute quantity updates deterministically;
5. remove levels when provider quantity semantics require removal;
6. preserve strict price ordering and canonical order-book invariants;
7. reinitialize on an authoritative continuity gap;
8. prevent stale updates from regressing state;
9. expose no state as authoritative while required recovery is unresolved;
10. preserve enough acquisition/provenance evidence to reproduce the accepted state transition sequence within the actual retained evidence boundary.

The algorithm MUST NOT assume that a bounded snapshot plus a finite live stream establishes the full or unlimited global market book.

## 7. Canonicalization boundary

The canonicalization boundary MUST distinguish:

- raw/provider evidence;
- an internally reconstructed provider-consistent local order-book state;
- a provider-neutral `CanonicalOrderBook` snapshot.

A reconstructed order book may be canonicalized only when all required semantic predicates for the existing contract are satisfied.

The implementation MUST NOT canonicalize:

- a state with an unresolved continuity gap;
- a state derived from malformed or ambiguous version metadata;
- a state whose required snapshot/recovery failed;
- a stale state falsely presented as current;
- a state whose provider identity/instrument identity cannot be established;
- a state requiring unsupported historical reconstruction.

If the existing contract cannot represent the necessary semantic distinction without inventing a new canonical fact, STOP and escalate to CONTROL.

## 8. Historical versus live applicability

The implementation MUST explicitly distinguish:

**Live / streaming applicability**
- REST snapshot + aggregated WebSocket depth continuity is the primary supported reconstruction mechanism.

**Historical applicability**
- No claim of unlimited or complete historical order-book reconstruction is authorized.
- Existing REST snapshot data may be preserved as provider evidence within its actual documented scope.
- Historical replay is valid only over evidence actually retained and semantically sufficient to reconstruct the requested state.
- Absence of retained updates MUST NOT be interpreted as proof of a complete historical book.

## 9. Provenance, identity and replay

The implementation MUST preserve:

- `AcquisitionEnvelope` identity and deduplication semantics;
- provider identity and adapter provenance;
- instrument identity;
- event time and received time distinctions;
- provider source sequence/version evidence;
- deterministic serialization;
- canonical identity semantics;
- replay/idempotency behavior;
- append-only raw evidence boundaries;
- existing G-4 identity material.

A provider version field MUST NOT be repurposed as a trade identifier, candle sequence, or generic global event ID.

No historical canonical rewrite is authorized.

## 10. Failure and recovery requirements

Producer MUST explicitly handle and test:

- REST snapshot unavailable;
- REST snapshot malformed;
- missing snapshot version;
- WebSocket disconnect;
- malformed depth payload;
- malformed `fromVersion` / `toVersion`;
- `fromVersion` equal to previous `toVersion + 1`;
- `fromVersion` greater than required next version;
- stale `toVersion`;
- duplicate update;
- overlapping snapshot/update boundary;
- recovery snapshot failure;
- repeated recovery failure;
- provider instrument mismatch;
- invalid/non-positive prices or quantities;
- empty or structurally invalid order-book state;
- bid/ask crossing;
- replay of identical snapshot/update evidence;
- restart with and without recoverable local state.

Failures MUST be explicit, deterministic and evidence-preserving. No fabricated fallback order-book state is permitted.
