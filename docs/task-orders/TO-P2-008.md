## 3. Objective

Establish, with implementation-level evidence and deterministic tests, the Binance provider-side finality/closed-candle semantics required to support a governed P5 `knowledge_time` bridge without:

- transferring Binance semantics to MEXC by analogy;
- substituting `event_time`, `persisted_at`, `received_at`, or another operational timestamp for `knowledge_time`;
- fabricating historical finality;
- changing frozen architecture without formal change control;
- silently changing existing G-4 identity material;
- reopening prior Phase 2 closure.

The implementation must preserve the distinction:

`event_time` ≠ `knowledge_time` unless the authoritative upstream contract explicitly establishes their equality.

## 4. Authoritative Semantic Basis

The implementation must be grounded in actual authoritative Binance evidence, not inference.

The current CONTROL evidence baseline includes Binance official documentation showing that the Spot kline WebSocket payload contains:

- `k.T` = kline close time;
- `k.x` = whether the kline is closed;
- repeated updates to the current kline.

The Producer must independently inspect the repository's current Binance adapter, normalization/canonicalization path, persistence boundary, and existing tests before changing code.

The Producer must not treat REST historical kline `close_time` alone as equivalent to a provider-declared closed/finality flag unless the authoritative provider contract and the repository's governed semantics explicitly justify that conclusion.

## 5. Authorized Scope

### 5.1 Provider-side Binance finality semantics

Implement the minimum bounded provider-side representation necessary to preserve authoritative Binance candle finality/closure evidence through the existing provider abstraction.

Required behavior:

1. Preserve the provider's explicit closure/finality signal where the provider exposes it.
2. Preserve the provider's candle close boundary separately from event/receipt timing.
3. Make the semantic relationship between provider finality and canonical `is_closed` explicit and deterministic.
4. Preserve provenance sufficient for later P3/P4/P5 evidence resolution.
5. Reject or classify malformed, contradictory, missing, or unsupported finality signals explicitly; never silently coerce them to `closed=true`.
6. Ensure replay/idempotency does not turn a previously non-final observation into an authoritative final fact without the provider evidence required by the contract.
7. Ensure no lookahead is introduced.
8. Keep provider-specific behavior behind the existing provider abstraction.

### 5.2 Historical/backfill boundary

Historical REST klines do not expose the same WebSocket `x` field. Therefore:

- the Producer must not fabricate a historical `x=true`;
- the Producer must not infer provider finality merely from the fact that a kline is returned by REST;
- any historical `knowledge_time` eligibility must be represented according to an explicitly documented, authoritative semantic rule;
- if no authoritative historical finality mechanism is available within the existing boundary, historical availability must remain explicitly bounded rather than silently upgraded.

The existing persisted Binance population must not be rewritten merely to make the new representation pass tests.

If a historical backfill path is implemented, it must prove its semantic basis, provenance, deterministic replay behavior, and identity impact.

### 5.3 G-4 / identity boundary

Default requirement: **preserve existing canonical identity material and canonical bytes**.

The Producer must explicitly inspect:

- `CanonicalCandle` identity construction;
- canonical serialization;
- persistence identity/hash fields;
- any payload included in identity material;
- downstream quantitative identity dependencies.

If implementation can expose the required finality/knowledge-time evidence additively without changing established identity material, that is the preferred bounded-additive route.

If the required semantic change necessarily modifies frozen identity material, canonical bytes, a frozen contract, or another G-4 criterion, **STOP THAT PART** and report the exact conflict. Do not redesign or silently migrate identity.
