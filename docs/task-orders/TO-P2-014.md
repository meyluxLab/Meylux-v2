# TO-P2-014 — Governed Binance Spot Trade Acquisition Capability for P5-006

**Task Order SID:** `TO-P2-014`  
**Project:** MEYLUX V2

**Producer Role:** PRODUCER / ARCHITECT-BUILDER — `ROL-V2-002`

**Status:** **AUTHORIZED TO EXECUTE**  
**Governance Class:** Bounded post-closure capability delivery / PRQ-2 trade prerequisite  
**Owner Authorization Basis:** Project Owner Phase-5 scope decisions recorded in `PH-P5.md`, specifically PD-1/PD-2, authorize real public market-data acquisition within the governed Phase-5 scope; this Task Order routes only the demonstrated trade prerequisite required by `STEP-P5-006` through the owning P2 boundary.

## 1. Authority and lifecycle boundary

`PH-P2` remains `CLOSED / VERIFIED` and `STEP-P2-006` remains `COMPLETE / VERIFIED`. This Task Order is a bounded post-closure capability delivery under the existing P2 ownership boundary. It does not reopen, invalidate, or silently modify historical Phase-2 closure.

The current Phase-5 gate requires `PRQ-1 Group-C` and the trade portion of `PRQ-2`. `PRQ-1 Group-C` is independently established under `TO-P4-014 / AR-P4-022`. The existing governed evidence also proves one real Binance Spot TRADE lineage through raw acquisition → P3 quality → CanonicalTrade and through the P4 S-17 acceptance, but that evidence does not by itself establish a reusable governed trade-acquisition capability. The repository still records the production `collector` as a foundation service that does not instantiate the acquisition adapters.

This Task Order resolves that remaining prerequisite at its owning P2 boundary. It does not authorize `STEP-P5-006` specialist implementation.

## 2. Required outcome

Establish a real, bounded, provider-isolated Binance Spot trade acquisition path capable of producing authoritative persisted TRADE evidence for the `STEP-P5-006` Group-C acceptance boundary.

The required endpoint is not merely source-code support or a single manually prepared trade row. The endpoint is an executable governed acquisition path with:

- actual Binance Spot trade acquisition;
- explicit instrument scope for the Phase-5 initial instruments `BTCUSDT` and `SOLUSDT`, without silent substitution;
- bounded runtime execution;
- raw acquisition persistence and read-back;
- correct provider-neutral `AcquisitionEnvelope` semantics;
- P3 quality/canonical propagation where the existing contracts require it;
- deterministic identity and replay/idempotency;
- provenance preservation;
- sufficient real trade evidence to support downstream P4 Volume Profile execution without synthetic or candle-substituted input.

If the actual repository contract shows that only a narrower instrument slice is technically necessary to establish the STEP-P5-006 gate, Producer must surface that evidence to CONTROL rather than silently broadening or narrowing the authorized outcome.

## 3. Existing facts to preserve

CONTROL's current SoT assessment establishes:

1. P2 owns acquisition; P5 must not build acquisition capability itself.
2. Existing Binance Spot acquisition supports public trade retrieval through the provider adapter.
3. Existing P3/P4 evidence contains one real Binance Spot TRADE lineage, proving that the upstream contracts can carry a real trade into CanonicalTrade.
4. The running `collector` boundary has historically been a foundation service and did not instantiate the Phase-2 acquisition adapters or persist acquisition events.
5. The P5-006 S-17 acceptance requires real trade input and must not substitute candles.
6. No synthetic trade history, fabricated provider facts, or manual canonical insertion is permitted as a substitute for acquisition capability.
7. Existing `CanonicalTrade`, `AcquisitionEnvelope`, provenance, identity, append-only persistence, and P3 quality contracts are authoritative and must be preserved unless a real conflict is escalated to CONTROL.

These facts are starting evidence, not a prescribed implementation mechanism.

## 4. Authorized scope

Producer retains implementation-level design authority inside this boundary and shall determine the minimum correct implementation necessary to achieve the outcome.

The implementation may include, where actually required:

- completing the existing P2 collector/runtime acquisition boundary for Binance Spot trades;
- invoking the existing Binance provider adapter through the provider-neutral acquisition contract;
- bounded polling/bootstrap or live acquisition behavior supported by the existing provider contract;
- raw acquisition persistence;
- propagation through the existing P3 quality/canonical path;
- deterministic identity/deduplication and replay behavior;
- configuration required to select the authorized instruments without hard-coded semantic shortcuts;
- tests and diagnostics required to prove the complete path.

No new provider abstraction is authorized.

No new canonical truth layer is authorized.

No new trade mathematical definition is authorized.

No P5 specialist implementation is authorized.

## 5. Required semantic boundaries

The implementation MUST preserve:

- provider identity versus venue identity;
- instrument identity;
- event time versus received/knowledge/persistence time;
- provider provenance;
- source identity and replay semantics;
- existing `AcquisitionState` / quality lifecycle semantics;
- append-only raw/canonical persistence;
- fail-closed behavior for malformed or unavailable provider observations;
- no NaN/Inf or fabricated fallback values;
- deterministic serialization and identity;
- no silent provider or instrument substitution.

The implementation MUST NOT infer trade completeness beyond the evidence actually established.

A finite retrieval window MUST NOT be represented as complete historical trade history unless the provider semantics and retained evidence justify that claim.

If the provider/runtime cannot establish a required semantic predicate, the result must remain explicit (`UNAVAILABLE`, `INSUFFICIENT`, or the applicable existing state) rather than being promoted by inference.

## 6. Runtime / VPS boundary

This Task Order authorizes Producer implementation and bounded runtime diagnostics within the governed development workspace where required.

CONTROL may separately authorize and execute SentinelX runtime acceptance once the Producer Build Report identifies the exact deployed/runtime boundary requiring verification.

No production, trading, execution, custody, account, capital or financial operation is authorized.

- malformed payload;
- missing trade ID/provider identity;
- invalid instrument;
- invalid price;
- invalid quantity;
- invalid event time;
- unavailable provider response;
- HTTP/API error;
- rate-limit response;

- empty response;

No test fixture may be used as production evidence.
