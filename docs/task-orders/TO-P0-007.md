# MEYLUX V2 — TASK ORDER

## TO-P0-007 — AI Continuation Protocol

**Task Order ID:** `TO-P0-007`
**Phase:** `PH-P0`
**Step:** `STEP-P0-006` — AI Continuation Protocol
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)
**Status:** AUTHORIZED TO EXECUTE
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-003`
**Predecessor:** `STEP-P0-005` — Governance / Artifact Protocol (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-006 — AI Continuation Protocol`: establish and reconcile the authoritative AI-to-AI continuation and resumability protocol so that a successor AI can reconstruct Meylux V2 project state from governed repository artifacts and evidence without relying on hidden chat memory.

## 2. Authoritative Boundary

`ADR-ARCHITECTURE-001` establishes `STEP-P0-006` as the sixth Phase 0 Step. It is now the sole activated Step. Later Steps remain defined but are not authorized.

The work shall use the existing V2 governance, continuity, registry, checkpoint, evidence, and Source-of-Truth mechanisms. This Step is a continuity/reconciliation task, not permission to redesign the architecture or create a competing governance subsystem.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the current authoritative continuity/bootstrap artifacts, checkpoint/state artifacts, registry, governance protocol, role boundaries, ratified decisions, and relevant architecture/constitutional requirements.
2. Determine whether the current repository artifacts provide sufficient authoritative information for a successor AI to reconstruct, at minimum:
   - project identity;
   - architecture status;
   - governance state;
   - current Phase/Step;
   - active Task Order;
   - open blockers/questions;
   - Stable IDs and registry state;
   - ratified decisions;
   - deferred decisions where applicable;
   - verified evidence and evidence state;
   - next authorized action.
3. Identify material continuity gaps, contradictions, stale state, ambiguous authority, missing traceability, or resumability weaknesses that affect reliable AI-to-AI continuation.
4. Reconcile only those continuity records required by the Step objective and supported by authoritative evidence.
5. Preserve the repository as the Source of Truth and ensure chat/model memory is not required as an authoritative state dependency.
6. Preserve lifecycle distinctions and distinguish current authoritative state from historical evidence, claims, assumptions, and unresolved matters.
7. Ensure continuation state does not silently authorize future Steps, runtime activity, V1/VPS activity, market/trading/capital activity, or architecture ratification/freeze.
8. Preserve Stable IDs and historical records. Do not invent speculative identities where authority is absent; retain `IDENTITY UNCONFIRMED` where still applicable.
9. Use the delegated Build Report allocation procedure under `ADR-GOVERNANCE-003` when a Build Report is required. Allocate only the next BR for this currently authorized Task Order.
10. Produce a Build Report containing actual evidence and preserving the distinction between Producer production and CONTROL verification.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- ratify or freeze the Master Architecture;
- alter the ratified Phase 0 sequence;
- activate future Steps or issue future Task Orders;
- replace the Source-of-Truth model with chat/model memory;
- create a competing continuity, governance, checkpoint, registry, or approval subsystem;
- silently rewrite or invalidate historical evidence;
- alter or reinterpret existing Stable IDs;
- self-approve, self-audit, self-verify, close the Step, or ratify governance decisions;
- modify V1, V1 VPS/runtime, market providers, trading, capital, fund-transfer, or provider-runtime state;
- fabricate continuity, execution, verification, or project-state evidence;
- make unrelated architecture, governance, registry, environment, implementation, or runtime changes.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-005` remains `COMPLETE / VERIFIED` with `AR-P0-AUDIT-009` as its completion audit;
- continuation/resumability requirements are addressed within the authorized Step objective;
- successor-AI reconstruction can be grounded in governed repository artifacts and evidence rather than hidden chat memory;
- current state, active work, verified history, unresolved matters, and next authorized action are distinguishable;
- authority and lifecycle boundaries remain explicit;
- existing Stable IDs, historical records, ratified decisions, and constitutional boundaries remain preserved;
- any unresolved continuity conflict is explicitly recorded rather than silently resolved;
- no later Step is activated;
- no unauthorized runtime, V1/VPS, market, trading, capital, or provider-runtime activity occurred;
- Build Report evidence is actual and remains unverified until independent CONTROL audit.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the resulting Build Report and repository changes before any Step completion transition. If accepted, the next Step may be activated only through the existing sequential governance process.
