# TO-P2-003 — MEXC Acquisition Adapter

**Task Order SID:** `TO-P2-003`  
**Phase:** `PH-P2`  
**Step:** `STEP-P2-003`  
**Issuer:** `ROL-V2-001` CONTROL / REVIEWER  
**Recipient:** `ROL-V2-002` PRODUCER / ARCHITECT-BUILDER  
**Status:** AUTHORIZED TO EXECUTE

## Authority

This Task Order is issued under the Project Owner's standing General Continuation / Phase Progression Authority, following verified completion of `TO-P2-002` and `STEP-P2-002` under `AR-P2-AUDIT-002`. It is bounded by the Constitution / Architectural Invariants, `DOC-V2-ARCH-001` RATIFIED / FROZEN, the Master Registry, the Phase 2 definition in `docs/phases/PH-P2.md`, `STEP-P2-003`, the approved provider-neutral acquisition boundary, and `GOV-BOUNDARY-001`.

This Task Order commissions implementation only within the established `STEP-P2-003` boundary. It does not redesign Phase 2, redefine the provider-neutral contract, or authorize `STEP-P2-004` or any later Step.

## Objective

Implement the MEXC acquisition adapter against the approved provider-neutral acquisition boundary for the Phase 2 acquisition scope, including the required public REST/bootstrap and live-stream capabilities, bounded retry/reconnect behavior, provider isolation, and evidence-compatible telemetry.

The adapter must consume the existing provider-neutral acquisition contracts and keep MEXC-specific wire/API behavior behind the provider adapter boundary. It must not create a competing canonical market-data contract or move Phase 3 validation/normalization ownership into Phase 2.

## Authoritative Scope

1. MEXC provider adapter implementation against the approved provider-neutral acquisition boundary.
2. Required MEXC REST/bootstrap acquisition capabilities within the existing acquisition architecture.
3. Required MEXC live-stream acquisition capabilities within the existing acquisition architecture.
4. Bounded retry/reconnect behavior; no unbounded retry, uncontrolled reconnect loops, or architecture-level policy changes.
5. Provider isolation so MEXC failure cannot silently corrupt Binance, other provider state, or authoritative canonical state.
6. Evidence-compatible telemetry for acquisition/provider state and relevant failure/degradation behavior, using existing observability/governance conventions where applicable.
7. Correct mapping of MEXC provider-specific payloads/events into the existing provider-neutral acquisition boundary.
8. Preserve provenance, provider identity, instrument identity, event type, event/receive timestamps, source sequencing where applicable, acquisition status, and deterministic identity/serialization semantics established by `TO-P2-001`.
9. Preserve the explicit Phase 2 raw/staging boundary and do not absorb Phase 3 validation/normalization ownership.
10. Add or update governed implementation/tests/traceability artifacts required to demonstrate adapter behavior and isolation from unrelated providers.

Provider-specific API/wire details are implementation concerns inside this boundary and must not leak into canonical provider-neutral contracts.

## Development / VPS Boundary

`GOV-BOUNDARY-001` applies.

The Producer may use the authorized Development Workspace, including a VPS-hosted Development Workspace, for implementation and development validation within this Task Order.

Authorized development/validation actions are limited to inspection of the V2 development environment, required development dependencies, project implementation/configuration changes required by this Task Order, authorized tests/integration validation, and bounded non-production adapter/runtime validation.

Live MEXC connectivity may be used only for authorized acquisition validation of this Step. It is not authorization for trading, account control, order placement, withdrawals, transfers, leverage, custody, or capital activity.
