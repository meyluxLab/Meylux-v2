## 1. Objective

Operationalize and persist, at the existing P4-owned boundary, the already-approved deterministic quantitative facts required specifically by the intended `STEP-P5-004 — Group A: Technical, Multi-Timeframe, Volatility` acceptance boundary.

The required outcome is genuine downstream usability of authoritative P4 facts, not a P5 workaround.

The resulting P4 capability must provide reproducible persisted evidence for the Group-A fact surface across the governed primary and higher timeframes, while preserving explicit insufficient/unavailable states where the existing deterministic engines cannot legitimately produce a fact from the supplied closed-candle history.

This Task Order is the bounded Route-A continuation authorized by the Project Owner. It does not authorize the full PRQ-1 package for later P5 groups.

## 4. Exact Required Capability

The Producer shall determine and implement the smallest coherent additive P4 capability that makes the following fact surface persistently available to the downstream P5 Group-A boundary:

### S-01 — Technical facts

For each governed timeframe actually supplied to the P4 runtime, persist deterministic outputs from the already-ratified P4-002 indicator library for the Group-A technical surface, including where applicable:

- EMA using the existing authoritative P4 configuration boundary;
- RSI-14;
- MACD 12/26/9;
- ADX-14;
- Bollinger Bands 20/2 and bandwidth.

The implementation must not silently introduce new mathematical definitions or new configuration semantics.

### S-06 — Multi-Timeframe facts

Persist the same authoritative fact families independently by timeframe so that a downstream consumer can resolve facts for the primary timeframe and eligible higher timeframes without recomputation inside P5.

Higher-timeframe eligibility remains bounded by the existing no-lookahead rule:

`close_time <= primary knowledge boundary`

No future or post-boundary candle may contribute to an eligible fact.

### S-08 — Volatility facts

For each supplied timeframe, expose the existing deterministic P4 volatility functions required by the Group-A boundary, including:

- ATR-14;
- historical volatility using its existing ratified definition and valid-window constraints;
- ATR percentile using its existing ratified definition and lookback constraints;
- Bollinger bandwidth;
- any existing volatility expansion ratio required by the authoritative Group-A fact vocabulary, only if its current P4 implementation/semantic authority supports it without new mathematics.

A metric with insufficient history must be persisted or represented through the existing explicit P4 calculation-status/reason mechanism rather than fabricated.

## 5. Persistence Boundary

The implementation must use the existing authoritative P4 quantitative persistence boundary.

At minimum, the persisted evidence must preserve independently:

- logical fact family;
- deterministic identity;
- symbol/instrument;
- timeframe;
- event/reference time;
- authoritative knowledge_time;
- provenance/source reference;
- calculation/configuration version;
- calculation status;
- reason/insufficient-history state;
- deterministic payload/value representation.

The already-established `knowledge_time` semantics from `TO-P4-010) remain authoritative and must not be weakened.

Do not create a competing P5 truth store.

Do not substitute `persisted_at`, `logged_at`, receipt time, wall-clock time, or snapshot time for fact-level knowledge time.

## 6. Historical Data Boundary

No historical value may be fabricated.

Existing historical rows may remain unchanged where their fact surface is not supported by preserved evidence.

If the required Group-A facts can only be reconstructed deterministically from preserved canonical historical candles, the Producer may implement deterministic reconstruction through the existing P4 calculation/persistence path, provided:

- identity remains deterministic;
- replay is reproducible;
- no unsupported timestamp is introduced;
- no destructive UPDATE/DELETE is used against append-only historical facts;
- the resulting evidence clearly distinguishes newly established facts from legacy rows that remain unavailable.

If the existing persisted historical population is insufficient for a requested metric/timeframe, the result must remain explicitly `INSUFFICIENT_HISTORY` / unavailable as appropriate.

## 7. Multi-Timeframe Runtime Boundary

The existing P4 candle-close worker contract remains the runtime entry boundary.

The implementation must ensure that higher-timeframe observations actually reach the deterministic P4 orchestration/persistence path rather than merely existing in a direct unit-test API.

The implementation must reject:

- timeframe-key/candle-timeframe mismatch;
- mixed instruments;
- incomplete candles;
- non-monotonic or overlapping candle sequences;
- higher-timeframe candles closing after the primary knowledge boundary.

No lookahead is permitted.

## 8. Identity and Provenance

Identity must remain deterministic and stable for the same authoritative fact.

Repeated processing of the same fact must be idempotent.

The implementation must not:

- infer venue from provider identity;
- alter existing identity algorithms without explicit need and impact assessment;
- discard source provenance;
- merge facts from different timeframes into one identity;
- silently overwrite a previously persisted fact.

If a new payload component must participate in identity to distinguish materially different facts, the Producer must document the reason and impact in the Build Report; any protected contract/identity change requiring formal change control must stop that affected portion.

## 9. Failure / Insufficient Evidence Semantics

The implementation must preserve existing deterministic status vocabulary.

Required negative cases include, where applicable:

- missing timeframe;
- malformed timeframe;
- incomplete candle;
- insufficient history;
- invalid input;
- contradictory timeframe mapping;
- post-boundary higher-timeframe candle;
- duplicate/replayed persistence;
- malformed or non-UTC temporal data;
- missing provenance;
- invalid numeric output;
- non-finite Decimal values.

No fallback value may be invented to make a specialist input appear complete.
