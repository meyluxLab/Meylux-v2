## 1. Objective

Establish the real authoritative P4-owned Group-B market-structure fact surface required by the intended `STEP-P5-005`.

This is an outcome-driven additive continuation. It is not a request for a schema-only change, fixture, summary row, documentation reclassification, or P5-side recreation.

CONTROL's pre-activation evidence establishes that the existing deterministic `MarketStructureEngine` already produces individual `StructuralEvent` facts, but the current quantitative orchestration/persistence boundary retains only structure summary information and does not operationally persist the individual event/zone fact surface required by Group-B.

The required result is therefore to carry the existing ratified P4 structural facts through the authoritative persistence/runtime boundary, preserving their semantics and evidence lineage.

## 2. Required Outcome

The implementation must establish, through real authoritative runtime evidence:

1. individual structural-event persistence, not only an `ORCHESTRATION` summary;
2. authoritative persistence of structure-bearing zones required by Group-B;
3. symbol and timeframe isolation;
4. preservation of event location, confirmation time, and knowledge time as distinct semantics where defined;
5. authoritative structural `knowledge_time`;
6. deterministic identity and source/member identity required by `DOC-P4-002`;
7. provenance and explicit venue context where authoritative evidence exists; unresolved venue must remain explicit rather than inferred;
8. deterministic historical reconstruction from preserved canonical candles;
9. real closed-candle runtime propagation through the P4 orchestration/persistence boundary;
10. no-lookahead selection using `knowledge_time <= snapshot.as_of`;
11. deterministic replay/idempotency;
12. append-only protection of historical structural facts;
13. explicit insufficient-history / unavailable outcomes where evidence is insufficient;
14. complete persisted event/zone read-back;
15. preservation of existing P4/G-4 closure evidence.

## 3. Semantic and Architectural Authority

The Producer shall use the existing ratified P4 market-structure engine and `DOC-P4-002` semantics as the source of truth.

This Task Order does **not** authorize:

- new swing/BOS/CHOCH/MSS mathematics;
- new FVG/Order Block/Breaker/liquidity definitions;
- changes to equality or `UNCONFIRMED` semantics;
- replacement of existing Decimal policy;
- a competing P5 truth store;
- P5 recomputation of P4 facts;
- silent changes to frozen contracts, Stable IDs, or architectural invariants.

If implementation reveals a genuine semantic, contract, identity, or architectural conflict, the affected portion must be surfaced to CONTROL for the applicable governance/change-control route.

## 4. Event Persistence Boundary

The authoritative persistence path must preserve individual structural facts, directly or through an unambiguous canonical representation, including as applicable:

- deterministic record identity;
- symbol/instrument;
- timeframe;
- event type;
- event location;
- confirmation time;
- knowledge time;
- direction;
- structural level;
- lower/upper bounds;
- lifecycle;
- structural state;
- source/member identity;
- prior structural state;
- semantic/calculation version;
- status/reason;
- provenance;
- explicit venue context;

## 5. Zone Persistence Boundary

The existing P4-owned `market_structure_zones` persistence family must become operationally reachable for zone-bearing facts produced by the existing structural semantics.

Zone persistence must preserve, as applicable:

- deterministic identity;
- symbol;
- timeframe;
- zone type;
- formation/event time;
- authoritative knowledge time;
- lower/upper bounds;
- direction;
- lifecycle;
- source event identity;
- provenance;
- venue context;
- semantic/calculation version;
- status/reason;
- deterministic payload.

Historical facts remain append-only. Lifecycle changes must be represented according to the governed event/transition model rather than destructive mutation.

## 6. Temporal / Knowledge-Time Requirements

The implementation must preserve the distinction among:

- event location;
- confirmation time;
- knowledge time;
- snapshot `as_of`;
- database `persisted_at`.

It must not silently set structural `knowledge_time` from persisted-at, receipt time, migration time, process time, or an inferred wall-clock.

Required evidence includes:

- exact `knowledge_time == snapshot.as_of` is eligible;
- post-boundary facts are excluded;
- event location earlier than knowledge time remains distinguishable;
- confirmation later than event location remains distinguishable;
- malformed/non-UTC temporal input is rejected;
- higher-timeframe evidence known after the primary snapshot boundary is excluded.

## 7. Historical and Per-Timeframe Coverage

Facts must remain independently identifiable by governed timeframe.

The implementation must establish a deterministic route using preserved canonical candles and the existing P4 engine, covering the Group-B evaluation boundary required for 15m primary structure and eligible 1h/4h structure.

No synthetic candles or fabricated structural facts are permitted.

Insufficient history must remain explicit rather than being converted into guessed structure.

## 8. Runtime Operationalization

Unit-test-only access is insufficient.

The implementation must establish an implementation-equivalent real path:

`canonical closed candles -> P4 quantitative orchestration -> existing structural analysis -> authoritative persistence`

The runtime path must be reproducible and idempotent.

Producer must not create a P5 structure calculator to compensate for this P4 persistence gap.

## 9. Provenance / Venue

Venue must not be inferred from symbol syntax, provider naming, adapter names, or other heuristics.

Where authoritative lineage establishes one venue, it may be persisted.

Where lineage is missing, malformed, or contradictory, the result must remain explicitly unresolved according to the existing semantic vocabulary.

Structural facts must remain traceable to their authoritative candle lineage.

## 10. Append-Only / Identity / Replay

The implementation must prove:

- deterministic identity;
- materially distinct facts receive distinct identity;
- required source/member identity is retained;
- repeated identical processing is idempotent;
- identical authoritative input produces the same logical fact set;
- application-role UPDATE and DELETE of authoritative history are rejected;
- lifecycle transitions are represented as governed facts rather than historical mutation.

No destructive historical migration is authorized.
