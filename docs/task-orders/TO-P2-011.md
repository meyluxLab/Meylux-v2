## 1. Purpose and lifecycle boundary

This Task Order exists to establish one empirical prerequisite before any later Owner decision about a possible Trade→Candle architecture for MEXC Spot.

## 2. Sole investigation objective

Determine, with authoritative documentation and real evidence where required, whether the MEXC public Spot trade/deals stream provides a genuinely monotonic and gap-detectable trade sequence identifier per instrument, and whether MEXC REST trade history provides sufficient deterministic historical depth to reconcile any detected gap.

The investigation must answer all of the following:

1. Whether the authoritative current MEXC Spot WebSocket trade/deals stream exposes a trade identifier (`tradeId` or equivalent).
2. Whether that identifier is unique per instrument.
3. Whether it is **strictly monotonically increasing per instrument**, rather than merely present or generally increasing.
4. Whether MEXC explicitly documents uniqueness/monotonicity, or whether those properties can be independently established from real live observations with reproducible evidence.
5. Whether a sequence discontinuity such as ID 100 followed by ID 105 can be deterministically classified as a real gap rather than an artifact of batching, ordering, sharding, filtering, reconnect behavior, or provider semantics.
6. Whether the authoritative REST trade-history endpoint can retrieve the exact missing identifier range or otherwise provide authoritative reconciliation for a detected gap.
7. What REST historical depth, pagination semantics, time/limit constraints, and rate limits apply to that reconciliation.
8. Whether the same trade has a stable and consistent identifier across WebSocket and REST paths.
9. Whether MEXC documents or evidence establishes exceptions such as resets, shard-local numbering, non-sequential assignment, reuse, ordering ambiguity, or other behavior that invalidates continuity-based gap detection.
10. Any additional provider-side property materially relevant to proving trade-stream completeness.

## 3. Required disposition

The Build Report MUST conclude with exactly one of:

`MEXC_TRADE_SEQUENCE_INTEGRITY: ESTABLISHED`

or

`MEXC_TRADE_SEQUENCE_INTEGRITY: UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`

No third disposition, invented certainty, or implicit intermediate verdict is permitted.

`ESTABLISHED` requires sufficient evidence for the complete mechanism, not merely evidence that a trade ID field exists.

## 4. Evidence standard

The investigation MUST distinguish:

- provider-documented guarantees;
- provider schema/endpoint behavior;
- repository implementation facts;
- independently observed live behavior;
- inference or interpretation.

A property must not be described as provider-guaranteed merely because examples appear monotonic.

For live observation, evidence MUST record the actual observation context, including provider endpoint/stream, instrument, relevant time window, observed identifier values, ordering, and enough raw/provider response detail to make the conclusion reproducible. Do not fabricate sample IDs, timestamps, gaps, depths, rate limits, or cross-path matches.

If live-provider access is unavailable, the Build Report must say so and must not promote documentation gaps into an established empirical guarantee.

## 5. Provider documentation investigation

Producer MUST inspect the current authoritative MEXC documentation/schema for:

- Spot public WebSocket trade/deals stream;
- Spot REST trade-history endpoint;
- trade identifier definition and type;
- identifier uniqueness scope;
- ordering/monotonicity guarantees;
- pagination and retrieval semantics;
- maximum retrievable history/depth;
- limits per request;
- rate limits;
- symbol/instrument scoping;
- reconnect/batching/order semantics;
- any documented reset, sharding, partitioning, or identifier-reuse behavior.

Third-party material may be used only as supplementary evidence and must not be presented as authoritative MEXC documentation.

## 6. Live empirical investigation

Where authorized provider access is available, Producer MUST perform a bounded read-only observation of the current MEXC Spot trade/deals stream and REST trade history.

The observation should establish, as far as the available window permits:

1. identifier presence and type;
2. identifier uniqueness for one instrument;
3. ordering of successive observations;
4. whether identifiers increase monotonically;
5. whether increments are necessarily one or may legitimately skip values;
6. whether duplicate/repeated messages occur;
7. whether message batching or delivery ordering differs from trade ordering;
8. whether reconnect/subscription behavior changes identifier continuity;
9. whether the same observed trades can be located through REST;
10. whether WebSocket and REST expose identical identifiers for the same trade.

**Important:** observing no gap in a finite sample does not establish global continuity. Such an observation may support consistency but cannot by itself prove a provider guarantee.

No attempt may be made to manufacture a gap by modifying, filtering, reordering, or synthesizing provider data.

## 7. Gap-detection analysis

Producer MUST determine whether a missing identifier can be distinguished from a legitimate sequence property.

If IDs appear as, for example, 100 then 105, the investigation must establish whether 101–104 necessarily represent missing trades, or whether the provider permits legitimate non-consecutive identifiers.

The analysis MUST consider:

- duplicates;
- out-of-order delivery;
- batching;
- reconnects;
- subscription boundaries;
- multiple consumers/connections;
- per-symbol scope;
- provider-side partitioning/sharding;
- legitimate non-consecutive IDs;
- resets/restarts;
- filtering or aggregation at the provider;
- delayed messages.

A simple `next_id == previous_id + 1` test is not sufficient unless MEXC evidence establishes that this continuity invariant is authoritative.

## 8. REST backfill/reconciliation analysis

Determine whether REST trade history can authoritatively retrieve a range identified by a suspected gap.

The report must establish, from actual documentation and/or real responses:

- endpoint identity;
- request parameters;
- pagination behavior;
- maximum page size;
- earliest/latest retrievable history under the documented/current mechanism;
- whether retrieval can be bounded by trade ID, time, or both;
- whether the endpoint can return the exact suspected missing range;
- rate-limit constraints;
- whether rate limits or depth constraints can make reconciliation incomplete;
- whether REST can return trades old enough to reconcile a delayed WebSocket gap.

If the endpoint cannot deterministically retrieve an identifier range, that limitation must be explicit.

## 9. Cross-path identity consistency

The investigation MUST determine whether a trade observed on WebSocket can be matched to the same trade on REST using authoritative fields.

At minimum inspect the provider's available:

- trade ID;
- symbol/instrument;
- price;
- quantity/size;
- side/aggressor metadata where available;
- provider timestamp;
- any other provider-defined identity field.

Do not assume that matching price/time/quantity proves identity if MEXC supplies a stronger identifier.

The required question is whether **the same provider trade has the same stable trade identifier across WebSocket and REST**.

## 10. Exception analysis

Producer MUST explicitly investigate any evidence of:

- identifier reset;
- identifier reuse;
- per-symbol versus global numbering;
- per-connection or per-stream numbering;
- shard/partition-local numbering;
- non-consecutive legitimate assignment;
- out-of-order delivery;
- duplicate identifiers for distinct trades;
- one trade represented by multiple messages;
- REST/WebSocket identifier mismatch;
- historical endpoint truncation;
- undocumented behavior that materially weakens completeness proof.

Where evidence is inconclusive, disposition must remain `UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`.

- missing messages;
- out-of-order WebSocket delivery;
- reconnect/re-subscription;

- provider-side batching.

Do not invent provider behaviors merely to create test cases.
