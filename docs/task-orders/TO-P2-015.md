# TO-P2-015 — Binance Spot Trade Evidence Venue Semantics for Group-C Acceptance

**Task Order SID:** `TO-P2-015`  
**Project:** MEYLUX V2  
**Issuing Role:** CONTROL / REVIEWER — `ROL-V2-001`  
**Producer Role:** PRODUCER / ARCHITECT-BUILDER — `ROL-V2-002`  
**Boundary:** `PH-P2` post-closure corrective dependency for `PH-P5 / STEP-P5-006`  
**Status:** **AUTHORIZED TO EXECUTE**  
**Governance Class:** Bounded post-closure prerequisite-resolution Task Order under `ADR-GOVERNANCE-014`  
**Owner Authorization Basis:** Project Owner full-resolution authorization dated 2026-10-06.

## 1. Required outcome

Resolve the authoritative venue-evidence gap exposed by independent `TO-P5-006` runtime acceptance.

The current Binance Spot trade acquisition path can produce real canonical trade lineage, but the accepted trade lineage does not carry an explicit authoritative `venue` / `venue_context`. The downstream P4 Volume Profile resolver correctly refuses to infer venue from `provider_id`, and P5 EvidenceRef requires an authoritative venue.

The required outcome is therefore:

> Real Binance Spot TRADE acquisition must carry an explicit, source-scoped `BINANCE` venue value at the authoritative acquisition evidence boundary, and that value must survive the existing P2 → P3 quality/canonical lineage without provider-to-venue inference.

This is a semantic evidence correction, not a reclassification of the existing NULL value.

## 2. Evidence basis

CONTROL has independently established:

- `TO-P2-014 / AR-P2-AUDIT-014` establishes real Binance Spot trade acquisition and canonical persistence, but its accepted trade payload does not establish an explicit venue value.
- `TO-P4-014 / AR-P4-022` established the P4 Volume Profile operational path, while the real accepted S-17 lineage persisted `venue_context = NULL`.
- `TO-P5-006` runtime acceptance therefore cannot satisfy the P5 EvidenceRef venue requirement by inference.
- The current Binance candle adapter already demonstrates the authoritative source-scoped pattern by attaching `"venue": "BINANCE"` to Binance kline payload context; the trade boundary must be evaluated against the same existing architecture rather than inventing a downstream mapping.

## 3. Producer discretion

Producer retains implementation-level design authority within this boundary.

Determine the exact smallest authoritative acquisition/evidence correction required after inspecting:

- Binance adapter implementation;
- AcquisitionEnvelope and provenance contracts;
- P3 normalization/quality evidence mapping;
- canonical trade persistence;
- existing venue semantics and tests.

Do not prescribe or introduce a new provider abstraction, venue registry, second truth source, downstream inference rule, or P5 workaround.

If the existing contracts cannot carry the required explicit venue without changing a frozen contract or architecture, stop only that sub-part at the exact authoritative conflict and report it to CONTROL. Do not silently infer venue.

## 4. Required implementation and evidence

At minimum establish:

1. real Binance Spot trade payloads carry explicit source-scoped venue context;
2. provider identity remains distinct from venue identity;
3. P3 quality evidence preserves the explicit venue;
4. canonical trade lineage preserves the explicit venue where the existing contract exposes it;
5. malformed/missing/contradictory venue context fails closed;
6. unauthorized or non-Binance provider data cannot be relabeled as Binance;
7. deterministic identity remains stable and replay remains idempotent;
8. existing canonical trade semantics remain unchanged;
9. no historical evidence is rewritten silently;
10. repository regression/CI evidence passes;
11. real provider-derived runtime evidence demonstrates the corrected lineage;
12. direct persistence/read-back confirms the venue value at the authoritative evidence boundary.

No synthetic or manually fabricated trade evidence may be used as acceptance evidence.
