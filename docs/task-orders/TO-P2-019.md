## 2.1 CONTROL preliminary public-documentation leads — NOT QUALIFICATION

These official-documentation leads were identified during CONTROL's continuation check. They are starting points for Producer's independent route-by-route assessment, not a provider selection or a qualification conclusion:

- **Bybit Funding:** the official V5 Funding Rate History page documents `GET /v5/market/funding/history`, covers linear and inverse product types, uses a symbol such as BTCUSDT, returns `fundingRate` and `fundingRateTimestamp`, and limits each page to 200 records: https://bybit-exchange.github.io/docs/v5/market/history-fund-rate
- **Bybit OI:** the official V5 Open Interest page documents `GET /v5/market/open-interest`, covers USDT/USDC/inverse contracts, and explicitly states that the unit for `openInterest` is BTC for BTCUSDT linear and USD for BTCUSD inverse. It documents interval-based history and cursor pagination: https://bybit-exchange.github.io/docs/v5/market/open-interest
- **Bybit ticker fields:** the official ticker schema includes `openInterest`, `fundingRate`, `basis`, and `basisRate`; however, this initial review did not establish that a direct non-empty Basis fact with the required semantics is guaranteed for the exact BTCUSDT/SOLUSDT perpetual products. Treat this as an evidence lead only: https://bybit-exchange.github.io/docs/v5/market/tickers
- **OKX:** the official API guide documents perpetual funding-rate history and OI response fields `oi` (contracts), `oiCcy` (coin quantity), and `oiUsd` (USD value). This may help assess unit semantics, but this initial review did not establish a direct Basis route for the exact required instruments: https://app.okx.com/docs-v5/zh

Producer must retrieve and assess the official sources directly, preserve product/instrument identity, and determine whether each candidate supplies all three required facts together. Do not promote a field name or the existence of an endpoint into complete route qualification.

## 3. Required investigation

### 3.1 Revisit prior unresolved evidence gaps

For Binance USDⓈ-M, search the official documentation/schema references for an explicit authoritative definition of:
- current `openInterest` unit and calculation basis;
- historical `sumOpenInterest` unit and calculation basis;
- `sumOpenInterestValue` currency/valuation basis and relationship to `sumOpenInterest`;
- official documentation explicitly covering the exact SOLUSDT USDⓈ-M product for Funding, current/historical OI, and Basis.

Do not infer units from examples, field names, numerical magnitudes, SDK types, third-party commentary, or COIN-M definitions. If no authoritative definition can be found in permitted evidence, preserve the gap and list exactly what source would resolve it.

### 3.2 Discover and evaluate additional provider/product candidates

Search for additional plausible provider/product routes without preselecting a provider. For each candidate, use official public documentation as the authority and inspect the actual product family and instrument identity. Candidate discovery is not qualification.

For each candidate that merits evaluation, establish separately:
- Funding endpoint/fields, units/sign meaning, event timestamp, history/cadence and exact symbol/product scope;
- current and historical OI endpoints/fields, explicit units and valuation basis, event/period timestamp and coverage;
- direct provider-supplied Basis endpoint/field, exact definition, units, timestamp and coverage;
- whether all three metrics belong to the same compatible exact instrument/product family for BTCUSDT and/or SOLUSDT;
- provenance/raw fields and failure/contradiction semantics documented by the provider;
- whether existing frozen contracts can represent the facts truthfully without unit inference, cross-product substitution, or protected-boundary changes.

A provider with only one or two metrics is not a complete route. A derived Basis proxy is not accepted unless an authoritative, already-governed definition and its inputs are established; do not create a new derivation or contract amendment.

### 3.3 Existing repository and S-04 boundary

Use the current repository Source of Truth and cite exact current paths/Blob SHAs where relevant. Keep separate:
- provider documentation capability;
- repository implementation facts;
- generic contract representability;
- an actually established end-to-end canonical-to-quality-evidence joined read-back path;
- runtime/listing/availability, which remain unverified and outside this Task Order.

No contract field, generic temporal validation function, or component-level persistence function alone proves S-04 `AVAILABLE_PERSISTED`. Preserve `available_persisted_claim: NONE` unless authoritative current evidence actually changes that claim through an independently authorized and verified boundary. This investigation itself cannot change runtime evidence.
