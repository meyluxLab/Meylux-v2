## Authority

This Task Order is issued under the Project Owner's standing General Continuation / Phase Progression Authority following verified completion of `TO-P2-004 / STEP-P2-004` under `AR-P2-AUDIT-004`. It is bounded by the Constitution / Architectural Invariants, `DOC-V2-ARCH-001` RATIFIED / FROZEN, the Master Registry, `PH-P2`, `STEP-P2-005`, and `GOV-BOUNDARY-001`.

This Task Order authorized only the implementation defined for `STEP-P2-005`. It did not authorize `STEP-P2-006`, Phase 3/4 work, production deployment, or trading/account/capital activity.

## Objective

Harden the Phase 2 acquisition boundary for dual-provider operational behavior while preserving the verified provider-neutral contracts, provider isolation, bounded resource behavior, and existing architecture.

## Authoritative Scope

1. Provider isolation and degraded-provider behavior across the existing Binance and MEXC acquisition paths.
2. Rate-limit and provider-failure handling using existing canonical acquisition states and bounded retry/recovery semantics.
3. Bounded reconnect and recovery behavior, including explicit lifecycle termination and no uncontrolled retry loops.
4. Resource-growth controls for collector, queues, persistence recovery, and related acquisition buffers within existing architecture.
5. Evidence-compatible observability for operational health, provider degradation, rate limiting, reconnect/recovery, backpressure, and terminal failure states using existing conventions.
6. Operational recovery and health checks required to demonstrate bounded behavior without redesigning the queue, persistence, or provider contracts.
7. Deterministic/local tests for newly hardened behavior and regression protection for the verified P2-001 through P2-004 acquisition boundary.
8. Bounded development/runtime validation where available and explicitly authorized by the existing VPS boundary; no uncontrolled long-running process may remain after validation.
9. Required repository traceability and Build Report `BR-P2-005`.

## Contracts / Architecture

Preserve without silent modification:
- `CMP-P2-001` — Provider-Neutral Acquisition Boundary;
- `CTR-P2-001` — `AcquisitionEnvelope` Provider-Neutral Acquisition Contract;
- verified Binance and MEXC adapter behavior except for minimal, evidence-backed corrections required by this Step;
- existing PostgreSQL/TimescaleDB persistence architecture;
- existing Redis/ARQ queue architecture and conventions;
- `DOC-V2-ARCH-001` and Phase 2 ownership boundaries.

Do not move Phase 3 validation/normalization or Phase 4 quantitative computation into Phase 2. Do not redesign provider contracts, queue architecture, or frozen governance.

If a requirement cannot be satisfied without changing a ratified/frozen contract, architecture, Stable ID, or higher-level governance rule, stop that part and report an Open Question / escalation.
