## 1. Required outcome
Establish a deterministic, reproducible and diagnostically sufficient Docker evidence path for the already-verified P3-009 PostgreSQL capability.
The required result is not merely a green CI status. The actual P3-009 PostgreSQL evidence path must either:
1. execute successfully and reproducibly in the Docker Foundation workflow; or
2. expose a demonstrated external/environmental condition with sufficient captured evidence to support an explicit legitimate disposition.
A repeated failure with hidden SQL/process diagnostics is not an acceptable final evidence state.

## 2. Direct evidence requiring resolution
CONTROL inspected current-mainline Docker Foundation runs after the TO-P4-011 merge:
- Run `37015633194` / attempt 1 — Docker Foundation `FAILURE`;
- Run `37015641046` / attempt 2 — Docker Foundation `FAILURE`;
- Run `37017079269` / main after PR #57 merge — Docker Foundation `FAILURE`.
In all three, the failing step is `Re-run PostgreSQL-backed P3/P5 evidence path`.
The P3-009 test fails during `setUpClass` while applying migrations inside its ephemeral PostgreSQL container.
The current test implementation invokes subprocesses with `capture_output=True` and then raises `CalledProcessError` without emitting the captured PostgreSQL stderr/stdout. Consequently, the CI record proves the failure boundary but does not preserve the underlying SQL/process diagnostic.
CONTROL also observed that the same P3-009 PostgreSQL suite passes in CI Core, including current correction-cycle evidence, demonstrating that the failure is not established as a deterministic P3-009 semantic defect.
The root cause is therefore **not yet authoritatively established**.

## 3. Required investigation
Producer shall inspect the complete affected path, including at minimum:
- `tests/test_p3_009_postgresql.py`;
- `.github/workflows/ci-docker.yml`;
- current Docker image/runtime assumptions;
- Timescale/PostgreSQL startup/readiness behavior;
- ephemeral container lifecycle;
- migration execution and ordering;
- Docker socket / host Docker execution context;
- environment variables and credentials used by the test;
- current `main` CI behavior;
- the successful Core execution path for comparison.
Determine whether the failure mechanism is a test/harness defect, readiness/race condition, Docker execution-context issue, PostgreSQL/Timescale initialization condition, migration defect, repository implementation defect, or another reproducible environmental condition.
Do not infer the cause from the exit code alone.

## 4. Root-cause correction standard
If the harness is defective, correct the underlying harness behavior without weakening the P3-009 assertions.
Examples of acceptable correction directions include, only if justified by the actual investigation:
- preserving actionable subprocess diagnostics;
- establishing a stronger readiness boundary;
- eliminating a race in ephemeral PostgreSQL startup;
- making the Docker evidence environment deterministic;
- correcting an invalid migration/test invocation assumption.
Do not suppress the P3-009 test, convert a failure to a skip, remove PostgreSQL assertions, bypass migrations, ignore stderr, hard-code against one successful fixture, weaken append-only/identity/provenance/knowledge-time/concurrency/persistence assertions, or split the test so the real evidence path is no longer exercised.

## 5. Acceptance evidence
The corrected boundary must provide evidence for:
1. deterministic startup/readiness of the ephemeral PostgreSQL environment;
2. ordered application of the complete required migration set;
3. successful execution of the actual P3-009 PostgreSQL test suite;
4. real persistence/read-back behavior;
5. quality-state semantics including unavailable acquisition;
6. `knowledge_time = received_at` where applicable;
7. identity/provenance/lineage;
8. EvidenceRef resolution;
9. duplicate/idempotent behavior;
10. concurrent duplicate persistence;
11. append-only/security boundaries;
12. reproducibility across at least the applicable Docker Foundation path and Core comparison;
13. actionable diagnostics if any failure occurs;
14. preservation of historical P3-009 semantics and current-mainline integration.
A passing single rerun without establishing reproducibility is insufficient.

## 6. Scope boundary
This Task Order does not authorize reopening `PH-P3`, reopening `STEP-P3-007` or `STEP-P3-008`, redesigning P3 quality semantics, changing `PRQ-4` semantics, changing P4 mathematics, modifying migration 0008, implementing PRQ-1 beyond separately authorized P4 boundaries, P5-004 implementation, PRQ-2/3, MEXC/Futures/Forex acquisition, trading/execution/capital/custody, or unrelated refactoring.
