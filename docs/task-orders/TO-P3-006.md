## 2. Objective

Establish deterministic cross-venue consistency and equivalence validation over validated canonical representations produced by P3-005, so that data from different venues is compared only when the underlying market semantics are sufficiently equivalent and aligned.

The result is a validation/equivalence decision and evidence, not an opportunity decision.

Required conceptual flow:

`Validated Canonical Venue A + Validated Canonical Venue B`
`→ semantic equivalence checks`
`→ temporal/freshness alignment`
`→ market-data consistency checks`
`→ explicit equivalence / inconsistency / insufficient-evidence result`

## 3. Authorized Scope

Implement the P3-006 cross-venue validation boundary using existing validated canonical contracts and the provider-neutral semantics established by P3-001 through P3-005.

The Architect/Producer must design the implementation as a reusable provider-independent comparison capability rather than a Binance/MEXC-specific one-off, while remaining within the currently authorized provider evidence boundary.

The authorized comparison dimensions include, where supported by existing canonical contracts/evidence:
- canonical instrument identity;
- base and quote assets;
- venue identity;
- market type;
- contract type;
- contract/unit/multiplier semantics where explicitly available;
- timeframe compatibility;
- timestamp/event-time alignment;
- freshness/alignment state when explicit evidence is available;
- price and quote semantics;
- bid/ask sanity and ordering;
- quantity/unit compatibility;
- canonical order-book representation compatibility;
- candle interval and OHLC semantic compatibility where comparable;
- explicit lifecycle/availability state where represented by canonical data;
- provenance and source references required to reproduce the comparison.

The implementation must make comparison prerequisites explicit. A pair that cannot be established as semantically comparable must not be treated as equivalent merely because symbols or provider identifiers match.

## 4. Required Cross-Venue Semantics

1. **Semantic identity precedes comparison.** Ticker/symbol string equality alone is insufficient evidence of equivalence.
2. **Provider neutrality.** Comparison logic consumes canonical semantics and must not depend on provider wire fields unless those fields have already been explicitly promoted into canonical semantics by an authoritative contract.
3. **Determinism.** The same canonical inputs and governed comparison context must produce the same result and reason set.
4. **No fabrication.** Missing, stale, contradictory, unsupported, or insufficient evidence must produce an explicit non-equivalence/insufficient-evidence state as appropriate; never invent a value merely to complete a comparison.
5. **No silent coercion.** Incompatible market type, contract type, units, multiplier, timeframe, or other material semantics must not be silently coerced into equivalence.
6. **Temporal alignment is explicit.** Comparisons must account for event-time alignment and freshness using authoritative existing semantics/configuration; no hidden wall-clock dependency may be introduced into pure comparison logic.
7. **Market-data sanity remains a prerequisite.** Impossible or invalid canonical values are not repaired by P3-006 and must not be promoted through comparison.
8. **Provenance is preserved.** Each comparison result must retain enough source/context information to identify the canonical inputs and validation basis.
9. **Explainable result classification.** A comparison must expose the reason(s) supporting equivalence, inconsistency, incompatibility, or insufficient evidence rather than returning an opaque boolean only.
10. **Provider isolation.** A failure or unsupported mapping at one venue must not corrupt or silently alter the other venue's evidence.
11. **No opportunity inference.** A price difference, spread, or dislocation observed during validation is a market-data fact only. P3-006 must not classify it as an arbitrage/opportunity candidate, calculate executable opportunity, or enter the Venue Intelligence state ladder.
12. **No lookahead/future data.** Historical or replayable comparison behavior must use only evidence available at the comparison timestamp.

## 5. Architectural Optimization / Future Compatibility Requirements

The Architect must use legitimate engineering judgment to make P3-006 reusable and maintainable across future venues and downstream consumers without expanding scope into later Steps or Phases.

Where materially relevant, the design should provide:
- a provider-independent comparison interface;
- explicit comparison dimensions and result/reason taxonomy;
- deterministic ordering of checks/reasons where multiple failures exist;
- versionable comparison semantics so later governed changes are traceable;
- preservation of canonical provenance and input identity;
- clean separation between equivalence validation and later venue/opportunity analytics;
- test fixtures that can represent both equivalent and deliberately incompatible venue pairs;
- extension points for additional canonical venue types without embedding provider-specific assumptions;
- bounded computational/resource behavior appropriate to validation workloads;
- observability hooks appropriate to the implementation without creating a new operational subsystem owned by P3-007/P3-008;
- evidence structures that are straightforward for later AI-to-AI reconstruction and audit.

Future requirements may inform interfaces and boundaries, but future functionality must not be implemented merely because it is foreseeable.

## 6. Inputs and Outputs

### Inputs

- validated canonical instrument/candle/trade/order-book/derivatives representations as actually supported by the existing canonical contracts;
- upstream validation results and explicit data-quality context where available;
- venue/provenance identity from the canonical evidence;
- governed comparison configuration only where such configuration is already authorized or explicitly established within this Task Order.

### Outputs

A provider-neutral cross-venue comparison result that, as applicable, contains:
- comparison status/classification;
- compared canonical identities;
- dimensions checked;
- explicit reasons and failed prerequisites;
- alignment/freshness result when supported;
- consistency findings;
- provenance/source references;
- deterministic/version metadata needed for reproduction.

The exact schema must use existing contract/registry conventions and must not invent Stable IDs without corresponding actual implementation/evidence and governed registration.

## 8. Testing and Acceptance Criteria

The implementation is acceptable for CONTROL audit only if actual evidence demonstrates, as applicable to implemented coverage:

- equivalent canonical representations from two venues can be accepted when all required semantic prerequisites are satisfied;
- symbol equality without semantic equivalence is rejected or explicitly classified as insufficient evidence;
- base/quote mismatch is detected;
- market-type mismatch is detected;
- contract-type or unit/multiplier incompatibility is detected when those fields are available;
- timeframe incompatibility is detected;
- timestamp misalignment is detected according to the governed comparison semantics;
- stale/insufficient evidence cannot silently pass as equivalent;
- invalid or contradictory canonical evidence cannot be repaired or promoted by comparison;
- bid/ask and other applicable market-data sanity prerequisites are respected;
- provider-specific wire fields do not leak into the comparison contract;
- provenance/source references are retained;
- deterministic repeated comparisons produce identical result semantics;
- multiple failure reasons are deterministic and reproducible if the implementation exposes an ordered reason set;
- positive and negative Binance/MEXC-derived canonical fixtures are covered where those provider representations are actually supported by the implementation;
- at least one deliberately non-equivalent pair and one equivalent pair are covered;
- the implementation does not perform opportunity detection or executable-arbitrage analysis;
- existing Phase 3 regression tests remain passing.

Tests should include boundary conditions and explicit missing/unsupported evidence cases. Property-based or matrix-style tests are encouraged where they materially strengthen equivalence coverage without introducing unnecessary scope.
