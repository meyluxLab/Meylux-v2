# MEYLUX V2 — TASK ORDER

## TO-P0-010 — Dependency and Boundary Graph

**Task Order ID:** `TO-P0-010`  
**Phase:** `PH-P0`  
**Step:** `STEP-P0-009` — Dependency and Boundary Graph  
**Issuer:** CONTROL / REVIEWER (`ROL-V2-001`)  
**Recipient:** PRODUCER / ARCHITECT-BUILDER (`ROL-V2-002`)  
**Status:** `AUTHORIZED TO EXECUTE`  
**Authority:** `ADR-ARCHITECTURE-001`; `ADR-GOVERNANCE-001`; `ADR-GOVERNANCE-003`  
**Predecessor:** `STEP-P0-008` — Verification / Evidence / Gates (`COMPLETE / VERIFIED`)

## 1. Sole Objective

Execute `STEP-P0-009 — Dependency and Boundary Graph`: establish the authoritative V2 dependency and boundary graph required by the ratified Phase 0 sequence, using the reconciled architecture/governance/evidence state, without activating `STEP-P0-010` or authorizing runtime implementation.

## 2. Authoritative Boundary

`ADR-ARCHITECTURE-001` establishes `STEP-P0-009` as the ninth Phase 0 Step. It is now the sole activated Step. `STEP-P0-010` remains defined but is not authorized.

The work shall establish explicit, traceable relationships among relevant V2 architectural entities and boundaries while preserving the existing hierarchy, Stable IDs, provider isolation, persistence boundaries, governance authority boundaries, evidence boundaries, and V1 isolation.

## 3. Required Work

The Producer shall, within this Task Order only:

1. Inspect the authoritative Master Architecture V2, ratified Constitution, current Phase/Artifact registries, current checkpoint, ratified ADRs, Artifact Protocol, AI Continuation Protocol, Environment Contract, Verification Gate Definitions, Evidence Policy, V1 lesson controls, Open Questions, Deferred Decisions, and relevant existing dependency/boundary material.
2. Determine the authoritative dependency and boundary relationships required to make the V2 target architecture traceable, including where applicable:
   - architectural hierarchy and precedence;
   - Phase 0 / Step / Task Order lineage;
   - component and subsystem dependencies;
   - provider isolation boundaries;
   - authoritative persistence and cache/transport boundaries;
   - governance and role authority boundaries;
   - evidence and verification boundaries;
   - environment/runtime/deployment boundaries;
   - V1 isolation boundaries;
   - prohibited dependencies and prohibited authority crossings.
3. Identify material dependency cycles, missing edges, contradictory relationships, ambiguous ownership/authority, boundary leakage, stale references, or missing traceability.
4. Reconcile only the records required by the Step objective and supported by authoritative evidence.
5. Preserve the repository as Source of Truth and preserve existing lifecycle/evidence distinctions.
6. Preserve all existing Stable IDs. Do not invent identities where authority is absent.
7. Use the delegated Build Report allocation procedure under `ADR-GOVERNANCE-003` when a Build Report is required.
8. Produce a Build Report containing actual evidence and explicitly distinguishing Producer analysis/reconciliation from independent CONTROL verification.

## 4. Explicit Prohibitions

The Producer MUST NOT:

- ratify or freeze the Master Architecture;
- alter the ratified Phase 0 sequence;
- activate `STEP-P0-010` or issue future Task Orders;
- convert target architecture into implementation/execution claims without evidence;
- modify V1, V1 VPS/runtime, market providers, trading, capital, fund-transfer, or provider-runtime state;
- perform runtime deployment or physical environment execution;
- create a competing dependency, boundary, registry, governance, checkpoint, evidence, or architecture subsystem;
- alter, reassign, renumber, or reuse Stable IDs;
- silently rewrite or invalidate historical evidence;
- self-approve, self-audit, self-verify, accept, ratify, freeze, or close the Step;
- fabricate dependency, runtime, execution, test, verification, or repository state;
- make unrelated architecture, governance, registry, implementation, or runtime changes.

## 5. Acceptance Boundary

Acceptance requires actual evidence that:

- `STEP-P0-008` remains `COMPLETE / VERIFIED` with `AR-P0-AUDIT-012` as its completion audit;
- the authoritative dependency and boundary relationships required by the Step are explicitly represented or reconciled;
- dependencies, forbidden dependencies, ownership/authority crossings, and relevant boundary classes are traceable;
- material cycles, contradictions, missing relationships, or leakage are explicitly resolved or recorded as unresolved;
- existing Stable IDs and ratified constitutional/governance boundaries remain preserved;
- the distinction between target/design relationships and executed runtime relationships remains explicit;
- no later Step is activated;
- no unauthorized runtime, V1/VPS, market, trading, capital, or provider-runtime activity occurred;
- the Build Report remains unverified until independent CONTROL audit.

## 6. Completion Protocol

Producer completion is a Build Report state only. CONTROL will independently audit the resulting Build Report and repository changes before any Step completion transition. If accepted, `STEP-P0-010` may be considered for activation only through the existing sequential governance process.
