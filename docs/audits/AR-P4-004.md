## 3. Blocking findings

### F-01 — Continuity-gap UNCONFIRMED state is not maintained after the boundary

**Authority:** DOC-P4-002 §4 and §7.5; TO-P4-004 §4 and §6.

At a continuity break the engine sets `state = UNCONFIRMED` and clears structural references. On the immediately following continuous bar, the implementation falls through to `_derive_state(...)`; because the cleared collections are empty, that function returns `NEUTRAL`.

Therefore the implementation can produce:

`gap bar = UNCONFIRMED → next bar = NEUTRAL`

without any new valid post-gap structural evidence.

DOC-P4-002 requires `UNCONFIRMED` to persist after the continuity boundary until fresh valid evidence establishes a state. The focused gap test only asserts the boundary bar and does not detect the following-bar regression.

**Disposition:** BLOCKING.

### F-02 — Equality preventing HH/HL/LH/LL classification does not force UNCONFIRMED

**Authority:** DOC-P4-002 §6 and §7.5.

The implementation records an equal comparison by leaving the new classification as `None`. `_derive_state()` then maps a non-directional latest classification to `RANGE`.

Thus a semantic ambiguity explicitly governed as `UNCONFIRMED` can be reported as `RANGE`.

The existing tests contain no equal-swing state assertion.

**Disposition:** BLOCKING.

### F-03 — Required append-only invalidation/state-transition behavior is incomplete for structural-break facts

**Authority:** DOC-P4-002 §8, §9, §10 and §16.

The engine implements lifecycle invalidation for Order Blocks, Breakers and liquidity pools, but it contains no corresponding invalidation/state-transition mechanism for previously emitted BOS/CHOCH/MSS facts.

DOC-P4-002 explicitly requires historical structural facts to remain immutable and, where later evidence makes a BOS obsolete/invalid, to emit a distinct later fact referencing the original identity rather than deleting or mutating it. The same append-only discipline is part of the governed structural-event model.

The current implementation has no such structural-break invalidation path and the tests do not exercise it.

**Disposition:** BLOCKING.

### F-04 — Liquidity-pool identity does not implement the ratified member-identity requirement

**Authority:** DOC-P4-002 §14 and §15.

The specification requires the pool identity to include the ordered identities of its member swings. The implementation creates a pool using the second swing as `source`; the identity serializer does not include the ordered member identities as a pair.

This is deterministic but not semantically equivalent to the ratified identity contract.

**Disposition:** BLOCKING.

### F-05 — FVG lifecycle is not implemented as a monotonic lifecycle state machine

**Authority:** DOC-P4-002 §11 and §16.

The engine keeps an FVG in the active collection after emitting `PARTIALLY_MITIGATED`. Subsequent bars can emit additional `PARTIALLY_MITIGATED` facts without a new lifecycle transition. The implementation does not retain the current lifecycle state as part of the active object and does not enforce a single monotonic transition path.

The governed lifecycle is exactly:

`ACTIVE → PARTIALLY_MITIGATED → FULLY_MITIGATED`

with no repeated or backward lifecycle transitions.

The current FVG test only checks that both lifecycle labels occur; it does not assert ordered, single-step, monotonic transitions or terminal behavior.

**Disposition:** BLOCKING.

### F-06 — Required per-bar processing order is not implemented exactly as ratified

**Authority:** DOC-P4-002 §17.

The specification requires:

1. continuity;
2. swing confirmation;
3. classification;
4. state;
5. structural breaks;
6. OB/Breaker;
7. FVG;
8. liquidity;
9. official post-bar state.

The implementation evaluates FVG formation/lifecycle before Order Block/Breaker processing. That is an explicit divergence from the ratified processing order.

Even where current fixtures do not expose a result difference, the governed order itself is a required deterministic contract.

**Disposition:** BLOCKING.
