## 5. Numeric Policy Audit

**Result: PASS.**

CONTROL inspected `docs/quantitative/NUMERIC_POLICY_P4_001.md`, `src/meylux/quantitative/numeric.py`, and `src/meylux/quantitative/primitives.py`.

The implementation consistently uses Decimal at the P4-001 quantitative boundary, rejects float/bool and non-finite values, performs no implicit rounding, uses explicit ROUND_HALF_EVEN quantization, serializes in plain decimal notation, and uses exact golden comparison without epsilon tolerance.

The standard-deviation implementation places mean, variance and square-root inside an explicit high-precision Decimal context. This directly addresses the earlier observed precision defect and preserves exact comparison semantics.

The policy also correctly distinguishes safe classification of invalid mathematical inputs from explicit TypeError/ValueError for contract violations.

## 7. Invalid / Missing / Malformed Input Evidence

**Result: CORRECTION REQUIRED.**

TO-P4-001 §5 and §6 require coverage of missing, malformed and non-finite input behavior.

The implementation correctly rejects malformed/type-invalid numeric inputs through explicit TypeError/ValueError and rejects non-finite values. Empty history is covered as insufficient history.

However, the inspected `tests/test_quantitative_foundation.py` does not contain explicit malformed/missing-value cases such as a non-numeric object, `None`, or an invalid decimal string at the public primitive boundary.

The implementation behavior may be correct, but the required evidence is incomplete.

Required correction: add deterministic tests covering representative malformed/type-invalid and missing-value inputs for the public numeric boundary, while preserving the documented distinction between contract exceptions and CalculationResult INVALID_INPUT/INSUFFICIENT_HISTORY semantics.

## 8. Persistence Foundation Audit

**Result: IMPLEMENTATION PASS; execution-evidence correction required.**

CONTROL inspected `migrations/versions/0005_quantitative_foundation.sql` and the migration harness.

Verified from repository implementation:
- all five authorized quantitative output-family tables are created;
- context/result/version fields required by the Task Order are present;
- deterministic identity hashes are unique;
- volume-profile session ordering is constrained;
- append-only mutation rejection is attached to all five tables;
- application role receives SELECT/INSERT and explicit UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER revocation;
- backup role receives SELECT;
- migration 0005 is registered idempotently and ordered after 0004.

However, the fresh Docker evidence only directly asserts application privileges for `calculated_indicator_vectors`. The Build Report describes the privilege boundary as verified for the five-table set, but the cited runtime query does not independently demonstrate the same privilege matrix for the other four tables.

Required correction: add a deterministic runtime database verification that checks the intended SELECT/INSERT/UPDATE/DELETE privilege matrix for all five quantitative tables, and record that exact evidence in the revised Build Report.

This finding is an evidence-coverage gap; the SQL implementation itself is consistent with the claimed privilege policy.
