## 3. Acceptance Review

### A1 — Canonical contract coverage

**Result:** `PASS WITH LIMITATION`

The eight-test suite constructs existing Instrument, Candle, Trade, Order Book and Derivatives contracts, and the full repository regression passed. This provides evidence that the new foundation is compatible with the existing canonical contracts.

However, construction is not equivalent to negative validation coverage. Existing repository contract tests may supply additional negative evidence, but the Step-specific suite does not demonstrate that the new foundation itself rejects invalid canonical semantic input across the required boundary.

### A2 — Identity validation

**Result:** `PASS`

Semantic-token syntax validation and deterministic SHA-256 identity derivation are implemented and tested for order independence.

### A3 — Required / optional / null semantics

**Result:** `PASS`

Required and explicit-null detection is implemented and directly tested.

### A4 — Decimal / numeric enforcement

**Result:** `PASS WITH LIMITATION`

Finite `Decimal` enforcement, binary-float rejection, and non-finite rejection are implemented and tested. Explicit scale overflow is rejected without rounding.

The implementation does not introduce a separate precision-bound validator despite the Task Order and Build Report describing both `precision` and `scale` semantics. The existing canonical contracts have precision fields and their own validation; this Step's reusable foundation does not establish an explicit generic precision validator. CONTROL therefore does not accept the Build Report's `Precision/scale` mapping as fully demonstrated by this foundation alone.

### A5 — Timestamp semantics

**Result:** `PASS`

Aware UTC timestamps are required and tested. The implementation does not consult the wall clock.

### A6 — Provenance requirements

**Result:** `REVISE REQUIRED`

`ProvenanceRef` requires non-empty semantic tokens and is immutable, and the test constructs a valid provenance reference. However, the Step-specific test does not test rejection of missing/invalid provenance at the canonical validation boundary, despite provenance requirements being an explicit minimum acceptance item in `TO-P3-001`.

The existence of a valid provenance object is evidence of positive construction only; it is not sufficient negative evidence for the required provenance rule.

### A7 — Lineage requirements

**Result:** `PASS WITH LIMITATION`

`LineageRef` is immutable and validates its two tokens. The test covers construction and immutability only. Missing/invalid lineage rejection is not directly exercised.

### A8 — Validation-result taxonomy / data-quality semantics

**Result:** `REVISE REQUIRED`

`ValidationResult` contains `VALID`, `INVALID`, `INCOMPLETE`, `STALE`, `DEGRADED`, `CONTRADICTORY`, `UNAVAILABLE`, `UNSUPPORTED`, and `QUARANTINED`.

The ratified architecture's P3 data-quality outcome vocabulary in `DOC-V2-ARCH-001` §13 explicitly includes:

`VALID`, `DEGRADED`, `STALE`, `INCOMPLETE`, `CONTRADICTORY`, `REJECTED`, `UNAVAILABLE`.

The implementation does not contain `REJECTED`; it contains `INVALID` instead. `INVALID` and `REJECTED` are not automatically interchangeable because the architecture separately defines rejected data state and the P3 gate explicitly requires rejection/DLQ behavior. CONTROL will not silently reconcile these terms.

Required correction: either demonstrate an authoritative repository basis that establishes `INVALID` as the canonical replacement for `REJECTED`, or align the foundation taxonomy with the authoritative architecture through the appropriate governed correction. No invented semantic reconciliation is permitted.

### A9 — Invalid-data rejection

**Result:** `PASS WITH LIMITATION`

The foundation rejects several invalid inputs through exceptions, including float, non-finite Decimal, scale overflow, invalid timestamp and invalid semantic token. This is useful negative evidence.

However, there is no direct Step-specific test establishing the mapping between invalid semantic findings and the declared validation-result taxonomy / outcome model. `ValidationOutcome` exists but the module does not provide a validation function that constructs an `INVALID`/`REJECTED` outcome from the demonstrated failure conditions. This leaves a semantic gap between reason codes and outcome classification.

### A10 — Provider neutrality

**Result:** `PASS`

The implementation does not encode Binance/MEXC wire aliases or transport-specific fields and accepts caller-supplied vocabularies rather than inventing them.

### A11 — Determinism / purity

**Result:** `PASS`

The inspected implementation is side-effect free and deterministic within its stated functions. Canonical JSON uses sorted keys and compact separators; identity uses SHA-256 over that representation.

### A12 — Scope discipline

**Result:** `PASS`

No evidence in the audited change set indicates implementation of later Phase 3 Steps, Phase 4, trading, V1 mutation, or unrelated infrastructure work.

## 4. Material Findings Requiring Correction

### FINDING-01 — Authoritative P3 outcome vocabulary mismatch

**Severity:** `HIGH`

`DOC-V2-ARCH-001` §13 defines `REJECTED`; `foundation.py` defines `INVALID` instead and also adds `UNSUPPORTED` and `QUARANTINED`.

CONTROL cannot treat this as a harmless naming difference because the architecture explicitly distinguishes rejected data state and the phase requires rejection/DLQ behavior.

**Required action:** reconcile the taxonomy against the authoritative architecture through the governed correction path. Do not silently rename or reinterpret the architecture.

### FINDING-02 — Provenance acceptance evidence is incomplete

**Severity:** `MEDIUM`

The Step requires provenance requirements, but the Step-specific tests only construct a valid `ProvenanceRef`; they do not prove missing/invalid provenance rejection at the relevant canonical boundary.

**Required action:** add deterministic negative tests for missing/invalid provenance and demonstrate the resulting governed validation behavior.

### FINDING-03 — Validation outcome is defined but not connected to validation behavior

**Severity:** `MEDIUM`

`ValidationOutcome` and `ValidationIssue` are immutable data structures, but the inspected foundation exposes primitive validators that return issues or raise exceptions rather than a complete deterministic foundation-level mechanism that maps validation findings to a `ValidationOutcome` classification.

**Required action:** either demonstrate the authoritative reason why this separation is intentional and sufficient for `STEP-P3-001`, or add the missing deterministic outcome construction/mapping required by the Step's validation-result taxonomy. Do not expand into later Step behavior.

### FINDING-04 — Precision semantics are claimed more broadly than the new foundation implements

**Severity:** `MEDIUM`

The Build Report maps `Precision/scale` to explicit scale validation, but the inspected new module contains no generic precision-bound validator. Existing contract precision fields remain outside the new helper.

**Required action:** either narrow the evidence claim to scale-only semantics and show existing authoritative precision coverage is intentionally relied upon, or implement the minimum generic precision semantics required by the Step. Do not invent new precision policy.
