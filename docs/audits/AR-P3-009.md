## 3. C6 — Concurrent duplicate persistence / deterministic retry semantics

The Task Order explicitly requires concurrent duplicate attempts, duplicate delivery, duplicate persistence retry and deterministic replay/idempotency.

The current `QualityEvidencePersistence.persist()` sequence is:

1. SELECT by evidence_id;
2. if absent, INSERT ... ON CONFLICT (evidence_id) DO NOTHING;
3. fetch logical-fact rows;
4. return `inserted=True` whenever the pre-check found no existing row.

Two identical concurrent callers can both observe no row. One INSERT succeeds; the other becomes a conflict no-op. Because the INSERT result is not used to distinguish those cases, the losing caller can still return `inserted=True`.

The database state remains duplicate-safe, but the persistence API result is not deterministically truthful for the concurrent case.

Required correction:

- make concurrent identical persistence attempts deterministic at both database state and persistence-result boundary;
- add a genuine concurrent PostgreSQL integration test exercising simultaneous identical persistence attempts;
- prove exactly one persisted evidence row exists;
- prove the winning invocation reports insertion and the losing invocation reports no insertion, or establish an equally precise and semantically justified result contract;
- prove concurrent retries do not create contradictory evidence;
- preserve append-only behavior and transaction atomicity;
- do not weaken the existing uniqueness boundary.

A mocked or conceptual concurrency test is insufficient. The acceptance evidence must exercise actual PostgreSQL concurrency.
