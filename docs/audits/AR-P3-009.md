## 2. Findings requiring correction

### C1 — Real runtime path for unavailable acquisition evidence

The production P3-008 vertical slice selects raw rows with acquisition_state='AVAILABLE'. The new runtime path therefore does not actually persist an acquisition-level UNAVAILABLE envelope. The dedicated test constructs such an envelope directly in memory. That proves contract construction, but not the required operational persistence path.

Producer must establish the real authoritative path for an UNAVAILABLE acquisition outcome, or prove the existing upstream representation through which that outcome must reach quality-evidence persistence. No fabricated market payload or artificial fallback row is permitted.

### C2 — End-to-end P5 EvidenceRef proof

The persistence adapter can map a row to the seven P5 fields, but the current dedicated tests do not prove the complete producer-to-P5 path.

Producer must add an integration-level proof that a real persisted record with complete timeframe and venue is read back, resolved to a complete EvidenceRef, admitted when knowledge_time == snapshot.as_of, rejected when knowledge_time > snapshot.as_of, and rejected as unavailable when required timeframe or venue is missing.

P5-002 must remain unchanged.

### C3 — Historical evidence boundary

The Build Report describes Class-B and Class-C historical treatment, and migration 0009 performs no blind historical promotion. However, the stronger historical classification claim is not backed by a direct evidence inventory or deterministic reconstruction demonstration.

Producer must provide repository evidence identifying the relevant legacy evidence population and the authoritative source material available for reconstruction, or demonstrate why promotion cannot legitimately occur. No historical record may become P5-eligible merely because the new schema exists.

### C4 — PostgreSQL behavioral verification

The dedicated tests use an in-memory persistence double. Actual Docker migration success is useful but does not by itself prove database behavior for duplicate retry, rollback, append-only UPDATE/DELETE rejection, application privileges, and persisted read-back.

Producer must add actual database-backed verification sufficient to establish those behaviors. No governed VPS mutation is authorized.
