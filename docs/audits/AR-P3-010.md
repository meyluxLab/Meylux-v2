## 3. Root-cause verification

The reproduced failure is supported by direct diagnostic evidence:

- diagnostic Docker run `37037250569`;
- failure at `0004_canonical_quality_state_alignment.sql`;
- captured PostgreSQL stderr: `FATAL: the database system is shutting down`;
- container logs showing Timescale initialization, `timescaledb-tune`, shutdown/restart, and migration execution overlapping the shutdown.

The prior readiness boundary accepted a successful `SELECT 1` before the image initialization/restart sequence had completed.

CONTROL therefore accepts the following bounded conclusion:

**The reproduced Docker failure mechanism was a PostgreSQL/Timescale startup-readiness race in the P3-009 evidence harness.**

Historical failed executions remain correctly qualified: their original stderr was not preserved, so their individual internal messages are not reconstructed. The audit does not rewrite those historical records.

## 4. Correction verification

The final implementation:

1. waits for the Timescale/PostgreSQL init-complete marker;
2. then requires successful final-server `SELECT 1`;
3. blocks migration execution until both readiness conditions are satisfied;
4. emits subprocess command, exit code, stdout and stderr on checked failure;
5. emits container state and bounded PostgreSQL logs on setup/readiness/migration failure;
6. identifies the failing migration;
7. explicitly removes the ephemeral container when `setUpClass` fails;
8. adds P3-009 PostgreSQL and quality-evidence paths to Docker Foundation PR filters.

CONTROL inspected the actual changed code and found no weakening, skipping, removal, migration bypass, assertion suppression, or semantic redesign.
