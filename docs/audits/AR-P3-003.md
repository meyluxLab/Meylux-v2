## 4. Implementation Findings

### 4.1 Temporal validation

`contracts/temporal.py`:

- consumes `AcquisitionEnvelope` rather than reconstructing it;
- reuses `validate_timestamp` from P3-001;
- validates `event_time` and `received_at` as aware UTC timestamps;
- rejects `event_time > received_at`;
- performs future-time checking only against an explicitly supplied `reference_time`;
- does not read wall-clock state;
- validates chronological order across an evidence sequence.

The underlying `AcquisitionEnvelope` constructor already enforces UTC timestamp representation, so P3-003 correctly operates after the P3-002 structural/contract boundary rather than redefining construction semantics.

### 4.2 Sequence validation

The implementation:

- treats `source_sequence` as an opaque string;
- detects exact duplicate sequence values within the provider/instrument stream;
- keeps per-stream previous sequence state local to the validation call;
- performs continuity/order checking only when an explicit `sequence_successor` is supplied;
- does not invent numeric sequence semantics.

This is consistent with the authoritative Phase-2 contract and the explicit P3-003 prohibition on inventing sequence policy.

### 4.3 Completeness / cadence

The implementation:

- performs cadence continuity checking only when an explicit `cadence_successor` is supplied;
- does not infer timeframe, cadence, gap threshold, or clock-skew policy;
- does not fabricate missing events or repair discontinuities.

No quarantine/DLQ or lineage implementation is present.

### 4.4 Determinism and identity preservation

The reviewed functions do not access network, database, filesystem, wall clock, or mutable global state. Temporal reference and sequence/cadence semantics are explicit function inputs.

`AcquisitionEnvelope.event_id` remains authoritative; P3-003 does not reconstruct or replace identity semantics.
