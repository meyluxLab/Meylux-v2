## 1. Executive determination

**Primary disposition: B — NO QUALIFIED ROUTE ESTABLISHED.**

Within the exact product/instrument scope required for Meylux's S-04 derivative facts, the retrieved authoritative evidence does not establish a complete compatible route supplying Funding, Open Interest (OI), and Basis together for the required BTCUSDT / SOLUSDT instrument scope.

The evidence does establish that Binance's COIN-M Futures API documents Funding, OI, and Basis endpoints for its own COIN-M product family. This is not qualification for a BTCUSDT USDⓈ-M contract: the documented COIN-M Basis endpoint is pair-based (example BTCUSD) and explicitly belongs to the COIN-M API family. Substituting BTCUSD COIN-M for BTCUSDT would change the instrument/product identity and is not permitted by TO-P2-018.

For Binance USDⓈ-M BTCUSDT, the official material successfully retrieved in this investigation did not establish a complete Funding/OI/Basis route. The current official USDⓈ-M Funding, OI and Basis documentation was not successfully retrieved and verified here, so all three are classified as **not established in this investigation**. The COIN-M documentation cannot be generalized to USDⓈ-M. This is not proof that any of those USDⓈ-M endpoints do not exist.

For MEXC Futures BTC_USDT, the official public contract documentation establishes Funding and exposes index/fair-price data and a ticker field named holdVol described as total holdings. The inspected documentation did not establish an authoritative public OI contract with sufficiently explicit unit/temporal semantics, nor a direct provider-authoritative Basis fact for the exact instrument. Fair price is not substituted for Basis, and holdVol is not silently promoted to canonical OI.

No provider/product has been selected for the Project Owner. No implementation, live API call, runtime/VPS operation, contract/schema change, or STEP-P5-007 activation occurred.

## 3. Evidence classification and method

Evidence classes used:

- **Official endpoint/schema fact:** the provider's official documentation names an endpoint, parameter, response field or explicitly described semantics.
- **Repository contract fact:** directly present in a retrieved frozen contract, persistence migration, requirement or governed artifact.
- **Not established:** the inspected authoritative sources do not establish the required claim. This does not mean the provider definitively lacks the capability.
- **Incompatible:** a documented route exists, but it does not match the required product/instrument identity or would require an unapproved substitution.
- **Inference rejected:** a plausible interpretation that is not promoted to provider guarantee.

#### USDⓈ-M OI unit finding — precise unresolved gap

The official USDⓈ-M page establishes that the fields exist, but the inspected response schema does **not** give an explicit unit for current `openInterest`, historical `sumOpenInterest`, or `sumOpenInterestValue`. The words “Open Interest”, “total open interest”, and “total open interest value” do not establish whether the quantity is contracts, base-asset quantity, quote-currency notional, or another precisely defined quantity for this product. A numeric example is not a unit specification. The COIN-M page's explicit “cont” / “base asset” labels are product-family-specific and cannot be transferred to USDⓈ-M.

This gap matters because `CanonicalDerivatives.open_interest` is a non-negative Decimal but carries no per-field unit tag; OI delta and comparisons are only meaningful when the same quantity definition and contract identity are preserved across observations. The gap would be resolved by an authoritative Binance USDⓈ-M specification (or official schema/field definition explicitly incorporated by that documentation) that defines the exact unit and calculation basis of current and historical OI fields, including whether `sumOpenInterestValue` has a defined currency/valuation basis and how it relates to `sumOpenInterest`. Until then, do not select either field as canonical OI merely by name or sample values.

#### BTCUSDT versus SOLUSDT — separate findings

- **BTCUSDT:** Explicitly used as the example for the Funding `symbol`, current OI `symbol`, historical OI `symbol`, and Basis `pair` parameters. This proves documentation-level route shape and response-field capability, not that the symbol is currently listed, enabled, returning data, or operationally available.
- **SOLUSDT:** The same endpoint schemas use generic `symbol`/`pair` string parameters and document the same response fields, so the API shape is potentially applicable to a SOLUSDT contract if that exact USDⓈ-M contract is listed. The inspected Market Data page does not provide a SOLUSDT example or establish current SOLUSDT listing/status. No live exchangeInfo/API query was performed, by authorization restriction. Therefore SOLUSDT is **not independently qualified**: exact listing/product metadata and runtime availability remain unverified, and OI unit semantics remain the same unresolved documentation gap.

**S-04 history assessment:** The governed S-04 description requires funding classification, funding-velocity sign, qualitative quadrants of OI-delta × price-change, and Basis status. The P4 semantics require prior ordered observations for funding velocity and OI delta; absent prior observations must remain insufficient history, not zero. The reviewed S-04 definition does not specify a multi-month/minimum-retention requirement for derivatives facts. Thus, the documented latest-one-month OI history and latest-30-days Basis history are **not shown to contradict the stated S-04 analytical requirements**: they can in principle provide a current observation plus an adjacent prior observation when both are available within the window. They do **not** establish completeness, stable cadence, gap-free coverage, or runtime availability; they cannot support retrospective reconstruction/backfill older than their stated windows. The OI unit gap remains independently disqualifying for full route qualification. Funding history has max 1000 records and a default of most recent 200, with time filters; the page does not establish unlimited retention. Future acquisition must page/handle truncation explicitly and report missing prior observations as unavailable/insufficient rather than manufacture continuity.

**Result:** USDⓈ-M is now a materially stronger documented candidate, and the prior statement that none of its three metric routes was established is corrected. Nevertheless, the exact route is **not yet qualified** because authoritative OI unit semantics and exact BTCUSDT/SOLUSDT listing/runtime evidence are unresolved; no live verification is authorized by TO-P2-018.

## 5. Units, identity, temporal behavior, provenance and coverage

### 5.1 Instrument identity

The current P5 requirements and roadmap do not permit replacing one instrument/product family with another merely because the underlying asset name is similar.

- BTCUSDT Spot, BTCUSDT USDⓈ-M perpetual, BTCUSD COIN-M perpetual and MEXC BTC_USDT Futures are distinct provider/product identities.
- The canonical identity must be assigned to the actual provider instrument. It must not collapse BTCUSD COIN-M into BTCUSDT.
- Provider symbol/pair, product family, contract type, settlement/margin asset, contract multiplier and quote/base assets must be captured from the authoritative instrument metadata applicable to the selected route.
- This investigation did not perform instrument discovery through live endpoints. No current contract listing or trading status is claimed.

### 5.2 Units and value semantics

The canonical derivatives contract CTR-V2-CANONICAL-DERIVATIVES version 1.0.0 contains Decimal fields `funding_rate`, `open_interest`, `open_interest_delta` and `basis`, but no metric-specific unit fields. Decimal typing and non-negativity validation do not establish provider units.

CanonicalInstrument can preserve base_asset, quote_asset, market_type, contract_type, unit and contract_multiplier. Those fields can support route-specific semantic interpretation only if authoritative instrument metadata and field units are explicit and unambiguous. They do not authorize treating unlike product units as equivalent.

- **Binance USDⓈ-M:** Official docs establish current `openInterest`, historical `sumOpenInterest` and `sumOpenInterestValue`, but the inspected schema does not explicitly define their units/calculation basis. Do not infer from examples or field names. This remains an exact qualification gap.
- **Binance COIN-M:** Official OI statistics explicitly label `sumOpenInterest` as “cont” and `sumOpenInterestValue` as “base asset”. These are COIN-M-specific documented semantics and must not be borrowed for USDⓈ-M.
- **Funding:** `fundingRate` is a rate; it must not be confused with a funding payment amount.
- **Basis:** Binance USDⓈ-M and COIN-M docs both expose a direct `basis` field separately from `basisRate` and `annualizedBasisRate`. These fields are not interchangeable. The canonical contract currently has `basis`, not a separate basis-rate field; only the semantically corresponding provider field could be mapped, with exact meaning recorded in provenance/payload and no silent substitution.
- **MEXC:** `holdVol` does not establish the same unit semantics as Binance OI fields; fair price does not establish that a canonical Basis fact is directly supplied.

The remaining USDⓈ-M OI unit gap matters to OI delta and the S-04 OI-delta × price-change quadrant: values with changed units, contract multipliers, or valuation bases could create false deltas/classifications even if the fields are numeric.

### 5.3 Timestamps and knowledge-time

The contracts require UTC-aware event timestamps. AcquisitionEnvelope preserves `event_time` and `received_at) independently. QualityEvidenceRecord sets `knowledge_time = received_at` under the authoritative P3 rule. Persistence timestamps are not substituted for knowledge_time.

Documented endpoint timestamp meanings must remain distinct:

- Binance USDⓈ-M Funding: `fundingTime` is the funding event time.
- Binance USDⓈ-M current OI: `time` is documented as transaction time.
- Binance USDⓈ-M historical OI: `timestamp` is period end.
- Binance USDⓈ-M Basis: `timestamp` is period start.
- Binance COIN-M Funding: `fundingTime` is funding event time.
- Binance COIN-M OI statistics: `timestamp` is period end.
- Binance COIN-M Basis: `timestamp` is period start.
- MEXC current Funding includes a system `timestamp` and `nextSettleTime`; historical Funding uses `settleTime`.

These meanings cannot be normalized into one invented observation time. The route must preserve provider event-time meaning per metric, capture receipt time separately, set authoritative quality-evidence knowledge_time to receipt time, and require `knowledge_time <= snapshot.as_of`. Late-arriving facts can have an event_time before receipt/knowledge_time; they must not be treated as having been known earlier than receipt. For S-04 velocity and OI delta, use explicitly ordered eligible observations with positive elapsed time where required; absent, duplicate, non-monotonic, or contradictory prior observations must produce explicit insufficient/invalid evidence rather than fabricated continuity. Persistence time is not a substitute for event or knowledge time.

### 5.4 Provenance and evidence lineage

AcquisitionEnvelope can carry provider identity, adapter identity/version, provider instrument identity, provenance, source sequence, event_time, received_at and raw payload. Quality evidence preserves provider/product identity, source identity hash, payload fingerprint, provenance, event_time, received_at and knowledge_time. Canonical persistence preserves provenance_id, source_record_id, lineage_parent_id, event_time, canonical bytes, identity hash and payload_json.

These contracts are sufficient as a general acquisition/evidence chain for a bounded future route, as assessed in TO-P2-017. They do not make undocumented provider semantics authoritative. Route qualification still requires the exact endpoint/field meaning, unit, product family and timestamp semantics to be established before implementation.

### 5.5 Coverage and retention

- **USDⓈ-M Funding:** max response limit 1000; default most recent 200 when no time filters are supplied; time filters are inclusive and results are ascending. The reviewed page does not establish unlimited retention. Pagination/truncation must be handled explicitly.
- **USDⓈ-M historical OI:** only the latest one month is documented, max limit 500.
- **USDⓈ-M Basis:** only latest 30 days are documented, max limit 500.
- **S-04 fit:** S-04 requires funding classification, funding-velocity sign, OI-delta × price-change qualitative quadrants, and Basis status. It requires ordered prior observations for velocity/OI delta but states no fixed multi-month derivatives history horizon. Therefore one month / 30 days are not demonstrated to conflict with the stated analytical requirements for current state and adjacent-prior calculations, provided valid observations exist within the window. These limits do not establish gap-free cadence, availability, or the ability to reconstruct history older than the retention windows. A future route must return explicit insufficient history when required observations are missing.
- **SOLUSDT:** the official endpoint schema's generic parameters do not prove that SOLUSDT is currently listed or returns data. Current symbol metadata/status was not queried because no live API calls are authorized.
- **COIN-M:** Basis and OI history explicitly document latest-30-days limits; Funding history has max 1000 and the retrieved page does not establish unlimited retention.
- **MEXC Funding:** the inspected page does not establish complete historical coverage for the full S-04 horizon.
- No route was tested against live data; no current data availability, uptime, rate-limit budget, latency or production freshness is claimed.

## 6. Existing contract and persistence compatibility

### Existing representation

- Acquisition: CTR-P2-001 AcquisitionEnvelope carries provider identity, provider instrument identity, event type DERIVATIVES, event_time, received_at, state, payload, provenance and source-sequence where available.
- Normalization: contracts/normalization.py has a _derivatives mapping that maps explicitly present funding_rate, funding_change, funding_velocity, open_interest, open_interest_delta and basis into CanonicalDerivatives. It does not itself prove that a provider field has the right meaning or unit.
- Canonical derivatives: CTR-V2-CANONICAL-DERIVATIVES carries one instrument_id, one UTC timestamp, optional Decimal metrics and provenance_id. Missing metrics are None, not fabricated values.
- Instrument identity: CTR-V2-CANONICAL-INSTRUMENT can retain base/quote assets, market_type, contract_type, unit and contract_multiplier.
- Quality evidence: P3 records provider_instrument_id, canonical_instrument_id, event_time, received_at and knowledge_time. The authoritative rule is knowledge_time = received_at.
- Persistence: meylux.canonical_derivatives is append-only and persists payload_json/canonical_bytes plus source/provenance lineage. meylux.quality_evidence is separately append-only and preserves the authoritative knowledge boundary.

### Compatibility conclusion

No protected contract/schema change is demonstrated to be inherently necessary merely to investigate or eventually represent a correctly identified route using separate observations and the existing canonical instrument metadata. The unresolved issue for this task is that no exact route in the retrieved evidence proves all required facts for the compatible required instrument scope.

A future implementation must not pack Funding, OI and Basis from different product families into a single canonical instrument record. Separate observations may have distinct event times; any OI delta or funding velocity requires ordered observations of the same canonical instrument and compatible unit semantics. Canonical persistence success alone does not prove semantic eligibility.

No new contract, schema, migration or Stable ID is proposed by this report. If later direct evidence reveals that required units or identity semantics cannot be represented truthfully under the frozen contracts, that specific conflict must be returned to CONTROL for formal change-control determination; it must not be patched silently.

## 8. Exact unresolved gaps and objective reconsideration triggers

### Gap G1 — Binance USDⓈ-M OI unit/quantity semantics

**Gap:** The official USDⓈ-M Market Data page documents current `openInterest` and historical `sumOpenInterest` / `sumOpenInterestValue`, but does not explicitly define their units or exact quantity/valuation basis. This is not a missing-endpoint claim; it is a semantic qualification gap.

**Why it matters:** The canonical OI Decimal has no unit tag. OI delta and S-04 OI-delta × price-change quadrants require comparable values for the same exact contract and unit across observations. A guessed contract/base/quote/notional interpretation could make deltas invalid.

**Reconsideration evidence:** An authoritative Binance USDⓈ-M field/schema definition specifying the units and calculation basis of current `openInterest`, historical `sumOpenInterest`, and `sumOpenInterestValue`, including the currency/valuation meaning of the latter and its relationship to the former. COIN-M unit labels or sample magnitudes do not resolve this gap.

### Gap G1b — Binance USDⓈ-M exact symbol listing/runtime

**Gap:** BTCUSDT is explicitly used in official parameter examples, but this documentation investigation did not establish current listing/status or runtime responses for BTCUSDT. SOLUSDT is only covered by generic `symbol`/`pair` schemas, not an exact example or current listing evidence.

**Why it matters:** A generic endpoint contract is not proof that a specific instrument is listed, enabled, or currently returning usable records. Live API calls are outside TO-P2-018.

**Reconsideration evidence:** Official exchange-information schema and authoritative current symbol metadata/status for each exact product/symbol, obtained in a separately authorized runtime-validation boundary. Until then, BTCUSDT documentation capability is established but runtime/listing remains unverified; SOLUSDT is not independently qualified.

### Gap G2 — MEXC BTC_USDT OI semantic guarantee

**Gap:** The public contract API's holdVol field is described as total holdings, but the inspected material does not establish it as the exact required canonical OI fact with unambiguous unit, temporal meaning and coverage.

**Reconsideration evidence:** Official MEXC public market-data documentation explicitly defining the exact OI endpoint/field, product/symbol scope, units, timestamp semantics, historical/current coverage and limitations.

### Gap G3 — MEXC BTC_USDT direct Basis

**Gap:** The inspected public documentation provides index/fair-price fields, but no direct canonical Basis field/endpoint was established.

**Reconsideration evidence:** Official documentation for a provider-supplied Basis fact with explicit definition, unit, product/symbol identity, timestamp semantics and coverage; alternatively, a separately ratified existing deterministic Basis definition with authoritative inputs would require its own applicable governance determination before any derivation could be used.

### Gap G4 — SOLUSDT exact product coverage

**Gap:** Binance USDⓈ-M documentation has generic Funding/OI `symbol` and Basis `pair` parameters, but the inspected page's examples use BTCUSDT, not SOLUSDT. No current SOLUSDT listing/status or live response was checked. MEXC and COIN-M coverage cannot be generalized to SOLUSDT USDⓈ-M.

**Why it matters:** Documentation-level generic endpoint shape is not proof of a current exact symbol listing or operational data availability; all three facts must refer to the same SOLUSDT USDⓈ-M perpetual identity.

**Reconsideration evidence:** Official USDⓈ-M exchange-information metadata documenting the exact SOLUSDT perpetual contract and its base/quote/contract identity, plus separately authorized read-only runtime evidence for Funding, current/historical OI, and Basis.
