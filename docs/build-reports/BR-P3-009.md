## 3. C6 — concurrent duplicate persistence

### Root cause

The previous implementation performed:

1. pre-insert SELECT by evidence_id;
2. INSERT ... ON CONFLICT DO NOTHING;
3. unconditional inserted=True when the pre-check found no row.

Two concurrent identical callers could both pass the pre-check. The losing INSERT could then conflict and do nothing while the caller still reported inserted=True.

The database uniqueness boundary prevented duplicate physical rows, but the application result was race-sensitive.

### Correction

The persistence boundary now uses:

`INSERT ... ON CONFLICT (evidence_id) DO NOTHING RETURNING evidence_id`

and derives the `inserted` result from the actual PostgreSQL INSERT outcome:

- returned evidence_id → `inserted=True`;
- no returned row after the conflict boundary → `inserted=False`.

The logical-fact read-back is then performed after that database statement within the same transaction. Under PostgreSQL READ COMMITTED semantics, the conflicting INSERT waits for the competing transaction's outcome before the no-row result is returned, so the subsequent read observes the committed logical-fact state.

No pre-insert existence check remains in the authoritative persistence decision.

### Why this is deterministic

For two identical concurrent attempts with the same evidence_id:

- exactly one INSERT creates the row;
- exactly one invocation receives RETURNING evidence_id;
- exactly one invocation reports `inserted=True`;
- the losing invocation reports `inserted=False`;
- the persisted row count remains exactly one;
- both callers see the same logical fact and neither invents a contradictory state.

A distinct evidence identity for the same logical fact remains an explicit contradiction and is never silently selected.

## 8. Identity, contradiction and retry

- database state;
