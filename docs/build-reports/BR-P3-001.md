## 4. Correction Summary

### F-01 — Authoritative Data-Quality Taxonomy

Corrected `ValidationResult` to the architecture-authoritative seven outcomes only:

`VALID / DEGRADED / STALE / INCOMPLETE / CONTRADICTORY / REJECTED / UNAVAILABLE`

Removed the previously introduced `INVALID`, `UNSUPPORTED`, and `QUARANTINED` members from this canonical validation-result taxonomy. `REJECTED` is now the deterministic outcome for validation findings that are not merely missing required evidence.

Repository evidence also confirms the existing authoritative `contracts/data_quality.py` already defines `DataQualityState.REJECTED` and the seven quality outcomes. No architecture change was required.

### F-02 — Provenance Negative Evidence

Added `validate_provenance()` as a deterministic canonical-boundary check.

Evidence now directly covers:

- missing provenance → `PROVENANCE_MISSING` → `INCOMPLETE`;
- invalid provenance type → `INVALID_TYPE` → `REJECTED`;
- empty `ProvenanceRef` construction → deterministic `ValueError`;
- valid immutable provenance remains accepted.

No fallback provenance is fabricated.

### F-03 — ValidationOutcome Mapping

Added `validation_outcome()` to deterministically map primitive findings to the declared outcome model:

- no findings → `VALID`;
- missing/null required evidence, missing provenance, or missing lineage → `INCOMPLETE`;
- any other validation finding → `REJECTED`.

The mapping does not infer freshness, contradiction, degraded state, availability, repair, quarantine, or later pipeline behavior. Those remain outside this Step boundary.

### F-04 — Precision Evidence Boundary

No new precision policy or separate precision-bound validator was invented.

The authoritative repository contract registry states that `Decimal` is authoritative for price/volume values, binary floating-point values are rejected, and source decimal scale is preserved without implicit rounding or quantization. Existing canonical Instrument semantics expose explicit `price_precision` / `quantity_precision` metadata and validate those metadata values deterministically; the generic foundation enforces exact finite `Decimal` representation and explicit scale rejection without rounding.

Therefore the Step relies on the existing canonical precision/scale contract semantics rather than introducing a competing precision policy.
