## 4. Contract / Evidence Semantics

### Stage-1 independence

`SpecialistRequest` exposes only:

- `specialist_id`;
- authoritative `InputSnapshot`;
- versioned `SpecialistConfigRef`.

The snapshot contract rejects nested specialist-output/dependency fields. This makes the Stage-1 boundary enforceable at the contract boundary rather than relying solely on documentation.

### Input Snapshot

`InputSnapshot.build()` derives a deterministic SHA-256 identity from:

- snapshot version;
- `as_of`;
- canonicalized facts;
- provenance references.

Equivalent fact/provenance ordering produces the same snapshot identity. Facts whose `knowledge_time` exceeds `as_of` are rejected.

### Evidence reference structural validation

`EvidenceRef` validates the structure and identity metadata of a reference:

- evidence identifier;
- source type;
- source reference;
- 64-character hexadecimal SHA-256 identity hash;
- optional UTC observation time;
- optional content version.

This is **structural contract validation only**.

P5-001 does **not** resolve, retrieve, dereference, availability-check, or independently verify the external/internal evidence target named by `source_reference`. No evidence resolver or provider retrieval subsystem was introduced. A structurally valid `EvidenceRef` therefore must not be interpreted as proof that the referenced evidence is currently retrievable or available.

SUCCESS/PARTIAL specialist outputs require at least one structurally valid evidence reference.

### Numeric / serialization safety

Authoritative specialist contract serialization rejects Python floats and non-finite `Decimal` values. Decimal values are serialized deterministically and UTC timestamps are normalized explicitly. No NaN/Inf fallback or fabricated numeric state is introduced.

### Deterministic mapping-key canonicalization

The authoritative canonicalization path now rejects non-string mapping keys rather than coercing them with `str()`. This prevents distinct mappings such as integer-key `1` and string-key `"1"` from collapsing into one canonical representation.

No broader serialization redesign was introduced.

### SpecialistConfigRef SHA-256 validation

`SpecialistConfigRef.identity_hash` now requires exactly 64 hexadecimal characters, accepting both uppercase and lowercase hexadecimal digits while rejecting malformed, non-hexadecimal, and incorrect-length values.

This preserves the established SHA-256 identity model.

## 5. Configuration and Enforcement Boundaries

`config/specialists.yaml` is intentionally JSON-compatible YAML. This provides deterministic parsing with the repository's existing standard-library-only CI environment; JSON is a valid YAML subset.

The configuration carries:

- `name`;
- `schema_version`;
- `configuration_version`;
- `environment`;
- `provenance`;
- parameter type and unit;
- explicit value;
- minimum/maximum bounds;
- immutable safety constraints.

The validator rejects attempts to enable trading, capital movement, custody or private-provider access.

Configuration identity is a deterministic SHA-256 over the canonical configuration material.

### `max_findings` / `max_evidence_refs` boundary

These parameters are **validated and versioned configuration declarations at the P5-001 foundation boundary, but are not execution-enforced by P5-001**.

Repository-grounded rationale: P5-001 contains the contract/config/persistence foundation only; it does not define or authorize specialist execution, finding production, evidence aggregation, or a later specialist runtime boundary. Enforcing these limits here would require inventing an execution semantics that belongs to a later governed Step.

Accordingly:

- P5-001 validates their type, unit and configured min/max bounds;
- P5-001 preserves them in versioned configuration identity/provenance;
- P5-001 does not truncate findings or evidence references;
- later governed specialist-execution logic must enforce the applicable limits at the execution boundary when that boundary is authorized.

No later specialist execution was introduced merely to activate these parameters.
