## 2. Root-Cause Analysis

### 2.1 Venue/provenance

The canonical candle contract carries `provenance_id` but no venue field. The indicator engine's derived `QuantitativeContext` preserved the candle source reference and timestamp but did not populate `venue_context`, allowing valid mathematical results to be persisted with a null venue.

The existing acquisition boundary already provides the needed evidence path: raw acquisition rows retain `provenance_id`, `provider_id`, `adapter_id`, and `adapter_version`; the governed Binance Spot candle adapter also attaches explicit `venue: BINANCE` source context to its REST and WebSocket candle envelopes. The defect was in carrying that source context across the P4 persistence boundary, not in a need to infer venue from the symbol or provider name.

### 2.2 EMA coverage

The quantitative configuration previously exposed a single EMA period, defaulting to 20, and emitted only the legacy `EMA` fact name. The existing `ema_candles` engine is deterministic and parameterized; the gap was the configured fact population, not a missing mathematical definition.

## 3. Implemented Venue Resolution

`src/meylux/persistence/quantitative.py` now resolves context from `meylux.raw_acquisition_events` for the input provenance identifiers, restricted to AVAILABLE CANDLE records.

Resolution rules:

- Each provenance identifier must have matching raw source evidence.
- Provider identity (`provider_id`, `adapter_id`, `adapter_version`) must be internally consistent for each provenance identifier.
- Venue is accepted only from an explicit string-valued `payload_json.venue` or `payload_json.venue_context`.
- Conflicting `venue` and `venue_context`, malformed values, multiple venues, incompatible source identities, unknown provenance, or missing raw evidence leave venue unresolved.
- Every provenance identifier contributing to the calculation must resolve consistently to one venue before the context is enriched.
- A calculation's `source_ref` must be explicit and belong to the orchestration's provenance set. Missing or contradictory source references fail before persistence; the indicator path no longer manufactures a `canonical-provenance:` fallback.
- An already supplied calculation venue that conflicts with resolved explicit raw source context is rejected.

When venue cannot be authoritatively resolved, the mathematical result is not relabeled as a different calculation. Its venue remains null, so it is not complete P5 EvidenceRef material and must not be treated as P5-available evidence. This is distinct from mathematical insufficient history.

## 4. Implemented EMA Population

`src/meylux/orchestration/engine.py` adds the configured `ema_periods` tuple with the required periods `(9, 20, 21, 50, 200)`. Runtime configuration can override this tuple through `MEYLUX_EMA_PERIODS`; the existing legacy `ema_period` setting and `EMA` fact remain backward-compatible.

The existing EMA engine is reused. Each distinct required period is calculated once, and the named facts are emitted as:

- `EMA_9`
- `EMA_20`
- `EMA_21`
- `EMA_50`
- `EMA_200`

Configuration rejects an empty period set, non-positive or non-integer values, booleans, and duplicate periods.

With 40 closed candles, the tests establish valid values for periods 9, 20 and 21, and explicit `INSUFFICIENT_HISTORY` with null numeric values and period-specific reasons for periods 50 and 200. With 240 closed candles, all five configured periods produce valid values from the existing deterministic engine. PostgreSQL worker-path tests also verify insufficient EMA-200 history on the shorter higher-timeframe fixture. These are test-population results, not claims about the actual governed runtime history.
