## 2. Implemented Comparison Boundary

The reusable boundary is:

`CanonicalVenueEvidence(left) + CanonicalVenueEvidence(right)` → `ComparisonResult`

Supported result states:
- `EQUIVALENT`
- `INCONSISTENT`
- `INSUFFICIENT_EVIDENCE`
- `REJECTED`

Implemented dimensions/behaviors include:
- explicit venue context without canonical-contract redesign;
- canonical instrument semantic identity: base asset, quote asset, market type, contract type, unit, multiplier and active state;
- venue-specific instrument IDs are retained as an audit reason but do not alone defeat semantic cross-venue equivalence;
- trade price, quantity and side comparison;
- candle timeframe, OHLCV/trade-count/closed-state and candle-window comparison;
- order-book bid/ask sanity and canonical level comparison;
- derivatives evidence comparison for existing optional canonical fields;
- timestamp alignment against caller-supplied tolerance;
- freshness against caller-supplied `reference_time` and `max_age` only;
- explicit stale, future-dated, missing-freshness and unavailable evidence handling;
- provenance IDs retained in result evidence and missing provenance rejected;
- provider-wire fields are not consumed or emitted by the comparison contract;
- deterministic reason ordering through fixed comparison order;
- bounded comparison inputs/results using immutable tuples and no unbounded state;
- no opportunity/spread/fee/friction/arbitrage classification.

No P3-001..P3-005 redesign, acquisition redesign, P3-007 subsystem, P3-008 persistence/handoff, Phase 4 functionality, V1/VPS/runtime activity, or Stable-ID mutation was performed.

## 3. No-Guessing / Temporal Boundary

P3-006 does not invent freshness or timestamp thresholds. `ComparisonPolicy` requires callers to supply any timestamp tolerance or freshness age. `reference_time` is explicit and caller-provided; the implementation never reads wall-clock time. Future-dated evidence is not accepted as fresh historical evidence.

A comparison without freshness policy produces explicit `FRESHNESS_UNCHECKED` and therefore `INSUFFICIENT_EVIDENCE`, rather than silently treating the evidence as fresh.

## 6. Open Questions / Deviations

1. `docs/registry/artifacts.yaml` lifecycle reconciliation was pending at Producer handoff and has now been completed by CONTROL under `AR-P3-006`.
2. The existing canonical contracts do not expose venue identity as a field. P3-006 therefore uses the provider-neutral `CanonicalVenueEvidence` wrapper rather than redesigning canonical contracts. This is an implementation boundary, not an architectural contract change.
3. Cross-venue semantic equivalence for payloads now requires compatible semantic instrument identity before payload equivalence can be established. Venue-qualified IDs are compared by their provider-neutral semantic portion; differing provider namespaces alone do not defeat equivalence, while differing semantic instrument identities produce `INSTRUMENT_ID_MISMATCH` and therefore `INCONSISTENT`.
4. No authoritative numeric freshness/timestamp thresholds were available in the Task Order; therefore all such thresholds remain caller-supplied and deterministic.
