## 1. Executive disposition

`MEXC_TRADE_SEQUENCE_INTEGRITY: UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`

The investigation establishes:

1. The current MEXC Spot aggregated public trade/deals Protobuf schema contains a `tradeId` field.
2. MEXC's public Spot WebSocket documentation does **not** document `tradeId` in the Trade Streams response parameter table.
3. The official `PublicAggreDealsV3Api.proto` schema does define `tradeId` as field 5.
4. MEXC provides no authoritative documentation establishing that this `tradeId` is strictly monotonically increasing per instrument, that `previous_id + 1` is a continuity invariant, or that a numerical discontinuity proves a missing trade.
5. A bounded live read-only observation of BTCUSDT over approximately 12 seconds produced real `tradeId` values, including multi-part values with `X0/X1` suffixes. Several later observations contained numerically smaller components than earlier observations. This is empirical evidence that the observed field cannot safely be treated as a simple strictly increasing scalar sequence.
6. Current public REST `/api/v3/trades` documentation exposes a trade-id field, but both the official example and the live read-only response returned `id: null`.
7. Current public REST `/api/v3/aggTrades` supports time-bounded retrieval and documents aggregate/first/last trade IDs, but both the official example and the live read-only response returned `a/f/l: null`.
8. Neither public REST endpoint therefore provides an authoritative exact-ID range that can reconcile a suspected WebSocket `tradeId` gap.
9. The documented REST trade endpoint has no `tradeId`/identifier range parameter; it exposes only `symbol` and `limit`, with a maximum limit of 1000.
10. `aggTrades` accepts `startTime` and `endTime` together, with a maximum limit of 1000, but its current returned identifier fields are null and its output is explicitly aggregate data rather than a one-to-one raw trade ledger.
11. The same provider trade cannot currently be authoritatively proven to carry the same stable identifier through public WebSocket and public REST.
12. No implementation was performed.

Therefore the required completeness mechanism is not authoritatively established.

## 2. Authoritative MEXC documentation

### 2.1 Current Spot WebSocket Trade Streams

Authoritative documentation:

`https://mexcdevelop.github.io/apidocs/spot_v3_en/`

Current public Trade Streams subscription:

`spot@public.aggre.deals.v3.api.pb@100ms@<symbol>`

The documented Trade Streams response lists:

- `dealsList`
- `price`
- `quantity`
- `tradetype`
- `time`
- `eventtype`
- `symbol`
- `sendtime`

The public documentation does **not** list `tradeId` in the response parameter table.

The same documentation explicitly states that parameters not returned in the documentation will be optimized soon and should not be used.

This creates an authority limitation: the field exists in the official Protobuf schema, but MEXC's human-readable public Trade Streams contract does not document it as a completeness guarantee.

### 2.2 Official Protobuf schema

Official MEXC repository:

`https://github.com/mexcdevelop/websocket-proto`

File:

`PublicAggreDealsV3Api.proto`

The current official schema defines:

- `price = 1`
- `quantity = 2`
- `tradeType = 3`
- `time = 4`
- `tradeId = 5`

Thus the existence and wire-level availability of `tradeId` in the aggregated deals schema is authoritative.

However, the schema defines the field type and position only. It does not document:

- uniqueness scope;
- monotonicity;
- consecutive numbering;
- reset behavior;
- partition/shard semantics;
- reconnect semantics;
- cross-endpoint identity;
- gap-reconciliation semantics.

No such guarantee was found in the inspected authoritative MEXC documentation.

### 2.3 WebSocket connection and limits

MEXC documents:

- maximum 30 subscriptions per WebSocket connection;
- 100 WebSocket messages per second;
- a connection lifetime of no more than 24 hours;
- disconnection after inactivity;
- PING/PONG keepalive behavior.

These limits are relevant operational constraints for a completeness monitor. They do not provide a trade-sequence completeness guarantee.

### 2.4 REST Recent Trades

Endpoint:

`GET /api/v3/trades`

Official documentation:

- `symbol` required;
- `limit` optional;
- default 500;
- maximum 1000;
- endpoint weight 5/IP.

No `startTime`, `endTime`, `fromId`, or equivalent identifier-range parameter is documented.

The documented response contains an `id` field described as Trade id, but the official example returns `id: null`.

### 2.5 REST Aggregate Trades

Endpoint:

`GET /api/v3/aggTrades`

Official documentation:

- `symbol` required;
- `startTime` optional;
- `endTime` optional;
- `startTime` and `endTime` must be supplied together;
- `limit` default 500;
- maximum 1000;
- endpoint weight 1/IP.

The documented response fields are:

- `a` = Aggregate tradeId
- `f` = First tradeId
- `l` = Last tradeId
- `p` = price
- `q` = quantity
- `T` = timestamp
- `m` = buyer maker
- `M` = best match

The official example returns `a/f/l: null`.

The endpoint explicitly aggregates trades that fill at the same time, from the same order, at the same price. It therefore is not an authoritative one-row-per-public-trade reconciliation ledger.

### 2.6 Historical depth

MEXC's Spot documentation separately advertises downloadable historical market data for Spot pairs since 2023.

That facility is not equivalent to the public REST recent-trades endpoint and does not establish a public REST trade-ID reconciliation mechanism. No exact WebSocket `tradeId` range-retrieval guarantee was established from it.

## 3. Live empirical evidence

### 3.1 Access method

Read-only observation was performed through the already-connected SentinelX host `server-l6rf`.

No VPS mutation, deployment, file modification, restart, installation, or service change was performed.

The WebSocket connection was opened directly to:

`wss://wbs-api.mexc.com/ws`

Subscription:

`spot@public.aggre.deals.v3.api.pb@100ms@BTCUSDT`

Observation duration was approximately 12 seconds.

### 3.2 Live REST evidence

Read-only request:

`GET https://api.mexc.com/api/v3/trades?symbol=BTCUSDT&limit=5`

Observed current response contained five trades whose `id` value was `null`.

The returned rows included current price, quantity, quote quantity, timestamp, maker flag and best-match flag, but no usable public trade identifier.

A bounded `aggTrades` request was also executed for the live observation interval with:

- symbol: BTCUSDT;
- startTime: 1790512254000;
- endTime: 1790512266000;
- limit: 1000.

All returned aggregate rows had:

`a: null`, `f: null`, `l: null`

while price, quantity, timestamp and maker/best-match fields were populated.

### 3.3 Live WebSocket evidence

The live aggregated-deals stream produced real trade IDs such as:

- `732870814738665472X0_732870814738665473X0`
- `732870814742859776X0_732870814742859777X0`
- `732870823123079168X0_732870823123079169X0`
- `732870836888764417X1_732870835055808517X1`
- `732870853007482880X1_732870852650917893X1`
- `732870856601968640X1_732870823290830848X1`
- `732870861219930112X1_732870860968157190X1`

The observed values are not simple scalar integers. They contain two numeric components separated by an underscore and an `X0` or `X1` suffix.

The observation included cases where a later message contained a numerically smaller component than an earlier message. For example:

Earlier:

`732870856601968640X1_732870823290830848X1`

Later:

`732870861219930112X1_732870860968157190X1`

and earlier/later messages also showed component ordering that cannot be reduced to a simple `previous_id + 1` rule.

No interpretation of the internal `X0/X1` structure is asserted because MEXC does not document its semantics in the inspected authoritative materials.

### 3.4 Empirical conclusion

The live observation establishes that:

- `tradeId` is actually emitted by the aggregated public WebSocket;
- the emitted value is structured rather than a simple scalar;
- strict scalar monotonicity cannot be assumed;
- the observed data does not establish a consecutive-number invariant;
- no finite sample can establish universal provider behavior.

The live evidence therefore supports the documented negative conclusion but does not itself define the provider's undocumented internal ID algorithm.

## 4. Uniqueness analysis

No authoritative MEXC guarantee of uniqueness-per-instrument was found.

The bounded live sample contained no duplicate complete `tradeId` string among the observed messages, but that finite sample cannot establish universal uniqueness.

Because the identifier format itself is undocumented, no decomposition of its components into a uniqueness key is asserted.

Disposition:

**Uniqueness: NOT AUTHORITATIVELY ESTABLISHED.**

## 5. Monotonicity analysis

No authoritative MEXC guarantee of strict monotonicity was found.

The live sample materially weakens a scalar-monotonic interpretation because:

- IDs contain multiple numeric components;
- suffixes vary between `X0` and `X1`;
- some later observations contain numerically smaller components than earlier observations;
- no documented rule states which component, if any, is the authoritative sequence position.

Disposition:

**Strict per-instrument monotonicity: NOT AUTHORITATIVELY ESTABLISHED.**

## 6. Gap-detection analysis

The invariant:

`previous_id + 1 == current_id`

is **not established**.

A discontinuity such as:

`100 -> 105`

could only constitute a completeness gap if MEXC first established that:

1. the identifier is a scalar sequence;
2. it is unique within the relevant scope;
3. it is strictly monotonic;
4. every integer increment corresponds to exactly one public trade;
5. no valid provider behavior can skip identifiers;
6. no batching/reordering/reconnect/partition behavior changes the sequence;
7. the observation path is itself complete.

None of these conditions is authoritatively established by the inspected MEXC contract.

Therefore a numerical discontinuity must not be treated as proof of a missing trade.

## 7. Legitimate non-consecutive / exception analysis

The following possible explanations were explicitly considered:

- batching;
- out-of-order delivery;
- delayed delivery;
- reconnect boundaries;
- multiple subscriptions/connections;
- symbol scope;
- partitioning/sharding;
- ID component structure;
- reset/reuse;
- undocumented provider optimization;
- filtering or aggregation.

MEXC's public documentation does not provide sufficient guarantees to eliminate these possibilities.

The live sample specifically demonstrates that the observed identifier cannot safely be treated as a simple monotonically increasing scalar.

No undocumented behavior was promoted to a provider guarantee.

## 9. WebSocket ↔ REST identity consistency

The investigation required answering:

> Does the same MEXC trade carry the same stable identifier across WebSocket and REST?

Current evidence does not establish this.

WebSocket aggregated deals emit `tradeId`.

Current REST recent trades returned `id: null`.

Current REST aggregate trades returned `a/f/l: null`.

There is therefore no live public identifier intersection with which to prove same-trade identity.

Price, quantity, timestamp and maker-side fields are insufficient to claim authoritative identity because multiple trades can share those observable attributes.

Disposition:

**WebSocket↔REST stable identifier continuity: NOT AUTHORITATIVELY ESTABLISHED.**
