## Database / migration

Migration `0002_raw_acquisition_staging.sql` creates `meylux.raw_acquisition_events` with:

- provider and adapter identity;
- canonical/provider instrument identity;
- event type/time and received time;
- acquisition state and source sequence;
- provenance and acquisition method;
- canonicalized JSON representation of the captured payload;
- exact deterministic `canonical_bytes`;
- `identity_hash` and primary `event_id` uniqueness;
- persisted timestamp.

The table is explicitly documented as acquisition evidence/staging only.

## Collector / queue integration

`AcquisitionCollector` provides bounded fan-in over the existing provider adapter boundary. Provider streams are invoked without modifying adapter behavior, and the existing `max_messages` / `max_reconnects` controls are forwarded unchanged.

`AcquisitionQueuePublisher` bridges the existing `QueueEnvelope` contract. Canonical bytes are carried as base64 so transport does not reinterpret Decimal/tuple payload semantics.

The collector's internal queue is bounded and applies producer backpressure when full. No unbounded queue or silent drop path was introduced.

## Persistence / replay / idempotency

Persistence uses the already-governed `AcquisitionEnvelope.event_id` / `deduplication_key` identity semantics. The repository stores the exact canonical bytes and a SHA-256 identity hash. Duplicate insertion returns `inserted=False` without creating a second row.

Replay of the same acquisition evidence therefore resolves to a safe duplicate rather than creating incorrect duplicate evidence.

## Sequencing / recovery

Provider-specific source sequence values are preserved verbatim and persisted; the collector does not invent provider-specific ordering semantics. FIFO queue insertion preserves acquisition arrival order. Provider reconnect/recovery remains owned by the already-verified Binance/MEXC adapters and their existing bounded reconnect controls.

Persistence failures are isolated to the affected event rather than causing an uncontrolled worker loop.

## Observability

Collector events cover backpressure, persistence outcome, persistence failure, provider failure, and bounded run completion. Existing observability scrubbing/rate limits are reused. Provider payloads and credentials are not emitted.
