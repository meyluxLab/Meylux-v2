## 3. Implemented Behavior

### 3.1 Data lifecycle representation

`DataLifecycleState` represents the architecture-defined lifecycle states exactly:

```text
RAW
STAGED
VALIDATING
NORMALIZED
CANONICAL
QUALITY_DEGRADED
REJECTED
QUARANTINED
EXPIRED
ARCHIVED
```

### 3.2 Data-quality representation

`DataQualityState` represents the architecture-defined quality outcomes exactly:

```text
VALID
DEGRADED
STALE
INCOMPLETE
CONTRADICTORY
REJECTED
UNAVAILABLE
```

### 3.3 Immutable quality evidence

`DataQuality` is a frozen/slot-based dataclass containing:

- `quality_state: DataQualityState`;
- immutable tuple `reason_codes`.

Validation rejects invalid state types, non-tuple reason collections, non-string reason codes, empty reason codes, and duplicate reason codes.

Empty reason codes remain permitted because the architecture does not require a fabricated explanation when the upstream reason is unavailable.

### 3.4 No-fabrication and canonical boundary

The implementation does not calculate freshness from the wall clock and does not manufacture missing, stale, contradictory, or unavailable market evidence.

The only cross-state prohibition enforced is the one explicitly established by the architecture: `REJECTED` and `UNAVAILABLE` data cannot be represented as `CANONICAL` truth.

Other quality outcomes are not silently granted additional promotion, repair, fallback, or scoring policy; those remain downstream/domain-specific responsibilities.
