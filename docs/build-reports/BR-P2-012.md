## 1. Executive architectural conclusion

### Definitive conclusion

A technically defensible capability-preserving architecture **does exist conceptually within the existing frozen architecture**, but it is **not** a route to manufacture MEXC finalized candles.

The defensible boundary is:

**MEXC provider observations/evidence → preserve provider-specific evidence upstream → canonicalize only independently defensible semantic facts → keep unsupported candle finality outside canonical candle truth.**

The evidence does **not** support the following broader conclusions:

- MEXC is unusable;
- all MEXC trades must be rejected;
- all MEXC order-book data must be rejected;
- all MEXC historical data must be rejected;
- Trade→Candle is the only possible architecture;
- TO-P2-010 should automatically resume.

The investigation instead establishes four distinct findings:

### 1.1 Failed mechanism

The previously investigated MEXC public trade-stream sequence-integrity mechanism remains unavailable:

`MEXC_TRADE_SEQUENCE_INTEGRITY: UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED`

This is fixed historical evidence from TO-P2-011 / AR-P2-AUDIT-011.

### 1.2 Failed specific architectural route

A Trade→Candle completeness/finality architecture whose proof depends on:

- consecutive MEXC `tradeId`;
- exact trade-gap detection;
- REST exact-ID reconciliation;
- or an inferred completion state

is **not defensible on the current evidence**.

### 1.3 Preservable MEXC capabilities

Substantially more MEXC information can nevertheless be retained as provider evidence, and some existing provider-neutral canonical contracts can represent individual semantic facts without asserting completeness of the entire provider population.

In particular:

- raw MEXC acquisition observations are already preservable;
- individual MEXC trade observations can be represented by the existing `CanonicalTrade` contract, subject to the distinction that this is an observed semantic trade event, not proof of complete trade-stream coverage;
- MEXC REST order-book snapshots can be represented by the existing `CanonicalOrderBook` contract;
- MEXC order-book WebSocket updates expose an authoritative provider version relationship that can support a future snapshot+delta reconstruction architecture;
- MEXC instrument metadata can be represented by the existing canonical instrument boundary;
- MEXC ticker/book-ticker/live market observations can remain provider evidence without inventing new canonical contracts;
- MEXC historical kline/trading data can remain raw/staging evidence.

### 1.4 Candle boundary remains blocked

MEXC public Kline/Candlestick data contains:

- interval;
- window start;
- OHLCV;
- window end;
- symbol;
- symbol ID;
- creation/send timing.

The current public contract does not provide an authoritative candle-finality flag or equivalent provider guarantee establishing that the interval will never change again.

Therefore:

**MEXC_FINALITY: UNAVAILABLE / NOT AUTHORITATIVELY ESTABLISHED**

remains unchanged.

The existing `CanonicalCandle.is_closed: bool` contract must remain truthful. The investigation found no provider-grounded mechanism that permits assigning `is_closed=True` to an MEXC candle merely from time, `windowEnd`, repeated observation, REST availability, or the next interval.

## 5. MEXC provider mechanisms assessed

### 5.1 Provider candle finality flag

**Required guarantee:** a provider-defined field or equivalent semantic mechanism proving that a candle interval is finalized.

**Documentation:** MEXC K-line stream exposes interval, windowStart, OHLCV, windowEnd, symbol, symbolId and createTime. No finality flag is documented.

**Live observation:** current live K-line stream emitted the same BTCUSDT Min1 interval repeatedly while OHLCV changed.

Observed bounded sequence:

- windowStart = 1790517540
- windowEnd = 1790517600
- first observed close = 85026.24
- later observed close = 85026.25
- volume and amount also changed between successive messages.

**Repository:** MEXC K-line decoding preserves the K-line payload; current normalization historically mapped the MEXC candle to `closed=True`, which is exactly the semantic defect identified by TO-P2-009 / TO-P2-010.

**Guarantee established:** NO.

**Completeness:** not established.

**Finality:** not established.

**Temporal semantics:** windowEnd identifies the documented interval boundary, not proof of immutability.

**Identity:** K-lines are uniquely identified by open time in the REST contract, but identity does not prove finality.

**Replay:** repeated observation does not establish closure.

**Historical/live applicability:** neither population acquires a finality guarantee merely from the presence of a close time.

**Failure modes:** live updates can continue changing OHLCV; historical REST rows expose close time but no finality semantic.

**Current canonical compatibility:** no canonical `CanonicalCandle.is_closed=True` promotion is defensible.

**Semantic laundering test:** FAILS if time/windowEnd/repetition is renamed as finality.

**Disposition:** MEXC candle finality remains unavailable.

## 6. Trade sequence mechanism

### 6.1 Trade ID

**Required guarantee:** unique, stable, strictly monotonic per-symbol sequence with a documented continuity invariant.

**Documentation/schema:** official protobuf contains `tradeId`, but the public Trade Streams documentation does not establish uniqueness, monotonicity, consecutive numbering, reset semantics, or completeness semantics.

**Live observation:** prior TO-P2-011 observation recorded structured trade IDs. The bounded observation does not establish a universal sequence invariant.

**Repository:** MEXC acquisition preserves the last trade ID as `source_sequence` when available and the normalization layer maps it into `CanonicalTrade.trade_id`.

**Guarantee established:** NO.

**Completeness:** NO.

**Finality:** NO.

**Temporal:** trade time is available, but time ordering is not equivalent to delivery ordering or sequence completeness.

**Identity:** the identifier can be retained as provider evidence/opaque trade identity, but WebSocket↔public REST stable identifier continuity was not established.

**Replay:** the existing acquisition identity preserves source sequence and payload, but replay safety does not create provider completeness.

**Historical/live:** the limitation applies to the public sequence proof; it must not be generalized to all possible MEXC data sets.

**Failure modes:**

- undocumented ID semantics;
- non-consecutive identifiers;
- batching;
- ordering differences;
- reconnect boundaries;
- provider partitioning;
- REST identifier nulls;
- lack of exact REST ID-range retrieval.

**Disposition:** the sequence mechanism remains unavailable.

## 8. Alternative provider-grounded mechanism: order-book versioning

This is the most important positive finding of TO-P2-012.

### 8.1 Official documented mechanism

MEXC's current documentation explicitly describes how to maintain a local order book:

1. subscribe to aggregated depth WebSocket updates;
2. obtain a REST depth snapshot;
3. require each new `fromVersion` to equal the previous `toVersion + 1`;
4. if continuity fails, reinitialize from the REST snapshot;
5. reject outdated messages;
6. detect missing data between snapshot version and incoming `fromVersion`;
7. apply the incremental changes to the snapshot.

This is materially different from the failed trade-ID mechanism because MEXC explicitly documents the continuity invariant and recovery procedure.

### 8.2 Official schema

`PublicAggreDepthsV3Api.proto` explicitly defines:

- `fromVersion = 4`;
- `toVersion = 5`.

### 8.3 Live observation

A bounded read-only BTCUSDT subscription produced successive depth messages with:

1. fromVersion = 82335433803; toVersion = 82335433860
2. fromVersion = 82335433861; toVersion = 82335433899
3. fromVersion = 82335433900; toVersion = 82335433933
4. fromVersion = 82335433934; toVersion = 82335433961
5. fromVersion = 82335433962; toVersion = 82335433993
6. fromVersion = 82335433994; toVersion = 82335434034
7. fromVersion = 82335434035; toVersion = 82335434116
8. fromVersion = 82335434117; toVersion = 82335434145

The observed transitions satisfy the documented continuity relationship.

This observation does NOT independently prove universal provider behavior; the provider documentation supplies that guarantee.

### 8.4 Semantic result

The combination is:

**provider documentation + official schema + live observation + REST snapshot endpoint**

and therefore materially stronger than a mere correlation.

MEXC has an authoritative provider-grounded sequence/reconciliation mechanism for **order-book depth**, not for public trade completeness.

### 8.5 Architectural consequence

A future live order-book reconstruction path can be defensible if it:

- begins with an authoritative REST snapshot;
- tracks provider depth versions;
- applies only provider-documented incremental updates;
- detects any continuity failure;
- reinitializes from a fresh snapshot on failure;
- never converts a broken stream into a trusted continuous state.

No such implementation is authorized by TO-P2-012 and none was performed.

`GET /api/v3/depth`

with:

- `lastUpdateId`;
- bids;
- asks;
- configurable limit;
- maximum documented depth limit.

A live BTCUSDT read-only response returned:

- lastUpdateId = 82335395230;
- bids and asks;
- timestamp = 1790517519967.

This is an actual provider snapshot observation.

The existing Meylux repository already has:

- `CanonicalOrderBook`;
- MEXC `fetch_order_book()`;
- source sequence populated from `lastUpdateId`;
- provider-neutral canonical persistence support.

Therefore an order-book snapshot is not blocked by the MEXC candle-finality problem.

The important limitation is different:

- a REST snapshot is a snapshot fact;
- it is not a historical replay of all prior changes;
- a live WebSocket delta is not itself a complete order-book snapshot;
- live reconstruction requires the provider-prescribed snapshot/version procedure.

## 13. Canonical candle boundary

The current `CanonicalCandle` contract requires:

`is_closed: bool`

with default value `True`.

The contract is frozen and downstream quantitative/market-structure semantics require closed candles for authoritative processing.

No valid third state is available in the current contract.

The following are all rejected as substitutes for authoritative finality:

- `windowEnd <= current time`;
- elapsed interval duration;
- local clock;
- receipt time;
- create time;
- repeated identical payloads;
- next interval appearing;
- REST row availability;
- statistical agreement between REST and WebSocket;
- OHLC geometry;
- synthetic `is_closed`;
- inferred provider closure.

Therefore the current canonical candle boundary remains:

**MEXC candle observation → raw/staging evidence → no canonical candle while finality is unavailable.**

This preserves canonical truth.

## 14. Canonical trade boundary

The existing `CanonicalTrade` contract represents an individual semantic trade event with:

- trade_id;
- instrument_id;
- timestamp;
- price;
- quantity;
- optional aggressor side;
- optional quote quantity;
- provenance.

The contract does not itself contain a statement that the input stream is complete.

Therefore there is an important distinction:

### Valid claim

> “This MEXC trade observation was received and passed the canonical trade field requirements.”

### Invalid claim

> “This canonical trade population is complete for the interval because MEXC trade IDs are continuous.”

The second claim is not supported.

This means the failed TO-P2-011 sequence mechanism does not automatically require rejecting every individual MEXC trade.

However, any downstream quantitative calculation that requires a **complete trade population over an interval** must not silently interpret the available canonical trade set as complete merely because individual trade objects are valid.

This is a downstream semantic applicability boundary, not a reason to fabricate completeness.

## 15. Canonical order-book boundary

The existing `CanonicalOrderBook` contract represents:

- instrument;
- timestamp;
- bid levels;
- ask levels;
- provenance.

It deliberately excludes provider wire sequence fields.

MEXC supplies an authoritative provider mechanism for reconstructing order-book state:

**REST snapshot + WebSocket versioned deltas + documented continuity/reinitialization rules.**

Therefore:

### REST snapshot

A directly acquired MEXC REST snapshot can be semantically represented as a canonical order-book snapshot, subject to normal validation.

### WebSocket delta

A single delta cannot be treated as a complete canonical order-book snapshot.

### Reconstructed live book

A reconstructed live book can conceptually be canonicalized if:

- snapshot is acquired;
- version continuity is verified;
- every delta is applied according to documented semantics;
- any gap causes reinitialization;
- the resulting book satisfies canonical contract validation.

The current Task Order does not authorize implementing that reconstruction.

## 16. Historical versus live populations

### 16.1 Historical K-lines

Historical K-lines provide:

- open time;
- OHLCV;
- close time;
- quote volume.

They are useful evidence.

Current evidence does not establish the canonical finality contract required by Meylux.

Therefore they remain raw/staging observations for the current architecture.

### 16.2 Live K-line stream

Live K-lines are explicitly mutable observations.

The bounded live observation demonstrated changing volume and close value inside the same window.

Therefore live K-lines cannot be promoted to finalized canonical candles.

### 16.3 REST trade observations

Current public REST trade observations returned null `id`.

They can still provide price, quantity, timestamp and maker metadata.

The missing identifier means they cannot be authoritatively joined to WebSocket trade IDs.

### 16.4 WebSocket trade observations

WebSocket trade observations provide provider trade data and a schema-level `tradeId`.

They can be retained as provider evidence and, where individual trade semantic requirements are satisfied, represented as individual trade events.

They cannot establish complete interval coverage.

### 16.5 REST order-book snapshot

This is a distinct population with a provider-defined snapshot semantics and update ID.

It is materially stronger than a raw ticker observation.

### 16.6 WebSocket order-book updates

These are incremental observations.

They require the provider-prescribed snapshot/version reconstruction process before they can represent a complete order-book state.

## 22. Existing architectural route assessed

### Route R1 — reject all MEXC data

**Result:** Not justified.

Reason:

The evidence establishes failures of specific semantics, not total provider unusability.

---

### Route R2 — force all MEXC data through CanonicalCandle

**Result:** Not defensible.

Reason:

Trades/order books are not candles, and MEXC candle finality remains unavailable.

---

### Route R3 — Trade→Candle with inferred completeness

**Result:** Not defensible on current evidence.

Dependencies that fail:

- trade sequence continuity;
- exact gap recovery;
- provider finality.

---

### Route R4 — evidence-first capability preservation

**Result:** Defensible conceptually.

Structure:

`MEXC provider → AcquisitionEnvelope → raw/staging evidence`

Then independently:

- valid individual trade → existing CanonicalTrade where semantically applicable;
- valid REST order-book snapshot → existing CanonicalOrderBook;
- provider-prescribed depth reconstruction → future authorized canonical live order book;
- ExchangeInfo → existing CanonicalInstrument;
- kline observation → raw/staging only while finality unavailable;
- ticker/book-ticker → provider evidence;
- historical datasets → provider evidence unless dataset-specific semantics satisfy an existing canonical contract.

This route does not weaken canonical truth.

## 23. Preferred path

The preferred conceptual path is therefore:

### Layer A — preserve maximum MEXC evidence

Preserve all valid MEXC acquisition observations with:

- provider identity;
- instrument identity;
- event type;
- event time;
- receipt time;
- source sequence;
- provenance;
- raw payload;
- acquisition state.

This layer already exists.

### Layer B — promote only independently defensible semantic facts

Promote only when the target contract's semantics are satisfied.

Examples:

- instrument metadata → CanonicalInstrument;
- individual trade event → CanonicalTrade, without claiming stream completeness;
- REST order-book snapshot → CanonicalOrderBook;
- reconstructed live order book → CanonicalOrderBook only after provider version continuity is actually implemented and verified.

### Layer C — keep unsupported semantics out

Do not promote:

- MEXC live/historical K-line as finalized CanonicalCandle;
- trade-stream completeness;
- exact trade gap recovery;
- inferred provider finality;
- synthetic closure.

### Layer D — downstream semantic awareness

Any quantitative component requiring a complete trade population must treat the absence of completeness proof as a data-availability/semantic limitation.

It must not silently infer completeness from the existence of valid individual trades.

## 24. Why this route does not require a new truth layer

A new truth layer is unnecessary because the current architecture already separates:

1. acquisition evidence;
2. normalization;
3. canonical semantic contracts;
4. persistence;
5. downstream quantitative interpretation.

The missing capability is not generic evidence storage.

The missing capabilities are specific provider semantics:

- MEXC candle finality;
- MEXC complete trade sequence;
- exact trade REST reconciliation.

The architecture can therefore remain frozen while preserving more valid provider information.

## 26. Replay implications

### Raw evidence

Replay of the same MEXC acquisition envelope remains deterministic because:

- payload is retained;
- event identity is deterministic;
- source sequence is retained;
- provenance is retained.

Replay therefore does not need a new semantic mechanism.

### Canonical trade

Replay of an individual valid trade can remain deterministic.

It does not establish that the surrounding trade stream was complete.

### Canonical order book

Replay of a reconstructed order book requires replaying the provider version chain and snapshot initialization rules.

A replay implementation must fail closed if continuity evidence is missing.

### Candle

Replay cannot upgrade an unavailable-finality candle into finality.

Repeated replay is still only repeated evidence.

---

## 27. Identity implications

### Trade identity

MEXC trade ID may be retained as provider identity material.

However, the lack of a provider-established sequence/completeness invariant means it must not be interpreted as a completeness cursor.

### Order-book identity

Provider version is evidence about state transitions.

The existing CanonicalOrderBook intentionally excludes provider sequence fields, so sequence information remains upstream provenance/evidence.

### Candle identity

Open time identifies the MEXC K-line, but does not establish immutable finality.

No identity change is authorized.

## 28. Failure-mode analysis

The evidence-first architecture explicitly handles:

### Provider unavailable

Retain failure evidence at acquisition boundary; do not fabricate values.

### WebSocket disconnect

Retain stream/disconnection state; do not claim completeness.

### Trade sequence discontinuity

Classify sequence completeness as unavailable; do not invent missing trades.

### REST trade ID null

Retain REST trade observation if otherwise valid; do not fabricate ID.

### K-line still changing

Retain observation; do not mark canonical closed.

### Depth version gap

Provider documentation requires reinitialization from REST snapshot.

### Depth snapshot limited

Do not claim complete infinite-depth market state; represent the observed snapshot scope.

### Book ticker only

Do not promote it to full order book.

### Historical data available

Do not equate file availability with every semantic guarantee required by canonical contracts.

- preserve valid individual trade observations;

- preserve instrument metadata;
- keep unsupported candle finality and trade completeness outside canonical truth.

Therefore the broader statement "no defensible alternative exists" would be incorrect on the current evidence.
