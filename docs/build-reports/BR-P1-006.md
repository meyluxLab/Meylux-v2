## 3. Implemented Behavior

### 3.1 Worker responsibility boundary

`WorkerSpec` requires an explicit logical worker name, one primary responsibility, inputs, outputs, allowed dependencies, forbidden responsibilities, side effects, resource budget, and failure-isolation statement. `AsyncWorker` executes only a supplied handler at the queue boundary.

### 3.2 Queue semantics and FIFO definition

`QueuePolicy` requires explicit owner, producer, consumer, purpose, payload contract, retry, timeout, concurrency, backlog, DLQ, idempotency, retention, and recovery values.

FIFO is explicitly defined at this foundation boundary as **FIFO enqueue and delivery order**. Redis Stream IDs preserve enqueue order and `XREADGROUP ... >` delivers new entries in stream order. FIFO completion order is intentionally **not** part of the contract; bounded concurrency may allow later work to complete before earlier work. No stronger FIFO guarantee is claimed. The deterministic suite exercises the actual enqueue/read path and asserts delivery order.

### 3.3 Retry / crash-window correction

The previous `publish(retry) -> ACK(original)` split transition has been replaced by an atomic Redis Lua retry transition. The backlog invariant is now explicit: **the backlog counter represents active logical work, and replacing a pending original with its retry leaves the counter unchanged**. The transition performs the following as one Redis-side state change:

```text
retry marker absent:
    capacity sanity check (current > max is rejected)
    retry XADD
    retry marker creation
    original XACK
    backlog unchanged (replacement, not additional work)

retry marker already present:
    no duplicate retry XADD
    original XACK
    backlog unchanged
```

Therefore a crash cannot expose the producer-side intermediate state in which a retry exists but the original remains indefinitely pending. Recovery repeats the same atomic transition and is idempotent. Retry markers are retained while the retry is active and removed when the retry is acknowledged, keeping active retry metadata bounded by active retry work rather than creating an unbounded journal.

The retry transition also permits a retry to replace an original message when the queue is exactly at its configured backlog bound; it does not require an additional backlog slot for the replacement. If `XACK` returns `0`, the retry still represents the same active logical work and the backlog counter remains unchanged, preventing both inflation and undercount.

### 3.4 Retry, timeout, failure isolation and DLQ

Retries remain bounded by `max_attempts`. Backoff is deterministic exponential backoff from the configured base. Handler timeouts use `asyncio.wait_for`. Retry exhaustion executes the actual DLQ transfer path, including source acknowledgement and source backlog accounting. Handler failure remains isolated to its queue message.

### 3.5 Retention correction

Redis 7.4 is the verified V2 Redis runtime. Redis 8.2's `ACKED` stream-trimming policy is therefore not assumed. The foundation instead performs an explicit retention sweep using Redis stream IDs and consumer-group pending state. The cutoff is derived from Redis server time and `retention_seconds`; when pending work exists, the safe trim boundary is the earlier of the retention cutoff and the oldest pending entry across consumer groups. Consequently completed history older than the retention boundary can be trimmed, while pending payloads are never crossed by the trim boundary.

This avoids the Redis 7.4 `KEEPREF` failure mode in which a stream payload could be trimmed while its PEL reference remains recoverable only as an ID. Pending work therefore remains physically recoverable until acknowledged.

### 3.6 Stale recovery

`recover_stale` uses bounded `XPENDING` inspection and `XCLAIM` to transfer stale pending work to a recovery consumer. The recovered entry remains pending until the normal handler/ACK boundary.

### 3.7 Redis role

Redis remains transport/coordination only. No authoritative business persistence was added.

## 10. Correction Addendum — CONTROL Retry/Backlog Audit

CONTROL identified a correctness defect in the previous retry/backlog accounting: the retry transition could decrement the backlog when a retry marker already existed, even though the retry remained active. The correction removes backlog mutation from retry replacement entirely. A retry replaces one active logical work item with one active logical work item, so the counter remains unchanged across both marker-absent and marker-existing paths.

The correction also handles `XACK == 0` without incrementing or decrementing the counter, preserving the same active-work representation. Final retry completion still decrements the counter exactly once through the normal ACK path and removes the active retry marker.

Additional deterministic tests directly cover normal retry with backlog preserved, existing retry marker with no backlog decrement, `XACK == 0` with no backlog drift, retry completion marker cleanup and final decrement, and retention after pending work is resolved.

The first runtime harness invocation after correction returned exit code `1` because the verification harness attempted a duplicate publish only after filling its configured backlog, so the implementation correctly returned `QueueOverloaded` before the duplicate-idempotency assertion. The harness ordering was corrected without changing production code, and the final runtime verification returned exit code `0` with all listed checks passing.

## 11. Correction Addendum — DLQ Retention Audit

CONTROL identified that the previous DLQ retention implementation used a TTL on the entire DLQ stream key. That semantics could refresh the stream lifetime on new DLQ activity and therefore did not guarantee a bounded lifetime for older entries.

The correction removes the DLQ stream-key TTL approach. Each DLQ insertion now obtains Redis server time, derives the retention cutoff, and performs `XADD` followed by exact `XTRIM MINID` inside the same Redis Lua transition. Therefore continuous DLQ insertion cannot refresh the retention lifetime of older entries. New entries are retained because their Redis stream IDs are created at or after the cutoff.

The normal `retention_sweep()` also trims the DLQ stream by the same server-time retention boundary, covering idle periods. Main-stream retention continues to use the oldest pending consumer-group entry as its safe trim boundary; DLQ trimming has no pending consumer-group preservation requirement because the DLQ stream is transport history, not active consumer-group work. No new retention metadata was introduced.
