## 1. Executive determination

### Definitive disposition: PATH A — IMPLEMENTABLE WITHIN EXISTING FROZEN CONTRACT/ARCHITECTURE

The current Meylux V2 architecture, provider-neutral acquisition contract, canonical derivatives contract, quality/acquisition evidence contract, and append-only persistence boundaries are sufficient to represent and persist an authoritative derivatives evidence path **without creating a new canonical contract, Stable ID, truth layer, migration family, or architecture invariant change**.

The required future implementation is therefore an additive provider-acquisition capability inside the existing P2 acquisition boundary, followed by existing P3 quality-evidence processing and existing canonical persistence.

However, this assessment does **not** establish PRQ-3 delivery or S-04 availability.

Current provider evidence establishes that derivatives market-data mechanisms exist, but provider/product coverage is not symmetric:

- Binance Futures documentation establishes funding-rate history, open interest, mark/index price and contract/product metadata mechanisms.
- Current repository Binance adapter is explicitly Spot-only.
- MEXC official Futures API exposes public market endpoints for contract information, index price, fair price, funding rate/history and market data, but the current official Market endpoint index does not establish a public OI endpoint.
- A direct provider-sourced basis endpoint was located in Binance COIN-M documentation; this does not establish the same basis endpoint for Binance USDⓈ-M or MEXC and must not be silently substituted with a locally invented basis formula.

Therefore the minimum future implementation boundary must first pin a concrete provider/product combination for which **funding + OI + basis** are each directly and authoritatively available with compatible timestamps and identity semantics. MEXC Futures OI and any unverified basis route remain unavailable until separately established by authoritative provider evidence.

## 10. Historical versus live capability

Provider documentation demonstrates both live/current and some historical REST mechanisms, but the project must not convert endpoint existence into unlimited historical truth.

Future implementation must distinguish:

- current/live observation;
- provider-bounded historical observation;
- provider-specific retention limits;
- incomplete history;
- unavailable history.

A historical request that exceeds provider-supported coverage must return explicit unavailable/insufficient semantics.

No synthetic backfill or reconstructed historical derivatives series is authorized.

## 11. Temporal / no-lookahead requirements

For every admitted observation:

- provider event time remains distinct from receipt/knowledge time;
- `knowledge_time` is derived through the existing P3 quality-evidence rule;
- no observation may enter an S-04 snapshot if `knowledge_time > snapshot.as_of`;
- future observations cannot be used to manufacture prior funding/OI/basis state;
- derived funding velocity and OI delta require explicitly ordered observations;
- non-positive elapsed intervals remain invalid;
- missing history remains insufficient, never zero-filled.

Provider settlement schedules must not be used as a substitute for actual observation timestamps.

## 12. Edge / contradiction / failure analysis

A future implementation under PATH A must explicitly handle:

### Product/identity

- unsupported Futures product → `UNAVAILABLE`;
- unsupported symbol/product type → `UNAVAILABLE`;
- provider/product mismatch → `INVALID`;
- cross-provider substitution → reject;
- silent Spot-to-Futures substitution → reject;
- product contract-type ambiguity → `INVALID/UNAVAILABLE`.

### Payload

- malformed response → `INVALID`;
- missing funding → unavailable field, not zero;
- missing OI → unavailable field, not zero;
- missing basis → unavailable field, not derived unless a ratified deterministic definition exists;
- non-numeric/non-finite numeric field → reject;
- negative OI → reject;
- contradictory provider fields → reject/reroute;
- incompatible instrument identities → reject.

### Time

- missing timestamp → invalid;
- ambiguous timestamp meaning → invalid/unavailable;
- non-UTC normalization must be explicit and deterministic;
- event time and received time remain distinct;
- knowledge time derives only from the established quality-evidence rule;
- future knowledge relative to `as_of` → excluded.

### Replay / idempotency

- identical acquisition envelope → same event identity;
- duplicate evidence → deterministic idempotent persistence;
- contradictory evidence for one logical fact → explicit contradiction;
- canonical record identity conflict → reject;
- no UPDATE/DELETE rewrite of existing authoritative evidence.

### Transport

- timeout/connection failure → unavailable/degraded according to acquisition state;
- provider maintenance → unavailable/degraded;
- HTTP/API error → explicit provider error;
- rate limiting → `RATE_LIMITED`;
- WebSocket disconnect → explicit disconnected/recovery state;
- REST/WS disagreement → contradiction until resolved by provider-authoritative semantics.

### Persistence

- successful DB insertion does not itself establish semantic validity;
- only `VALID` canonical evidence enters canonical persistence;
- quality evidence retains invalid/unavailable acquisition disposition;
- canonical persistence without resolvable evidence lineage must not be promoted as P5-authoritative S-04 input.

## 14. Exact minimum future implementation boundary

A future implementation Task Order should be bounded to:

1. introduce a **separate Futures derivatives acquisition adapter boundary** rather than modifying the existing Spot adapters;
2. select one concrete provider/product route for which funding, OI and basis are each directly authoritative;
3. acquire provider/product metadata sufficient to validate identity;
4. acquire funding observations with provider-defined timestamp semantics;
5. acquire OI observations with provider-defined timestamp semantics;
6. acquire basis as a provider-authoritative field, or only use a separately ratified deterministic formula if such formula is explicitly authorized before implementation;
7. emit existing `AcquisitionEnvelope` with `EventType.DERIVATIVES`;
8. preserve provider identity, provider instrument identity, provenance, event time, receipt time and source sequence where available;
9. route every observation through existing P3 quality-evidence generation/persistence;
10. canonicalize only semantically valid evidence into existing `CanonicalDerivatives`;
11. persist through existing canonical persistence;
12. prove deterministic identity, replay/idempotency, contradiction rejection and append-only behavior;
13. prove no-lookahead against `knowledge_time <= as_of`;
14. explicitly disposition unsupported/unavailable provider/product facts;
15. perform runtime verification only under a separately authorized runtime boundary.

### Provider expansion sequencing

MEXC Futures must **not** be added merely because MEXC Spot already exists.

If MEXC Futures is later selected, its OI acquisition route and exact basis semantics must first be established by authoritative provider evidence. A separate implementation boundary may then extend the same provider-neutral contracts without changing the canonical truth model.
