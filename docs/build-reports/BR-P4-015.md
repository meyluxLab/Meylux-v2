## 1. Executive Result

The remaining P4 S-17 implementation gap was investigated and carried forward to the farthest legitimate Producer boundary.

The authoritative Volume Profile engine already defines the required operation over:

- validated `CanonicalTrade` input;

No session/calendar discovery is required by that engine and none was introduced.

The missing P4 operational capability was the trade-to-P4 propagation/persistence path. That path is now implemented:

1. load persisted `CanonicalTrade` rows for the explicitly supplied interval;
2. validate the stored canonical payload against row identity, instrument, event time and provenance;
3. retain source-record lineage;
4. resolve authoritative `knowledge_time` and venue only from the corresponding `quality_evidence` records;
5. execute the existing ratified `VolumeProfileEngine`;
6. persist the resulting fact surface to the existing append-only `meylux.volume_profile_sessions` table;

The implementation is **not** declared project-level VERIFIED, COMPLETE, or CLOSED.

## 2. Semantic Investigation Result

The authoritative P4 Volume Profile semantics require an explicitly supplied profile interval and explicitly forbid hidden session/calendar discovery.

Accordingly, the implementation does not:

- invent a trading calendar;
- infer rolling sessions;
- derive session boundaries from wall-clock state;
- substitute provider-specific session semantics;
- use candles in place of CanonicalTrade input;
- synthesize historical trades.

The existing open question `OQ-P4-GROUPC-S17-SESSION-BOUNDARY` is therefore not silently "resolved". The operational boundary is explicit: the caller supplies `interval_start` and `interval_end`.

This removes the previously assumed need to invent session semantics for the P4 operational path.

## 3. Implementation

### 3.1 CanonicalTrade acquisition from the governed P4 persistence boundary

Added deterministic read-back of `meylux.canonical_trades` for:

`instrument_id = symbol AND event_time >= interval_start AND event_time < interval_end`

Rows are ordered by `event_time, record_id`.

The stored canonical payload is reconstructed as `CanonicalTrade` and checked against:

- instrument identity;
- provenance identity;
- event timestamp;
- UTC correctness;
- required Decimal fields;
- source-record lineage.

Malformed or contradictory persisted canonical rows fail closed.

### 3.2 Authoritative evidence linkage

Each contributing canonical trade carries its `source_record_id`. The correction cycle no longer treats that lineage field as an evidence identity.

The resolver joins each canonical trade to all matching `meylux.quality_evidence` identities and validates the authoritative correspondence before the profile may claim `knowledge_time` or venue. It requires, for each contributing trade:

- matching `source_record_id`;
- `source_identity_hash` equal to the canonical acquisition/event identity;
- `event_type = TRADE`;
- matching canonical instrument;
- matching event time;
- matching provenance;
- `acquisition_state = AVAILABLE`;
- `quality_state = VALID`;
- `lifecycle_state = ACCEPTED`;
- `knowledge_time = received_at` with a UTC-aware boundary.

Multiple distinct evidence identities for one relevant source/logical fact now fail closed using the existing P3 `ContradictoryQualityEvidence` semantics. No evidence identity is silently collapsed into a dictionary keyed only by `source_record_id`.

The following are never fabricated or inferred:

- `knowledge_time`;
- venue.

If required quality evidence is missing, the persisted Volume Profile disposition is explicitly `UNAVAILABLE` with reason:

`missing_authoritative_quality_evidence`

No provider ID is promoted into venue context.

When authoritative evidence is present, the profile knowledge boundary is the maximum authoritative `quality_evidence.knowledge_time` among all contributing trades: the complete profile cannot be known before the latest contributing evidence is known.

Contradictory explicit venue evidence fails closed. Mismatched source/event/instrument/provenance evidence also fails closed.

The existing ratified engine remains responsible for:

- VAH / VAL;

On replay:
