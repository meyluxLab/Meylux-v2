## 3. Implemented Contract Behavior

### 3.1 `CTR-V2-CANONICAL-CANDLE`

The previously implemented contract is preserved. It remains an immutable validated OHLCV boundary using authoritative `Decimal` price/volume values, UTC timestamps, explicit temporal ordering, provenance, and deterministic rejection of invalid values.

### 3.2 `CTR-V2-CANONICAL-INSTRUMENT`

Implemented as `CanonicalInstrument` with:

- canonical instrument identity;
- base and quote assets;
- market and contract type semantics;
- canonical unit;
- UTC `as_of` timestamp;
- optional non-negative price/quantity precision metadata;
- optional positive `Decimal` contract multiplier;
- active-state boolean;
- mandatory provenance reference;
- immutable frozen dataclass representation;
- rejection of invalid types, empty semantic identifiers, non-UTC timestamps, negative precision metadata, non-finite/non-positive multipliers.

Provider-specific aliases and wire identifiers are intentionally excluded from the canonical object.

### 3.3 `CTR-V2-CANONICAL-TRADE`

Implemented as `CanonicalTrade` with:

- canonical trade identity;
- instrument identity;
- UTC observation timestamp;
- authoritative `Decimal` price and quantity;
- optional authoritative `Decimal` quote quantity;
- optional semantic aggressor side restricted to `BUY` or `SELL`;
- mandatory provenance reference;
- immutable frozen dataclass representation;
- rejection of binary floating-point and non-finite numeric values;
- rejection of non-positive price/quantity values and invalid side/timestamp/provenance values.

Provider wire/event identifiers are not introduced as canonical provider-specific semantics.

### 3.4 `CTR-V2-CANONICAL-ORDERBOOK`

Implemented as `CanonicalOrderBook` with:

- instrument identity;
- UTC observation timestamp;
- immutable tuple-based bid and ask levels represented as `(Decimal price, Decimal quantity)`;
- mandatory provenance reference;
- positive finite Decimal price/quantity enforcement;
- duplicate-price rejection within each side;
- strict descending bid ordering and strict ascending ask ordering;
- rejection of crossed best bid/ask;
- rejection of an entirely empty book;
- immutable frozen dataclass representation.

Provider sequence numbers and wire event identifiers are intentionally excluded from canonical semantics.

### 3.5 `CTR-V2-CANONICAL-DERIVATIVES`

Implemented as `CanonicalDerivatives` with:

- instrument identity;
- UTC observation timestamp;
- optional funding rate;
- optional funding change;
- optional funding velocity;
- optional open interest;
- optional open-interest delta;
- optional basis;
- mandatory provenance reference;
- authoritative `Decimal` numeric representation;
- signed funding/rate/delta/basis values permitted;
- non-negative open interest enforcement;
- non-finite and binary floating-point rejection;
- immutable frozen dataclass representation.

Unavailable optional derivatives evidence is represented by `None`; no fallback or fabricated market value is introduced.

## 4. Common Contract Semantics

All newly implemented contracts follow the existing P1 contract convention:

- frozen dataclass runtime representation;
- explicit Stable ID and version constants;
- authoritative `Decimal` financial/market numeric boundary;
- no implicit rounding or quantization;
- rejection of non-finite Decimal values;
- rejection of binary floating-point values at authoritative Decimal fields;
- timezone-aware UTC timestamps only;
- mandatory provenance reference;
- deterministic validation failure through `TypeError`/`ValueError` according to the violated type/value rule;
- no network, database, filesystem, provider runtime, or wall-clock dependency in contract logic.
