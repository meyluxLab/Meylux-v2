## 1. Executive result

The intermittent failure mechanism was reproduced and identified as a startup/readiness race in the test harness. The TimescaleDB image starts a temporary PostgreSQL server during image initialization, runs `timescaledb-tune`, and shuts down/restarts that server to apply configuration. The previous test harness treated a successful `SELECT 1` as sufficient readiness, which could succeed against the temporary server before initialization completed. The test then began migrations while the entrypoint was stopping that server. The failing migration varied with timing.

The corrected harness waits for the image entrypoint's explicit initialization-complete marker and then verifies `SELECT 1` against the final PostgreSQL server before applying any migration. Failure output now preserves subprocess stdout/stderr and includes container state plus the last 200 PostgreSQL log lines. The failed-`setUpClass` path also explicitly cleans up its container.

On the exact current PR head `fd20194...`, CI Core passed and Docker Foundation passed in two independent runs. The actual P3-009 PostgreSQL suite passed all 7 tests in each observed successful execution. No P3-009 assertion was weakened, removed, or skipped to obtain these results.

## 3. Investigation and root-cause evidence

### 3.1 Historical failures retained

The following failures remain preserved as genuine CI history:
- Docker Foundation run `37015633194`: failed at P3-009 migration execution.
- Docker Foundation run `37015641046`: failed at P3-009 migration execution.
- Docker Foundation run `37017079269`, attempt 1: failed; CONTROL's attempt 2 job `110931344502` passed the full workflow, including P3-009's 7 PostgreSQL tests.

The historical failed logs did not include the original PostgreSQL stderr because the test harness captured subprocess output without emitting it. Therefore, those historical invocations cannot individually be proven to have failed for exactly the same internal PostgreSQL message. Their migration-stage failures are consistent with the race reproduced below.

### 3.2 Reproduced failure with diagnostics enabled

- Diagnostic Docker PR run: [37037250569](https://github.com/meyluxLab/Meylux-v2/actions/runs/37037250569), job `110938385252`.
- Failure occurred at `0004_canonical_quality_state_alignment.sql`.
- Captured stderr: `FATAL: the database system is shutting down`.
- Container logs showed PostgreSQL start and readiness during image initialization, the Timescale `timescaledb-tune` init script changing server configuration, and then a fast shutdown/restart sequence. The migration subprocess was attempted while that server shutdown was in progress.
- The same run logged the Timescale background workers being terminated by the shutdown request and the psql connection being lost.

This is direct evidence of the mechanism, not an inference from exit code 2. It demonstrates that a successful SQL probe against the temporary init server was not a sufficient readiness condition. The fact that prior failures occurred at different migrations is consistent with a timing race.

### 3.3 Root-cause conclusion

**Established for the reproduced failure:** the readiness check could pass before the Timescale/PostgreSQL entrypoint finished initialization and restarted PostgreSQL after `timescaledb-tune`. Migration execution could therefore overlap server shutdown.

**Not claimed:** the precise missing stderr for each historical attempt cannot be reconstructed. The reproduced race explains the observed intermittent boundary and is the condition corrected here; historical records are not rewritten.

## 4. Implementation correction

### 4.1 Final-server readiness

The harness now requires both:
1. the Timescale/PostgreSQL entrypoint marker `PostgreSQL init process complete; ready for start up.`; and
2. a successful `SELECT 1` after that marker.

The migration loop cannot start before both conditions are met. If the condition is not satisfied within 60 one-second probes, the test emits container diagnostics, cleans up, and fails explicitly.

### 4.2 Actionable diagnostics and cleanup

For checked subprocess failures, the harness prints:
- command and exit code;
- captured stdout;
- captured stderr.

On readiness/setup/migration failure, it additionally prints:
- container state, running state, exit code/error, start time, and image;
- the last 200 lines of container logs.

A migration failure names the exact migration. Because unittest does not invoke `tearDownClass` when `setUpClass` fails, the setup failure handler now emits diagnostics first and then removes the ephemeral container. Successful readiness and migration application are also explicitly logged in order.

### 4.3 Workflow trigger coverage

The Docker Foundation pull-request path filters now include:
- `tests/test_p3_009_postgresql.py`;
- `tests/test_p3_009_quality_evidence.py`.

This corrects the evidence trigger gap so edits to the P3-009 evidence harness exercise the Docker Foundation workflow before merge.
