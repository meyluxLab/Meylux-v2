## 2. F1 — WebSocket Reconnect Bound

`src/meylux/acquisition/binance.py` was corrected so that both clean WebSocket termination and exceptional connection failure consume reconnect attempts.

For one `stream()` invocation:

- `max_reconnects` is a hard upper bound on reconnect attempts;
- clean provider-side termination cannot bypass the bound;
- exceptional connection failure cannot bypass the bound;
- reconnect delay remains bounded by the existing `RetryPolicy`;
- reconnect and exhaustion telemetry remains explicit;
- exhaustion yields a canonical `DISCONNECTED` acquisition envelope and terminates the invocation.

Regression coverage was added for repeated clean connection termination, clean termination with `max_reconnects=0`, and exceptional connection failure/exhaustion.

## 3. F2 — Canonical Provider Failure Mapping

The Binance adapter maps applicable provider failures into the existing `AcquisitionEnvelope` failure semantics using the existing `ProviderError` structure.

Covered canonical states include:

- `RATE_LIMITED` for Binance HTTP 418/429 conditions;
- `UNAVAILABLE` for bounded transport/server failures;
- `DISCONNECTED` for WebSocket reconnect exhaustion;
- `INVALID` for malformed/invalid REST or WebSocket provider payloads.

The adapter retains `BinanceTransportError` as an internal/provider-specific exception mechanism, while externally returned acquisition results carry canonical acquisition state and `provider_error` where required by `CTR-P2-001`.

No new canonical state, Enum, Stable ID, contract, or identity model was introduced.
