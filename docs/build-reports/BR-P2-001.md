## 4. Correction Evidence

### 4.1 Enum float bypass

`_freeze()` now checks an Enum's underlying `.value` and rejects a binary `float` before the value can be accepted into the immutable payload representation.

`_normalize()` now performs the same explicit float rejection and recursively normalizes the Enum's underlying value. Therefore a float-valued Enum cannot bypass the canonical serializer's existing binary floating-point rejection.

Regression test added:

`test_float_valued_enum_payload_is_rejected`

The test constructs an actual `AcquisitionEnvelope` with an Enum-valued payload and asserts that construction rejects the unsupported binary floating-point value. This exercises the supported payload construction path rather than testing a helper in isolation.

## 5. Contract Semantics

### Provider and instrument identity

`ProviderIdentity` separates provider identity from adapter identity/version. `InstrumentIdentity` carries both the canonical V2 instrument identity and the provider-side instrument identifier without embedding Binance/MEXC-specific behavior.

### Provenance

`Provenance` binds a provenance identifier to the exact provider identity and acquisition method. An envelope whose provenance references a different provider is rejected.

### Acquisition state

The contract explicitly represents:

- `AVAILABLE`
- `DEGRADED`
- `UNAVAILABLE`
- `STALE`
- `INVALID`
- `DISCONNECTED`
- `RATE_LIMITED`
- `SEQUENCE_GAP`
- `INSUFFICIENT_DATA`

Degraded/failure states require structured `ProviderError`; an `AVAILABLE` envelope cannot carry a provider error. This preserves missing/unreliable acquisition conditions explicitly.

### Deterministic serialization and identity

The envelope is recursively immutable. Canonical serialization uses sorted JSON keys and compact separators. Decimal values are represented as exact strings; binary floating-point values and non-finite Decimal values are rejected, including the corrected Enum bypass path.

`event_id` and `deduplication_key` are the SHA-256 digest of deterministic provider/instrument/event/time/sequence/payload identity material. Receive time, provider error detail, and capability state do not alter this identity.

### Phase 2 → Phase 3 boundary

The envelope is a raw/staging acquisition representation. It does not normalize provider values into canonical analytical truth and does not take ownership of Phase 3 Validation / Normalization / Data Quality behavior.

## 10. Known Design Considerations

- Source sequence remains an opaque provider-neutral string. Later provider adapters must map provider sequence semantics into this field without redefining canonical contract identity.
- `event_id` intentionally includes payload in addition to source sequence. This protects same-timestamp collisions when a trustworthy source sequence is absent, while allowing receive-time changes during replay.
- Provider-specific wire schemas, retry algorithms, transport implementations, and live-stream lifecycle behavior remain outside this Step and belong to later provider/collector Steps.
