## 4. Current MEXC WebSocket implementation

The current MEXC Spot V3 public WebSocket endpoint remains:

`wss://wbs-api.mexc.com/ws`

Current subscription channels implemented by the adapter:

- Trade: `spot@public.aggre.deals.v3.api.pb@100ms@<SYMBOL>`
- Incremental depth: `spot@public.aggre.depth.v3.api.pb@100ms@<SYMBOL>`
- Kline: `spot@public.kline.v3.api.pb@<SYMBOL>@Min1`

The adapter now expects binary Protocol Buffers market-data payloads and decodes the current MEXC `PushDataV3ApiWrapper` envelope/body fields for the authorized trade/depth/kline capabilities.

The deterministic decoder covers the corresponding current public protobuf message structures for:
- aggregated deals;
- aggregated incremental depth;
- spot kline.

Legacy JSON market-data payloads are explicitly rejected rather than silently accepted as current protocol data.

The MEXC Spot documentation states that the current WebSocket market streams use Protocol Buffers and provides the `.pb` channel forms and protobuf integration procedure. The official MEXC `websocket-proto` definitions were used as the wire-schema reference.

The user-provided note concerning `wss://contract.mexc.com/edge` was also checked against the official MEXC Contract API documentation. That endpoint is the MEXC Futures/Contract WebSocket service and is not substituted into this Spot V3 adapter, because `TO-P2-003` implements the public Spot acquisition surface already established by its REST endpoints and does not authorize a futures adapter.

## 5. REST and failure handling

MEXC public Spot V3 endpoints remain isolated inside the adapter:
- `/api/v3/exchangeInfo`
- `/api/v3/depth`
- `/api/v3/trades`
- `/api/v3/klines`

Failure semantics remain:
- HTTP 429 → `RATE_LIMITED` with bounded retry;
- HTTP 5xx → `DEGRADED` with bounded retry;
- other HTTP 4xx → `UNAVAILABLE`;
- transport failures → `UNAVAILABLE` with bounded retry;
- malformed REST payloads → `INVALID`;
- malformed protobuf stream payloads → `INVALID`;
- exhausted WebSocket reconnects → `DISCONNECTED`;
- provider API error payloads → canonical `UNAVAILABLE` / `ProviderError`.

Retry/reconnect remains bounded; there is no unbounded loop.
