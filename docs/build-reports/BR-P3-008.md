## 4. Architectural Mapping

The implementation preserves the verified P3-001 through P3-007 contract boundary and does not introduce Phase 4 analytical, intelligence, opportunity, arbitrage or trading behavior.

The persistence boundary accepts only a canonical-eligible `VALID` quality assessment with complete provenance, source identity and lineage references. Provider wire structure remains upstream of normalization.

The event boundary is a normalized provider-neutral envelope on `stream:canonical:market_events`.

## 5. Persistence Design

Migration `0003_canonical_persistence_event_outbox.sql` establishes:
- `canonical_instruments`
- `canonical_candles`
- `canonical_trades`
- `canonical_orderbook_depth`
- `canonical_derivatives`
- `data_quality_logs`
- `canonical_event_outbox`

Canonical records contain deterministic record/event identity, canonical payload JSON, canonical bytes, quality state/score, provenance, source identity, lineage parent identity and UTC persistence time.

Canonical history is append-only at both privilege and trigger boundaries. Application runtime privileges allow SELECT/INSERT but not UPDATE/DELETE/TRUNCATE on canonical tables.

The canonical insert and outbox insert occur inside one database transaction. Duplicate record identity is idempotent and identity conflicts are rejected.

The outbox is mutable only for publication acknowledgement and is ordered by a database-generated sequence.

## 6. Event-Handoff Design

The relay consumes pending outbox rows in sequence order and publishes normalized fields only. It does not expose provider-specific wire structure.

Redis publication uses a stable event identity and an atomic Lua check/publish/remember operation. Redis 7 compatibility is preserved; newer Redis 8.6-only IDMP syntax is not required.

The stream is bounded with approximate MAXLEN retention. Idempotency keys have bounded TTL. The authoritative database outbox remains the recovery source when Redis is unavailable or a publication acknowledgement is lost.

A publication failure raises an explicit handoff error and leaves the outbox publication marker unchanged.

## 7. Quality / Lineage Preservation

The persistence boundary requires:
- `DataQualityState.VALID`;
- canonical eligibility;
- provenance ID;
- source record ID;
- lineage parent ID.

The transaction also records the quality state/lifecycle, score, reason codes, validation result, lineage references and payload fingerprint in `data_quality_logs` when a quality assessment is supplied.

Non-promotable evidence is rejected before canonical insertion.

## 10. Failure / Recovery Matrix

Implemented handling:
- database transaction failure → transaction rollback; no canonical/outbox partial commit;
- duplicate canonical record → idempotent no-op when event identity agrees;
- canonical identity conflict → explicit error;
- Redis publication failure → explicit EventHandoffError; outbox remains pending;
- publisher crash after Redis publication before DB acknowledgement → stable Redis idempotency key prevents a duplicate within the bounded deduplication window; outbox remains recoverable;
- Redis restart/loss of ephemeral idempotency keys → authoritative outbox permits replay, with stable event identity for downstream idempotency;
- stream growth → bounded MAXLEN retention;
- relay batch size → bounded 1..1000;
- canonical quality rejection → no canonical persistence.
